# T70L 看电视 App · 交付说明（v4 · 2026-11-06）

## 一句话

自己写的极简直播播放器，**33 KB**，Android 4.4 原生 HLS，装好就能看：42 个台（央视 + 卫视 + 地方）。
**v4 已根治"播一两分钟整屏冻死"**（根因与验证见 §6.3）。

## 1. 为什么不用现成的

T70L 是 **Android 4.4.4 / API 19 / 1GB RAM**，这是硬约束：

| 方案 | 结论 |
|---|---|
| ExoPlayer（GitHub 主流播放器都用它） | ❌ minSdk 21+，装不上 |
| 各类 IPTV App（TVBox / 我的电视…） | ❌ 基本都是 minSdk 21+，或依赖 WebView 新版内核 |
| VLC for Android | ❌ 包 60MB+，1G 内存吃不住 |
| **系统 MediaPlayer 原生 HLS** | ✅ 4.4 自带，零依赖，APK 16.9 KB |

Android 4.4 的 MediaPlayer 从 3.0 起就支持 HLS（m3u8），只吃 **MPEG-TS** 分片，不认 fMP4（.m4s）。
选源时已经按这个筛过，所以能播。

## 4. 换源（不用重新编译）

频道表格式：`分组|名称|地址`，一行一个。

两种改法：

**A. 改内置**（要重编译）
编辑 `app/assets/channels.txt` → `bash build_tv.sh` → 重装。

**B. 改外部**（不用重编译，推荐）
```bash
adb push channels.txt /sdcard/tv/channels.txt
adb shell am force-stop com.lm.tv
adb shell am start -n com.lm.tv/.MainActivity
```
App 启动时**优先读 `/sdcard/tv/channels.txt`**，没有再回落到 assets 里的。所以以后换源只要 push 一个文本。

## 6.1 换台为什么要 1.5~3 秒（v2 提速记录）

v1 换台要将近一分钟，根因不是网速，是代理自己把自己锁死了：

| # | v1 的问题 | v2 的修法 |
| --- | --- | --- |
| 1 | HTTP 服务和分片下载**共用 4 线程池**，播放器一连上就占满，下载任务永远排不上，只能干等 40 秒超时 | HTTP 服务独立 10 线程池，与下载彻底解耦 |
| 2 | 窗口里 5 个分片平分带宽，首片只分到零头 | 一次只攻首片，独占全部带宽；下完再按顺序下后面的 |
| 3 | 必须整片 11MB 全落地才开始返回 | `RandomAccessFile` 预分配 + 边下边发，播放器读到哪就吐到哪 |
| 4 | 播放器比预取线程早来要首片，拿到 404 直接报 `-1004` 再重试 | 分片请求时现场创建并开始下载，不让它落空 |
| 5 | 播放列表每次回源 | 内存缓存 3 秒 |
| 6 | 切台后旧任务还在抢带宽 | 代次计数 `gen`，旧任务每个数据块都检查，切台即放手 |

实测（CCTV-11 / 12 / 13 连切三次）：**2.79s / 2.54s / 1.43s**。

## 6.2 换台快了，但切过去还要卡十几秒（v3 记录）

v2 把换台压到 3 秒内，但切完那一瞬开始，新台会卡 10~20 秒才顺。根因是**预取和播放器各下各的**：

| # | v2 的问题 | v3 的修法 |
| --- | --- | --- |
| 1 | 上游窗口是 5 片 × 10 秒，Android HLS 播放器起播点是**倒数第 2~3 片**，v2 却只预取**最旧的第 1 片**——我们下的它不用，它要的我们没下 | 改写 playlist 时把窗口**裁成最后 3 片（30 秒）**，播放器起播点必然落在窗口内靠前的位置，预取顺序就对齐了播放顺序 |
| 2 | 分片切成 2 段，`prefix` 只由第 0 段推进，第 0 段（5.7MB）下完 prefix 就停住，播放器读到那里必须干等另一段 join（约 9 秒）——**这正是那十几秒卡顿** | 分片按 **512KB 切块**，6 条连接从块 0 开始流水线并行，块按序完成就连续推进 prefix，prefix 一直往前跑 |
| 3 | 单连接 0.64MB/s，追不上 1.085MB/s 的消耗，buffer 永远填不满 | 6 连接并行（实测 2.0~2.5MB/s），是消耗的 2 倍以上，buffer 只增不减 |
| 4 | 播放器要的片排在队尾，得等前面下完 | `playing` 插队：哪个片被播放器读了，6 条连接立刻全部转过去 |
| 5 | 窗口内靠后的片被请求时是 0KB | **头部预铺**：先给窗口内每片各下 1.5MB，再回头按播放顺序补满 |

实测（连切 5 个台 + 90 秒长稳）：

- 切台后解码全程 **29~30fps 不掉帧**
- 每次换片时本地已有 **1.5~3MB** 缓冲，最差也是 0KB 但在 0.8 秒内补齐
- 90 秒长稳 **零错误、零重试**
- 内存：播放 1080i 时空闲 143MB；磁盘缓存 54MB（上限 57MB）

## 6.3 播一两分钟整屏冻死（v4 已根治，2026-11-06）

**现象**：任何频道进去放一会儿（实测最短 30 秒，长则 1~2 分钟），整个画面定住，不出错、不重连、永远不动。
只有退出重进才恢复。

**现场取证**（不是猜的）：

| 取证手段 | 结果 |
| --- | --- |
| 隔 4 秒截两张图 | md5 完全一致 → 画面确实冻住 |
| `kill -3` 线程转储 | 代理的 10 个 HTTP 线程**全部空闲**，没人卡住 |
| `/proc/net/tcp` | 播放器（mediaserver）那条到 18765 的连接 ESTABLISHED 但收发队列都是 0 |
| 日志 | 播放器**不再来要任何东西**，代理还在照常下载新分片 |

也就是说：**代理是好的，是播放器自己不吃了。**

### 6.3.1 根因一：m3u8 被播放器的 HTTP 缓存住了

v3 的响应里既没有 `Cache-Control`，playlist 里又写着 `#EXT-X-ALLOW-CACHE:YES`。
Chromium 网络栈对"没有缓存指令的 200 响应"会**启发式缓存**——于是播放器后续刷新拿到的永远是同一份
m3u8，里面那 3 片它已经播完了 → 它认为"没有新内容" → 安静地什么都不再请求。

### 6.3.2 根因二：失败路径返回的是 `200 OK + 一段文字`

v3 拿不到分片时返回 `HTTP/1.0 200 OK` 加一句 `no file` / `size unknown`。
播放器把这段文字当 TS 数据吃掉，既不报错也不推进 → 卡死而不是重连。

### 6.3.3 根因三：MEDIA-SEQUENCE 算错了

`#EXT-X-MEDIA-SEQUENCE` 用的是"上游那个数 + 裁剪偏移"，而上游那个数其实是**最新一片的编号**
（不是第一片），叠一起必然对不上，窗口一抖序号还可能回退。

### 6.3.4 根因四（最阴的一个）：一块 512KB 卡住，整片永远凑不齐

v3 把分片切成 23 块、用"单调自增的块号"一次性分配给 6 条线程。只要某条连接在一块的读取里
**假死**（上游限速时会"滴流"式回字节，`read` 每 8 秒都能拿到一两个字节，永远不触发超时），
要么它自己卡死、要么这块 4 次重试后被标成"完成"，**此后没有任何线程会再碰这块**。
`prefix`（连续可读前缀）就永久停在那个块边界。

实测就卡在 **1536KB**——正好是第 3 块（3×512KB）的边界。日志铁证：

```
REQ 片 7269458 第1次 prefix=1536KB
REQ 片 7269458 断流于 1536/11108KB      ← 播放器读到 1.5MB 干等 20 秒
REQ 片 7269458 第2次 prefix=1536KB      ← 重试还是 1.5MB
REQ 片 7269458 断流于 1536/11108KB
……（反复 2 分钟，直到看门狗把播放器重建）
```

### 6.3.5 v4 的六处改动

| # | 改什么 | 怎么改 |
| --- | --- | --- |
| 1 | 彻底禁掉缓存 | 所有响应加 `Cache-Control: no-store,no-cache,must-revalidate` + `Pragma` + `Expires:0`；playlist 写 `ALLOW-CACHE:NO`；播放地址再带一个递增会话号，缓存键每次都不同 |
| 2 | 失败就是失败 | 拿不到分片返回真正的 **404/503**，播放器立刻报错走重连，不再吞文字干等 |
| 3 | 序号用真编号 | 直接取分片文件名里的 `live_1_1_<编号>.ts` 数字当 media sequence，严格单调，永不回退 |
| 4 | 窗口放到 5 片 + 只前进不后退 | 跟上游一样 5 片（50 秒余量）；某次回源失败就继续用上一份，绝不给播放器更旧的窗口；离开窗口的片再留 60 秒 |
| 5 | **块改成"可抢回"调度** | 每块带认领时间，**22 秒硬超时**没下完就释放、别的线程立刻重下；认领超 25 秒也可以被抢。任何一块都不可能再永久拖住 prefix |
| 6 | 加画面看门狗 | 兜底：播放器 35 秒一次数据都不来（或 120 秒没吃到新分片）就静默重建播放器，1~2 秒自己回来；如果判定是**上游断网**，只提示"信号中断，正在重连…"、不瞎重建 |

## 7. 学习强国的源：为什么没做进去（重要）

按你的要求，用 静态分析 把红米上的学习强国（`cn.xuexi.android` v2.74.0，39102 个类）翻了一遍，结论如下。

### 7.1 静态分析结论

| 查什么 | 结果 |
|---|---|
| 13 个 dex 全量扫 `m3u8` / 直播 URL | **零命中**，源码里没有任何硬编码直播源 |
| 频道数据来源 | `STTVBStationRemoteDataSource.requestChannelDataFromNet()` → `TVBFeedChannelService.getChannelItems()` |
| 走什么协议 | 阿里 **LWP 私有 RPC**（不是 HTTP，有 appKey + 签名） |
| 播放器 | `ali_tvsharelib`（阿里 TV SDK）+ `com.torch.open.feeds` 内容平台 |
| 频道对象 | `STTVBStation{ title, liveUrlsArray, liveQualities, ... }` — 地址是**运行时下发**的 |

也就是说：**学习强国自己不存直播源**，登录后向服务器要，返回的 JSON 里才有 `liveUrlsArray`。

### 7.2 三条路为什么都堵着

1. **抓包**：Android 14 + targetSdk 30，默认不信任用户 CA 证书，非 root 抓不到 HTTPS 明文。
2. **模拟调用**：LWP 要 appKey + 签名 + 登录态，脱离 App 调不通。
3. **静态提取**：源压根不在包里。

### 7.3 还差什么

**差一个登录态。** 红米上的学习强国现在是未登录（启动直接落在 `SignUpWithPwdActivity`），
进不去「电视台」页面，所以也没法做运行时观测。

如果你愿意在红米上登录一次，我可以继续做这两件事：
- 用 `logcat` 抓播放器实际请求的 URL（部分播放器会打日志）
- 用 `/proc/net/tcp` 定位 CDN 域名，反向推接口

但要提醒一句：学习强国的源大概率带**时效签名**（`auth_key` 之类），就算抓出来，
也可能几小时到几天就失效，做进 App 里得频繁更新。

### 7.4 更稳的长期方案

- **DTMB 地面波**：国家公益信号，央视 1-17 + 省卫视免费，插天线就能看，断网也能看

## 九、源失效问题的根治（2026-11-06 晚，重要）

### 事故：开播不到一天全挂

原来 42 个台**全部指向同一台源服务器** `112.123.243.37:50085`。这台服务器下线后，
整个 App 就是"点哪个台都加载不出来"。表现是日志里 `playlist 生成失败: empty playlist`。

### 根治思路：源不能写死，必须会自己更新

公共直播源的寿命以"天"计，任何静态表都会烂。所以改成三层：

| 层 | 做什么 | 失效时 |
|---|---|---|
| 路由器（OpenWrt） | 每 2 小时 `wget` 一次 GitHub 上的聚合列表，存到 `/www/tv/` | 盒子用上次的文件 |
| App | 从 `http://192.168.1.1/tv/result.m3u` 取列表，按台名归一，写 `/sdcard/tv/channels.txt` | 回落到内置表 |
| 播放 | 每个台 6~8 条线路，失败自动换下一条；记住每个台上次能播的那条 | 全部不通 → 触发重新找源 |

**为什么必须让路由器代拉**：这台盒子是 Android 4.4，Java 的 TLS 栈太旧，
拉 `raw.githubusercontent.com`、`gh-proxy.com` 这类强制 TLS1.2 的站，
一律 `SSLHandshakeException: handshake aborted`（手动开 TLSv1.2 也没用，缺密码套件）。
路由器 24 小时在线且 TLS 正常，让它代拉、局域网内用明文 HTTP 给盒子，是最稳的组合。

路由器侧脚本 `/root/tv_sources.sh` + cron `0 */2 * * *`，拉两个列表：
`Guovin/TV` 的 `result.m3u`（约 590 个台）和 `vbskycn/iptv` 的 `iptv4.m3u`。

### 顺便修掉的三个坑

1. **直连播放取代自建代理**（`DIRECT_TEST = true`）
   代理这套（多连接分片预取）在换源后极不稳定：上游首次回源要 3~4 秒，
   而播放器等源代的宽限只有 3 秒 → 判成"空列表" → -1004 → 换源 → 再失败，形成死循环。
   实测这颗 HAL 直连完全够用，链路越短越不容易出错。代理代码保留，改 `DIRECT_TEST = false` 可回退。

2. **冷启动宽限 3s → 12s**，并且不再在等待循环里每 50ms 把 `plAt` 清零
   （那等于把预取线程按最快速度踢起来，一个慢请求被叠加成几十个并发，更容易超时）。

3. **看门狗改用"播放位置"判活**（直连模式）。原来用代理的分片计数，直连下全是没有意义的默认值，
   会把正常播放每 20 秒误判一次冻死。

### 实测

- 自动找源：589 个台 → 归一后落到 42 个台 / 249 条线路，写入 15.8 KB
- CCTV-1、CCTV-6 均能正常起播（画面清晰，播放位置持续推进）
- 记住线路后，再次打开同台 5 秒内起播

### 以后源又全挂了怎么办

不用管，等路由器下一次（≤2 小时）刷新，App 下次打开会自动读新表；
如果那个台的线路全不通，App 会自己触发一次重新找源（10 分钟内只试一次）。
要手动催一次：`ssh root@192.168.1.1 sh /root/tv_sources.sh`，再在盒子上重开 App。

## 十、音量控制（2026-11-06 晚）

T70L 没有独立音量键，进 App 后想单独调音量很别扭，所以在**左侧抽屉里**加了一条音量滑条：

```
看电视                        ‹
音量  ●━━━━━━━━━━━━━━━━━  66%
CCTV-1 综合
CCTV-2 财经
...
```

- 位置在抽屉标题下面、列表上方：抽屉展开时一定看得见、够得着，
  抽屉收起时整块跟着移出屏幕，**画面上不留任何东西**（不遮挡直播画面）。
- 点哪跳哪、按住可拖动，右边实时显示百分比；读写的是系统媒体音量
  （`STREAM_MUSIC`），所以退出 App 后也保持一致。
- 调音量时 `setStreamVolume(..., flag=0)`，**不会弹系统那个音量条**（那也是一层遮挡）。
- 每次展开抽屉会同步一次系统当前音量，别处改过也不会显示错。
