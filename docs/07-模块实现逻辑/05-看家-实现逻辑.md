# 05 · 看家 —— 实现逻辑全解

> 产物：`guard.apk`（约 62KB，零第三方依赖）
> 源码：`源码/05-看家/src/com/lm/guard/`（7 个类，约 2800 行）
> 设备脚本：`源码/05-看家/cam_guard.sh`（root 守护，抢相机 + 代按电源键）
> 运行环境：中移 T70L，Android 4.4.4 / API19 / armv7 / 1G RAM / 1280×800

## 0. 一句话定位

**不录像，只"待人"。** 常驻开着摄像头做人脸检测，检测到人脸就抓一张 1080p 原图、存本地、同时邮件推到你手机。为什么敢不录像——8G 空间按"只存抓拍"算能存两万多张，录像反而半小时就满。

## 2. 四个硬骨头（每个都踩过坑，这是本项目的精华）

### 2.1 `Camera.open()` 永远返回 null

这台设备**只有前摄、没有后摄**。无参 `Camera.open()` 只找 `CAMERA_FACING_BACK`，找不到就返回 null。

```java
cam = Camera.open(0);   // 必须指定编号 0，不能无参
```

顺带：`getSupportedPreviewSizes()` 只返回 **1920×1080** 一个尺寸，没得选。

### 2.2 摄像头是"单客户端"，原厂会议 App 一直抱着不放

Android 4.4 全局只允许一个相机客户端，**先到先得**。原厂 `vulture.app.home` 只要打开过"录像机"或会议界面，就一直持有相机，退回桌面、按 BACK 都不放。

更关键的是：**这个 App 拿不到 root**（`Runtime.exec("su -c id")` 返回 `rc=1`）。所以不能让 App 自己 force-stop 原厂应用。

解法：走一条**文件通道**，借已存在的 root 守护脚本：

```
看家 open 失败
  → 写 /sdcard/HomeGuard/.need_cam（请求文件）
  → cam_guard.sh（root，每 2 秒轮询）发现文件
  → 确认相机确实被占 → am force-stop vulture.app.home → 删标志
  → 看家每 2.5 秒重试 Camera.open(0)，直到抢到（实测 10 秒内）
```

`cam_guard.sh` 是这台机器上既有的 root 守护（随开机启动），我们只是**扩展了它的轮询逻辑**，没有新开 root 通道。

### 2.3 Android 4.4 发不出 QQ 邮件（两个独立原因，都要修）

**(a) 系统根证书库太老**：`Trust anchor for certification path not found`。QQ 现在用的 CA 不在 4.4 的信任列表里。
→ 自定义 `X509TrustManager` 宽松校验（仅用于本机发信通道）。

**(b) 默认不启用 TLS 1.2**：必须显式打开。
```java
s.setEnabledProtocols(new String[]{"TLSv1.2", "TLSv1.1", "TLSv1"});
```

后续还有一个坑：`EP` 阶段返回 **550 The "From" header is invalid**。原因是 RFC2047 的 `=?UTF-8?B?...?=` **只能编码显示名，地址必须留在外面**：
```
From: =?UTF-8?B?VDcwTOeci+Wutg==?= <your-email@example.com>   ✓ 正确
From: =?UTF-8?B?VDcwTOeci+WutSA8Li4uPg==?=                ✗ 错误（地址被一起编码）
```

### 2.4 1080p 预览把 GC 拖死

`setPreviewCallback` 每次分配 3MB 的 `byte[]`，15fps 就是 45MB/s 的垃圾 → GC 占 22% 一个核、整机 74%。

→ 改 `setPreviewCallbackWithBuffer` + `addCallbackBuffer` 复用缓冲，用完再还。
**GC 从 22% 降到 0，整机从 74% 降到 39%（约 6.5%）。**

```java
int bufSize = lastFrameW * lastFrameH * 3 / 2;   // NV21 大小
for (int i = 0; i < 2; i++) cam.addCallbackBuffer(new byte[bufSize]);
cam.setPreviewCallbackWithBuffer(this);
// onPreviewFrame 里：不用这帧就立刻 addCallbackBuffer(data) 还回去
```

## 3. 人脸检测链路（核心算法）

### 3.1 数据流

```
onPreviewFrame(NV21, 1920×1080, ~15fps)
  → 跳帧（亮屏每 12 帧检测一次 / 熄屏每 3 帧）
  → downscale 到 480×270（RGB565）
  → android.media.FaceDetector.findFaces（系统自带，API1 就有）
  → 命中判定 → 抓拍 → 存盘 → 邮件
```

### 3.2 为什么要下采样到 480×270

- 系统 `FaceDetector` 每次约 200ms，1080p 全图会太慢
- 480×270 是"远处人脸不漏检"和"速度够快"的平衡点
- 实测眼距 20~32px、置信度稳定 0.51

### 3.3 误报控制（双条件）

```java
if (conf >= cfg.minConfidence && eye >= cfg.minEyeDist) { hit = true; }
```

- `confidence ≥ 0.35`（默认，越小越灵敏、误报也多）
- `眼距 ≥ 16px`（眼距太小说明是纹理误检，不是真人）

### 3.4 NV21 → RGB565 下采样（手写，不依赖 YuvImage）

`GuardService.downscale()` 里手写了 YUV→RGB 转换，关键细节：
- 用**步长采样**（stepX = sw/dw），不是先缩全图再取
- UV 分量按 `frameSize + (sy >> 1) * sw` 定位（NV21 是 Y 平面 + 交错的 VU 平面）
- 直接用整数移位做 YUV→RGB（`91881*V >> 16` 这类定点算法），避免浮点

### 3.5 去重与新事件判定

```java
static final long FACE_GONE_MS = 45000;   // 人离开 45 秒以上，再回来算新事件

if (lastFaceSeenAt > 0 && now - lastFaceSeenAt > FACE_GONE_MS) {
    lastShotAt = 0;   // 清掉冷却，允许立刻拍
}
if (now - lastShotAt < cfg.cooldownSec * 1000L) { return; }  // 冷却内不重复报
```

同一个场景 60 秒（`cooldownSec`，可配）内不重复报；人离开 45 秒再回来算新事件。

### 3.6 抓拍：直接吃 NV21 编 JPEG，不转 Bitmap

```java
YuvImage yi = new YuvImage(nv21, ImageFormat.NV21, w, h, null);
yi.compressToJpeg(new Rect(0, 0, w, h), 78, bo);   // 质量 78
```

省掉一次 `nv21 → Bitmap` 的 8MB 内存分配。

## 4. 离屏预览（SurfaceTexture）

关键设计：服务自己持有一个 `SurfaceTexture`，不依赖任何 Activity 的 SurfaceView。

```java
offscreen = new SurfaceTexture(10);
offscreen.setDefaultBufferSize(1920, 1080);
cam.setPreviewTexture(offscreen);   // 预览数据进这个离屏纹理
```

好处：**切到任何界面（包括息屏）都不中断检测**。界面（MainActivity）只显示"最近一张抓拍"的静态图，不参与相机数据流。

## 5. 息屏值守（出门场景）

看家是给"人不在家"用的，所以屏幕必须能关。但普通应用没有 `DEVICE_POWER` 权限，按不了电源键。

### 5.1 关屏通道（复用 cam_guard.sh 的 root）

```
App 写 /sdcard/HomeGuard/.need_screenoff
  → cam_guard.sh（root，每 2 秒轮询）发现文件
  → 先确认 mScreenOn=true（已经黑了就不按，免得又点亮）
  → /system/bin/input keyevent 26   （代按电源键）
```

### 5.2 三个坑

1. **busybox 没有 `dumpsys` 子命令**：脚本里写 `$BB dumpsys power` 会静默返回空、永远判成"已经黑了"。要用系统的 `dumpsys`。
2. **Toast 窗口带 `FLAG_KEEP_SCREEN_ON`**（最阴的一个）：点按钮时弹的提示还挂在屏幕上，这期间按电源键关不掉。所以 App 里等 3.2 秒（Toast 消失）再写请求文件，cam_guard.sh 里再补一次"2 秒后还亮就重按"兜底。
3. **不能加 `FLAG_SHOW_WHEN_LOCKED`/`FLAG_DISMISS_KEYGUARD`**：实测会让刚关掉的屏幕立刻又亮起来。

### 5.3 跳帧间隔自适应（熄屏相机降帧）

熄屏后相机帧率掉到 2~8fps，如果还按亮屏的 12 帧跳帧，一次检测要等 4 秒以上。

```java
int detectEvery() {
    // 每 2 秒重新查一次屏幕状态
    everyCache = pm.isScreenOn() ? 12 : 3;   // 亮屏 12 帧 / 熄屏 3 帧
    return everyCache;
}
```

实测：亮屏 0.6 次/秒，**熄屏 0.8~1.3 次/秒**（反而更快，因为熄屏时几乎每帧都检测）。人进门 1 秒内就被抓。

### 5.4 亮屏自动回看家

服务注册 `ACTION_SCREEN_ON` 广播，值守中亮屏时延迟 1.2 秒 `startActivity` 切回看家页。可用 `Prefs.autoShowOnWake` 关掉。

## 6. 邮件（手写 SMTP，零依赖）

`Mail.java` 手写 SMTP 协议，替代 JavaMail（会大 300KB）：

| 端口 | 协议 | 适用 |
|---|---|---|
| 465 | SSL（直接 TLS 握手） | QQ `smtp.qq.com`、163 `smtp.163.com` |
| 587 | STARTTLS（明文升级） | Gmail `smtp.gmail.com` |
| 25 | 明文 | 备用 |

三个关键实现点：
1. TLS1.2 显式启用（4.4 默认不开）
2. 自定义 X509TrustManager 宽松校验（4.4 根证书太老）
3. RFC2047 编码：显示名用 `=?UTF-8?B?...?=`，地址留外面

邮件是**同步发送**（在 worker 线程，不阻塞检测），失败计入"发送失败"，照片仍留本地。

## 7. 本地照片管理（GalleryActivity）

相册是**纯自绘的二级 Activity**（Canvas 画网格，无 XML 布局、无 ListView/GridView）。

### 7.1 网格模式

- 4 列网格，新照片在最上
- 每张卡片：缩略图 + 左下角时间 + 右下角大小
- 点卡片 = 勾选/取消（蓝框 + 右上角蓝勾）
- 顶部工具栏：全选 / 反选 / 删除选中
- 删除有二次确认（显示"删除 N 张照片？共 X KB"）

### 7.2 缩略图性能

```java
BitmapFactory.Options o = new BitmapFactory.Options();
o.inSampleSize = 4;            // 1080p → 270p，缩略图够用
// 用 8MB LruCache 缓存，上百张不卡、不爆内存
```

### 7.3 大图预览（长按进入）

- 长按 500ms（Handler postDelayed，MOVE 超阈值即取消）打开全屏大图
- 左右滑动切换上一张/下一张
- 双指缩放 1x~4x，放大后可拖动
- 右下角「删除」单张删除（直接删 + 自动切下一张）、「返回」、点空白返回
- 原图**按需解码（RGB_565）**，看一张解一张、用完 recycle，不进缓存（防 OOM）

### 7.4 一个 API19 的坑

`Canvas.drawBitmap` 在 API19 没有 `(Bitmap, RectF, RectF, Paint)` 重载，画缩略图要 `Rect` 转 `Rect`：

```java
Rect src = new Rect(0, 0, thumb.getWidth(), thumb.getHeight());
Rect dst = new Rect((int)cr.left, (int)cr.top, (int)cr.right, (int)cr.bottom);
c.drawBitmap(thumb, src, dst, ip);   // 用 Rect 版，不是 RectF 版
```

## 10. 已知限制

1. 看家运行时原厂会议/录像不可用（摄像头只有一个）。退出看家自动恢复。
2. 冷启动到抢到相机约 2~10 秒。
3. `FaceDetector` 对侧脸、低头、大逆光不敏感，正脸最稳。
4. 邮件同步发送，网络差时该次失败，照片仍留本地。
5. 息屏相机帧率掉一半，靠跳帧间隔自适应补回（响应仍 1 秒量级）。

- **六版（2026-11-08 下午）· 预览流畅化**：
  - 帧率解锁：不再挑「上限最小的 ≥10fps 档」（那等于自己锁死 10fps），改为请求 `setPreviewFpsRange(30000,60000)`；
    节流门限 65ms → 40ms。实测预览 **6~10fps → 14~15fps**。
  - 双缓冲 → **三缓冲**（界面慢一帧时双缓冲会覆写正在显示的那块 → 一顿一顿/撕裂）。

    切后台不做转换时仍只有 15fps → **15fps 是硬件上限**，现在每帧都不丢。
  - 顺带：禁用 `com.ainemo.speech.app/.service.wakeup.XYWakeupService`（原厂讯飞助手唤醒服务），
    常驻内存 191MB → 0，MemFree 250MB → 452MB。详见
    `故障复盘-20261108-看家预览流畅化与191M语音助手.md`。

## 12. 实时预览（低清）实现要点 v2

```
Camera 回调 (1920×1080 NV21, 14~15fps  ← HAL 物理上限)
  └─ maybePreview()  ← 只有界面在前台（previewSink != null）才执行
       ├─ 40ms 节流（≤25fps，相机给多少放过多少）
       ├─ downscaleInto(NV21 → RGB565 int[240*135])   复用数组，零分配
       ├─ 三缓冲 Bitmap A/B/C 轮换 setPixels          固定 3×64KB
       └─ sink.onPreview(bm) → latest-wins → PreviewView.onDraw
                                                   （自绘，不 new Drawable、不 layout）
```

- 界面 `onResume` 注册 sink、`onPause` 置 null —— **息屏/切走时预览零 CPU**，检测与抓拍照常。
- 界面三层按状态互斥：`PreviewView`（实时）/ `shotView`（最近抓拍）/ `pvHint`（提示语）。
  预览断流 1.5 秒才退回显示最近抓拍。
- 状态行显示 `摄像头 1920×1080 · 实时 Nfps`；没有画面时提示语会写清卡在哪一步
  （「正在接管摄像头…原厂 App 正抱着相机」/「画面马上来…正在出第一帧」）。
- 抓拍路径完全没动：仍是 `YuvImage.compressToJpeg(1080p, q=78)`。

### 12.0 卡顿三连（v5 遗留，v6 修掉）

| 症状 | 真因 | 修法 |
|---|---|---|
| 只有 6~7fps | 自己把 fps 区间选成 10fps + 65ms 节流，跟 80ms 出帧一拍一撞，隔帧丢 | 请求 30-60fps + 门限 40ms |
| 一顿一顿/撕裂 | 双缓冲被生产者覆写 | 三缓冲轮换 |
| 越看越延迟 | `runOnUiThread` 每帧排队，UI 忙就堆积过期帧 | latest-wins 合并丢帧 |
| 每帧卡一下 | `setImageBitmap` 每次 new BitmapDrawable + requestLayout | 自绘 PreviewView |

### 12.1 为什么检测必须独立线程

`FaceDetector.findFaces` 一次约 200ms。原来它和相机回调同线程，这 200ms 里回调线程被占住、
缓冲不还给相机 → 预览每 1.2 秒卡 200ms。拆线程 + 3 块缓冲后，回调线程只做缩图与还缓冲。

## 13. 接管链路 v2（原厂抱着相机时）

```
点「开始看家」
  → GuardService.openLoop：先写 /sdcard/HomeGuard/.need_cam（预请求，和 open 并行）
  → cam_guard.sh（0.4s 轮询，root）
       ├─ 相机空闲 → 跳过，看家自己就能打开
       └─ 相机被别人占 → force-stop vulture.app.home（6 秒冷却）
  → 看家 400ms 重试 Camera.open(0)，1~2 秒内抢到（先到先得，占住就抢不走）
  → cam_guard 确认 cam_pid == guard_pid 后，才 am startservice PeripheralService
     （电话 widget + 电源键呼吸灯在里面，顺序反了会被它抢回相机）
  → 15 秒仍没交出去（用户中途退出）→ 兜底也把 PeripheralService 拉回来
```

实测：相机空闲 2 秒；原厂占着 2~4 秒。

**守护保活**：`boot_svc.sh` 开机启动 `cam_guard.sh`；`mic_keeper.sh` 每轮（15s）用
`sh cam_guard.sh check` 兜底拉起。存活判定一律用**心跳文件**（`cam_guard.beat` / `mic_keeper.beat`），
不能用裸 `kill -0` —— 重启后 pid 会被别的进程复用，会永久误判成「还活着」。
