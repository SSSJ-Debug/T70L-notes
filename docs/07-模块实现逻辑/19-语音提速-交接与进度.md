## 0. 一句话说清现在的位置

「小智开灯 / 小智关灯」**已经能正确识别、能正确执行**，延迟从 **738~2074ms 压到 514~573ms**，
达到"接近实体开关手感"的目标，普通问答链路也一并验证正常。

**真正的病根不是 CPU 被抢，是 Opus 编码在这台机器上根本追不上实时。**
A83T 跑 Dalvik（不是 ART）+ 纯 Java Concentus，实测 **71ms/帧**，
而一帧只有 60ms 音频 —— 天生赤字，队列必然积压，收尾必然白等。

**解法：上行不吃 Opus 了，直接发裸 PCM。** 服务端（api.tenclass.net）认这个格式，
编码开销归零，「收尾→发完」从 1507ms 降到 **59ms**。

```diff
- "audio_params":{"format":"opus","sample_rate":16000,"channels":1,"frame_duration":60}
+ "audio_params":{"format":"pcm", "sample_rate":16000,"channels":1,"frame_duration":60}
```
上行 16kHz/16bit = 32KB/s，WiFi 上毫无压力；识别率反而更稳（PCM 无损）。

## 2. 本轮（2026-11-07 18:47–19:00）到底改了什么

### 2.1 核心改动：音频编码/发送异步化

**改之前**（`stream()` 在录音主循环里同步做 Opus 编码 + WebSocket 写）：
```
开口 18:46:18.208 → 收尾 18:46:20.776 = 2568ms
但 chunks 只有 10 个（10×100ms = 1 秒音频）
→ 1.5 秒全被编码发送吃掉，录音节拍被拖到每片 256ms
→ 连"静音"都判得慢，用户感受"喊完愣一秒多"
```

**改之后**（`stream()` 只入队，独立线程 `xz-sender` 编码发送）：
```
开口 18:51:46.351 → 收尾 18:51:47.628 = 1277ms / 13 片
→ 每片约 98ms，录音节拍恢复正常 ✓
```

### 2.2 涉及代码（都在 `XzService.java`）

| 位置 | 内容 |
|---|---|
| 字段区 ~186 行 | `sendQ`（LinkedBlockingQueue，容量 60）、`senderAlive`、`senderThread`、`finishPending`、`finishDone` |
| `stream()` ~970 行 | 改为只 `sendQ.offer()`，队满丢最旧 |
| `startSender()` / `senderLoop()` / `encodeAndSend()` ~1000 行 | 新增发送线程，优先级 `MAX_PRIORITY-1` |
| `flushTail()` ~1040 行 | 补零发最后一帧（**只在发送线程调用**） |
| `endTurn()` 开头 | `finishPending=true` → 等 `finishDone` → 再 `listenStop()` |
| `onStartCommand` | `running=true` 后调 `startSender()` |
| `onDestroy` | 先停发送线程再 `closeClient()` |

### 2.3 踩的坑（**新 AI 千万别重复**）

**坑：OpusEncoder 不是线程安全的。**
第一版让 `endTurn()` 自己调 `c.codec().encode(pad)` 补尾巴，
和发送线程同时用同一个编码器 → 当场抛：
```
java.lang.AssertionError
  at org.concentus.Resampler.silk_resampler
  at org.concentus.OpusEncoder.encode
  at XzService.endTurn(XzService.java:1047)
```
整轮录音作废、主循环自愈重启。
**修复方式**：补尾巴也交给发送线程（`finishPending` / `finishDone` 握手），
保证 `OpusEncoder` 永远只有一根线程碰。

## 3. 当时的瓶颈分析（结论已被推翻，留作反面教材）

> ⚠️ **这一节的结论是错的，保留是为了别再走一遍。真正的根因见 3.1。**

1. `vulture.app.home`（会议音频服务）每秒刷 180 行"录音失败重试"日志，吃掉 A83T CPU；
2. 纯 Java Opus 编码被拖到 **76ms/帧**（正常 20ms），60ms 一帧 → 1 秒音频要 1.5 秒编；
3. 异步化后录音不卡了，但编码追不上，`sendQ` 积压；
4. `endTurn()` 必须等队列排空才能 `listenStop()`，于是白等 1.5 秒；
5. CPU 吃满时 **adbd 也会被饿死**，表现为设备 `offline`、ping 却正常（延迟从 9ms 涨到 65ms）。

### 3.1 更正：vulture 只是放大器，编码才是根因

19:10 把 vulture 全系压到 nice 19、把小智提到 -10 之后：

```
收尾→发完  1507ms → 1085ms      ← 有改善，但还差得远
```

19:13 再把 complexity 1→0、码率 24k→16k 之后，加了编码埋点，终于拿到硬数据：

```
编码 32 帧共 2293ms（平均 71ms/帧）      ← 32 帧 = 预录 8 片 + 语音 11 片
```

**关键判断**：降复杂度只把 76 压到 71，说明这不是参数问题。而 top 显示
`User 4% System 2% Idle 91%` —— **系统几乎是空的，压根没人在抢 CPU**。
71ms/帧就是这台 Dalvik 机器跑纯 Java Opus 的地板价。

而一帧只有 60ms 音频 → 编码速度 0.85x 实时 → 说什么都追不上。
另外**预录 8 片（0.8 秒）是在开口瞬间一次性灌进队列的**，
等于开局就先欠 13 帧 ≈ 900ms 的债，语音还在继续往里加，结尾必然要还。

所以三个结论：
1. vulture 那套"抢 CPU"（录音死循环重试 + 摄像头移动侦测常驻 29fps）确实存在，
   也确实让 76 > 71，但**它只是把已经输的局面变得更难看**；
2. 只要还在用 Opus，无论怎么调参数/压优先级，都绕不过 60ms/帧这条线；
3. 唯一出路是**把编码从关键路径上拿掉**。

## 4.1 顺带查清：vulture 到底在抢什么

`mic_owner.sh` 的套路是「force-stop vulture 抢到麦 → 只单独拉起 PeripheralService」。
但这个进程起来之后，里面的 CallSdk 三条流水线全醒着：

| 动作 | 现象 |
|---|---|
| `AudioRecord openInput()` | 麦已被小智占了，开不起来 → **死循环重试**，日志刷屏 |
| 摄像头移动侦测 | `OmxCamera:camdiff` + OMX 编码 **常驻 29fps** |
| 音频回调线程 | nice = **-16**，和我们的发送线程抢 CPU 永远是它赢 |

所以"CPU 被抢"不是 vulture 的 bug，是**我们抢它麦克风的副作用**。
不解决也不影响达标（PCM 已经不编码了），但要知道这口锅是谁的。

## 9. 遗留：服务端 session 寿命（2026-11-07 20:05 记录，未修）


**规律**：同一条 WebSocket 挂十几分钟后，服务端主动 close。重连是自动的
（下一轮 `beginTurn()` → `ensureClient()`），但**重连后的第一轮容易丢识别** ——
音频发出去的那一刻连接已经断了。

**影响**：


**为什么没马上修**：两条路都要动音频通路，风险大于收益：

## 11. 指令执行远场灵敏度加固（2026-11-07 20:45~21:02）

### 11.1 用户主诉

> "整体 80 分了，想往 100 分走。极个别时候，两三米外大声喊还是没法唤醒。
>  可能过一会儿不叫它了，再在远处喊就听不见、不执行了。偶发。"

关键词是**"过一会儿不叫它"**。这条线索指向的不是灵敏度，而是连接状态。

### 11.2 实测抓到两个独立原因

**原因一：远场话"差一点点没够到线"（不是听不见）**

20:44 现场日志（`开口 rms=... 底噪=... 阈值=...`）：

```
底噪 332~420 ｜ 阈值(底噪×3.0) 996~1260 ｜ 远场开口电平 1419 / 1702
```

远场话只比阈值高 12%。底噪从 332 漂到 420（+26%），阈值就顶到 1260，
1400 的电平开始压不住 —— **所以是偶发，而且环境越吵越明显。**

**原因二：连接空闲被服务端关掉，补连有 20 秒空窗（这才是"过一会儿"）**

20:56 实测：闲置 100 秒期间设备上打出

```
20:56:54 连接断开: 对端关闭
```

而补连只挂在主循环里、`now - lastWarmTry > 20000` 才有一次机会。
**断开后的头 20 秒里喊它，音频全发进一条已死的连接 —— 本地 `open` 还是 true，
所以日志里什么都没有，用户感受就是"像没听见"，下一句才好。**
这跟"过一会儿不叫它"完全吻合。

### 11.3 三处改动

#### ① 双门限开口（`XzService` 主循环）

原来只有一档 `rms > thr`，且计数是**累计**不是连续（不达标时不清零，
噪声每 100ms 攒 1 帧，300ms 攒够 3 帧就误开口——"连续 3 帧"从来没真正生效过）。

现在拆成两条通道，**各自独立计数、互不清零**：

| 通道 | 门限 | 要求 | 场景 | 响应 |
|---|---|---|---|---|
| 高档 | `底噪 × 2.4` | 连续 3 帧(300ms) | 近场/正常音量 | 最快 |
| 低档 | `底噪 × 1.5` | 连续 6 帧(600ms) | **两三米外小声** | 慢 300ms |

人喊一句"小智开灯"持续 1 秒以上，稳过 600ms；碰桌子/关门是 1~2 帧冲击，
房间噪声是上下抖的，都攒不出连续 600ms。

> ⚠️ **写第一版时踩的坑**：一开始写成"高档命中就把低档计数清 0"。
> 远场能量本来就在门槛上下浮动（实测 727/1068/624/910/536…），
> 一帧过高档、下一帧只过低档，两条计数轮流归零，**10 帧喊完一帧都没攒够——
> 比改之前还聋**。必须两条独立计数（因为 thrLo < thr，过高档时两条都该涨）。

#### ② 远场单独给增益

走低档通道开口 = 确实是远处小声，这时按原来的 2000/rms 算增益，
送到云端只有 2000 电平，和噪声差距太小 → ASR 认不出"小智"，虽然开了口也不执行。

| | 目标电平 | 上限 |
|---|---|---|
| 高档（原样） | 2000 | 4.0× |
| 远场低档（新增） | **3400** | **3.2×** |

800×3.2≈2560，接近正常说话电平，又不会像 4 倍那样把峰值推到削波
（削波丢共振峰，ASR 反而更差）。

#### ③ 断开即补（这是"过一会儿不灵"的正解）

```java
public void onClosed(String why) {
    L.w(TAG, "连接断开: " + why);
    if (now - lastReconnAt < 3000) return;   // 3 秒冷却防重连风暴
    lastReconnAt = now;
    new Thread(... ensureClient() ..., "xz-reconn").start();
}
```

配套两处：
- 主循环兜底补连 `20s → 4s`（防"假死但没有 close 事件"，即 NAT 静默回收）
- **`ensureClient()` 里删掉 `stopTrack()`** —— 和 `closeClient()` 同样的理由：
  这台机器的 HAL 一销毁 AudioTrack，输入通路跟着被拆，
  `AudioRecord.read()` 从此返回 ≤0，要十几秒才恢复。
  既然现在"断开即补"会频繁触发 ensureClient，留着这行等于每重连一次聋十几秒。

#### ④ 顺带：灵敏度档位整体下调

`sensParam`：中 3.0× → **2.4×**，高 2.2× → 2.0×，低 4.5× → 3.8×。

### 11.4 实测数据（21:00~21:02，Mac 外放模拟）

| 用例 | 结果 |
|---|---|
| 正常音量开灯 | 554ms ✓ |
| 正常音量关灯 | 544ms ✓ |
| **音量 0.016（旧门槛 1260 必漏）** | rms 901 → 开口 → 识别"小智开灯" → **260ms** ✓ |

### 11.5 开口日志新增两个字段（排障用）

```
开口 rms=8027 底噪=330 高门槛=792 低门槛=495 [高档] 声道=L 增益=1.0 连接=ok/静默0s
```

`连接=ok/静默Xs` 这个 `静默` 值来自 `XzClient.lastRxAt`（最后一次收到任何帧的时刻）。

### 11.6 仍然存在的干扰项（与本次改动无关）

服务端从 19:49 起对这台设备持续限流，20:59 那次实测：

```
20:59:27.295 已发完音频，等回答（从开口算 1159ms）
20:59:27.491 连接断开: 收到 close        ← 只差 196ms
```

即"音频刚发完、ASR 结果还没回来就被 close"，这一句必然丢。
这是额度问题（见第 10 节），**明天额度重置后会自然消失**。

判断方法：日志里如果是 `收到 close` 紧跟 `已发完音频`，就是额度；
如果是 `对端关闭` 且 `静默` 很大，就是空闲被回收（本次已修）。
