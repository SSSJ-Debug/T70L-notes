## 1. 这个软件的第一个问题：为什么不能直接用浏览器

直觉方案是"装个浏览器 / 套个 WebView 壳"。这条路在 T70L 上是**死的**，而且死得很硬：

| 事实 | 后果 |
|---|---|
| 系统 WebView = **Chromium 33**（2013 年） | 现代 JS 语法一律不认 |
| B 站 2025 前端用了 `?.`（可选链）和 `??`（空值合并） | 需要 Chrome 80+，**解析阶段就抛 SyntaxError** |
| 解析失败 → 整个 `<script>` 块不执行 | 页面白屏，不是"慢"，是**一行都不跑** |
| Via / X 浏览器等"轻量浏览器"内核**就是系统 WebView** | 换壳完全无用 |

浏览器内核是系统级的，**App 层无法替换**（除非自带 Chromium，那是几十 MB 的事，1G 内存也跑不动）。

所以唯一可行的路是：

> **完全绕开网页渲染，直接调 B 站官方 JSON 接口拿数据，
> 用系统 MediaPlayer 播直链，界面全部用原生 View 自绘。**

这也正好符合"纯粹看视频、不做任何互动"的定位——不登录、不投币、不发弹幕，只要一个能刷能播的客户端。**代价是 App 只有 29KB。**

## 3. 四个必须踩过才知道的坑

### 坑 1 · TLS 握手直接失败

Android 4.4 的 `HttpsURLConnection` **默认协商 TLSv1**，而 B 站只接受 TLSv1.2+。不处理的话，第一个 HTTPS 请求就挂在 handshake。

```java
SSLContext sc = SSLContext.getInstance("TLSv1.2");
sc.init(null, new TrustManager[]{ new X509TrustManager() {
    public void checkClientTrusted(X509Certificate[] c, String a) {}
    public void checkServerTrusted(X509Certificate[] c, String a) {}
    public X509Certificate[] getAcceptedIssuers() { return new X509Certificate[0]; }
}}, new SecureRandom());
HttpsURLConnection.setDefaultSSLSocketFactory(sc.getSocketFactory());
HttpsURLConnection.setDefaultHostnameVerifier((h, s) -> true);
```

两件事一起做：

1. **显式建 TLSv1.2 的 SSLContext** —— 这条是必须的，不建就握手不了
2. **trust-all** —— 4.4 内置 CA 库是 2013 年的，B 站换过证书链，老 CA 验不过

> 安全性说明：这是本机专用 App，只访问固定的 B 站接口和视频 CDN，不做任何敏感传输。trust-all 在这个前提下是可接受的取舍。

### 坑 2 · 不带 buvid3 会被风控拦（code = -352）

直接请求排行榜接口，返回：

```json
{"code": -352, "message": "请求被拦截"}
```

B 站要求带上**设备指纹 Cookie `buvid3`**。取法：

```
GET https://api.bilibili.com/x/frontend/finger/spi
→ {"data": {"b_3": "XXXX...", "b_4": "YYYY..."}}
```

然后把 `buvid3=<b_3>; buvid4=<b_4>` 带进后续所有请求。

`getJson()` 里还做了一层自动重试：遇到 `-352`（风控）或 `-400`（偶发）就**丢掉旧指纹重新取一次**再打。因为 buvid 会过期，重取一次大多数情况就好了。

### 坑 3 · UA 不能用手机 UA

一开始用 `Mozilla/5.0 (Linux; Android 4.4.4)` 这类老手机 UA，**反而更容易被风控**（B 站对低版本客户端有专门策略）。

改成桌面 Chrome 120 UA 后稳定：

```java
public static final String UA =
    "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 "
    + "(KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36";
```

同时必须带齐 `Referer: https://www.bilibili.com/` 和 `Origin`。

### 坑 4 · 视频直链有防盗链

`bilivideo.com` 的 CDN 校验 `Referer`，裸请求返回 403。

麻烦在于 **Android 4.4 的 `VideoView` 只公开了 `setVideoURI(Uri)`**，带 headers 的那个重载是 `private`。只能反射：

```java
java.lang.reflect.Method m = VideoView.class.getDeclaredMethod(
        "setVideoURI", Uri.class, Map.class);
m.setAccessible(true);
m.invoke(video, uri, headers);     // headers 里带 Referer + UA
```

反射失败时降级为 `setVideoURI(uri)`（无头），多数 CDN 节点仍能播。

## 4. 接口层：为什么能不用签名

B 站大部分接口现在要求 **wbi 签名**（`w_rid` + `wts`，基于 `img_key`/`sub_key` 做 MD5 混淆）。但这两个接口**不需要**：

| 接口 | 用途 | 是否需要登录 | 是否需要 wbi |
|---|---|---|---|
| `/x/web-interface/ranking/v2?rid=&type=all` | 分区排行榜，一次 100 条 | 否 | **否** |
| `/x/player/playurl` | 取播放地址 | 否 | **否**（配合特定参数） |
| `/x/frontend/finger/spi` | 取 buvid 设备指纹 | 否 | 否 |

**这是这个 App 能只有 29KB 的根本原因**——省掉了整套签名算法（wbi 混淆表、时间戳、URL 参数排序）。

### 4.1 排行榜

```
GET https://api.bilibili.com/x/web-interface/ranking/v2?rid={rid}&type=all
```

分区对照（全部实测 `code=0`，2026-11-05）：

| Tab | 全站 | 动画 | 音乐 | 游戏 | 影视 | 科技 | 鬼畜 | 舞蹈 |
|---|---|---|---|---|---|---|---|---|
| rid | 0 | 1 | 3 | 4 | 181 | 188 | 119 | 129 |

解析字段：`bvid`、`cid`、`title`、`pic`、`owner.name`、`stat.view`、`duration`、`desc`。

**封面 URL 要升级协议**：接口返回的是 `http://i0.hdslb.com/...`，在 4.4 上走明文有概率被运营商劫持/改写，统一改 `https://`。

### 4.2 播放地址（最关键的一个参数组合）

```
GET /x/player/playurl?bvid={bvid}&cid={cid}
    &qn=16&fnval=0&fnver=0&fourk=0&platform=html5&high_quality=1
```

这几个参数缺一不可：

| 参数 | 值 | 作用 |
|---|---|---|
| `platform=html5` | html5 | **强制返回 `durl` 数组**（完整 mp4），而不是 DASH 分段 |
| `qn=16` | 360P | 未登录能拿到的最高画质 |
| `fnval=0` | 关闭 DASH | 只要一个完整 mp4 文件 |
| `fourk=0` / `high_quality=1` | — | 避免触发 4K / 高码率分支 |

**为什么一定要 `durl` 而不是 DASH**：

```
DASH：视频流（m4s）+ 音频流（m4s）分开，需要自己解封装 + 音画同步
      → 系统 MediaPlayer 播不了，得引 ExoPlayer（API 21+，装不上）

durl：一个完整 mp4
      → 系统 MediaPlayer 直接播，硬解，零额外代码
```

这是整个方案成立的技术前提。**360P 在 1280×800 的 8 寸屏上完全够看**，而码率低意味着 1G 内存和这台设备的 WiFi 都轻松。

## 5. 界面实现要点

### 5.1 三列卡片网格（不用 GridView）

`ListView` + 手写 `BaseAdapter`，每行装 3 张卡：

```java
public int getCount() { return (videos.size() + 2) / 3; }   // 向上取整
```

`getView` 里用 `row.getTag()` 缓存 3 个卡片 View 引用，复用时只重新 `bindCard`，**不重建 View 树**。这是在 1G 机器上滚动不卡的关键。

尺寸全部按 **px 硬编码**（1280×800 定屏定做）：

| 常量 | 值 | 说明 |
|---|---|---|
| `CARD_W` | 400 px | 3 × 400 + 2 × 16 + 2 × 24 = 1280 正好铺满 |
| `COVER_H` | 250 px | 16:10，贴合 1280×800 的屏比 |
| `GAP` | 16 px | 卡片间距 |
| `PAD` | 24 px | 左右边距 |

> 不做 dp 适配是有意的：这台设备分辨率固定，多一层换算只会引入取整误差。

### 5.2 圆角封面为什么要软件层

```java
cover.setLayerType(View.LAYER_TYPE_SOFTWARE, null);  // clipPath 在 4.4 硬件层不稳定
```

`RoundImageView.onDraw` 用 `canvas.clipPath()` 裁圆角。在 4.4 的硬件加速层上，`clipPath` 对 `Bitmap` 的裁剪**会出现锯齿或整块不显示**。强制走软件层绘制后稳定。

代价是这张卡不享受硬件加速，但封面图本身已经降采样到 400px 宽，影响可忽略。

### 5.3 播放页的两个"这台设备专属"决定

**① 返回按钮必须常驻，不能自动隐藏**

```java
// 顶部（返回按钮 + 标题）常驻不隐藏
// 本机只有一个物理电源键且被映射成 HOME，返回入口必须随时可达
private void setControlsVisible(boolean show) {
    bottomBar.setVisibility(show ? View.VISIBLE : View.GONE);   // 只藏底部
}
```

T70L 的物理按键被改造成了桌面键，一旦把返回按钮也自动隐藏，用户点画面唤出失败就会**卡在播放页出不去**。所以只有底部控制条参与 3.5 秒自动隐藏。

**② 播放/暂停图标必须 Canvas 自绘**

```java
// 实测：Android 4.4 的 DroidSans 没有 U+275A（❚）字形
// 用文字画暂停键会显示成空白
```

4.4 的系统字体缺这个字形，用 `"❚❚"` 画出来是**两个空白方块**。只能 `drawRoundRect` 画两根竖条 + `drawPath` 画三角形。

**③ 点击事件必须挂在 VideoView 上**

```java
// VideoView 内部是 SurfaceView，事件不会冒泡到父容器
video.setOnTouchListener(...)
```

这和电视 App 里要加一层 `curtain` 是同一个根因：**SurfaceView 是独立绘图层，触摸不会传给父容器**。

### 5.4 进度条美化（4.4 的黄条太丑）

4.4 默认 SeekBar 是黄色 holo 风格。换成 B 站粉要用 `LayerDrawable + ClipDrawable`：

```java
GradientDrawable bg   = 圆角灰底；
GradientDrawable prog = 圆角粉色；
ClipDrawable clip = new ClipDrawable(prog, Gravity.LEFT, ClipDrawable.HORIZONTAL);
LayerDrawable ld = new LayerDrawable(new Drawable[]{bg, clip});
ld.setId(0, android.R.id.background);
ld.setId(1, android.R.id.progress);   // 这两个 id 是框架约定的，不能随便起
```

`setId` 那两行是必须的：`AbsSeekBar` 通过 `android.R.id.background` / `android.R.id.progress` 找图层，id 不对就不刷新。

## 6. 图片加载器（111 行，不引 Glide）

```java
LruCache<String, Bitmap>(8 * 1024 * 1024)   // 8MB 上限，按 getByteCount 算
Executors.newFixedThreadPool(3)             // MIN_PRIORITY + daemon
```

三个关键点：

**① 防错位（复用 View 时图片串台）**

```java
iv.setTag(url);
...
if (url.equals(iv.getTag())) iv.setImageBitmap(bmp);   // 回来时再校验一次
```

列表快速滚动时，ImageView 已经被复用于另一个视频，异步图回来必须核对 tag，否则会出现"A 的封面贴在 B 的卡片上"。

**② 降采样，防 OOM**

```java
o.inJustDecodeBounds = true;                    // 只读尺寸，不分配像素
BitmapFactory.decodeByteArray(raw, 0, len, o);
if (o.outWidth > targetW * 2) sample = 2;
if (o.outWidth > targetW * 4) sample = 4;
o2.inSampleSize = sample;
o2.inPreferredConfig = Bitmap.Config.RGB_565;   // 每像素 2 字节，不是 4
```

封面原图常见 1280×720，一张 ARGB_8888 就是 3.6MB。8 张就能把 1G 机器打爆。降采样 + `RGB_565` 后单张约 **180KB**。

**③ 线程优先级最低**

```java
t.setPriority(Thread.MIN_PRIORITY);
```

封面加载永远不该跟视频解码抢 CPU。这是"看着不卡"的隐形功臣。

## 7. 扫码登录备用方案（已写好，未启用）

`源码/02-B站客户端/_备用-扫码登录/` 里留了完整实现：

| 文件 | 内容 |
|---|---|
| `Auth.java` | 二维码生成 → 轮询扫码状态 → 拿 SESSDATA |
| `QrCode.java` | **自写 QR 编码器，零依赖**（RS 纠错 + 掩码 + 容量表） |
| `LoginActivity.java` | 扫码界面 |
| `BiliApi.带登录版.java.txt` | 带 Cookie 的接口层 |
| `README.md` | 启用步骤 |

`QrCode.java` 是逐字节验证过的：用 OpenCV 的 5 个样本 + 6 个容量边界做对照，编码输出与参考实现一致。

**为什么没启用**：扫码登录后能拿 1080P，但会引入 SESSDATA 过期、账号风控、多设备登录踢线等一堆问题。而 360P 在 8 寸屏上已经够看。**保持"纯观看、零账号"是最省心也最稳的形态。**

真要启用，按 `_备用-扫码登录/README.md` 走：把 4 个文件放回 `src/com/lm/bili/`，`BiliApi.java` 换成带登录版，重新编译即可。

## 9. 已知限制

1. **最高 360P**（未登录）。想要更高需启用扫码登录
2. **不支持弹幕/评论/投币**（有意为之，定位就是"纯看"）
3. **不支持搜索**——只有 8 个分区排行榜，这是接口层面最省事的取舍
4. **视频地址有时效**（约 2 小时），长时间挂着不切视频会 403，切下一个即恢复
5. **列表只有 100 条**（接口上限），没有翻页

## 10. 这套方案的可复用性

核心是两条判断，任何"老旧 Android 上跑现代 Web 服务客户端"的场景都适用：

1. **先确认 WebView 内核版本**。Chromium < 80 基本等于"现代前端全废"，套壳浏览器救不了。
2. **找一个不需要签名的只读接口**。排行榜/推荐这类"公开内容"接口通常无签名、无登录，配合 `platform=html5` 往往能拿到完整 mp4 直链——**这是避开 DASH 解封装需求的唯一捷径**。

只要这两条成立，客户端就能做到几十 KB 级别。
