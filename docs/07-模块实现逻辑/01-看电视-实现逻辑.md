# 01 · 看电视 —— 实现逻辑全解

> 产物：`tv.apk`（33 KB，无第三方依赖）
> 源码：`源码/01-电视直播/src/com/lm/tv/`（MainActivity.java + HlsProxy.java）
> 运行环境：中移 T70L，Android 4.4.4 / API19 / armv7 / 1G RAM / 1280×800
> **v4（2026-11-06）**：根治"播一两分钟整屏冻死"，并去掉左侧常驻小把手。详见第 12 节。

---

## 1. 这个软件到底解决了一个什么"不可能"

一般思路做直播 App：上 ExoPlayer 或 ijkplayer。但在 T70L 上有三个硬约束：

| 约束 | 后果 |
|---|---|
| Android 4.4，ExoPlayer 2+ 最低要 API 21 | 高版本播放器**装不上** |
| 1G RAM，App 常驻不能被系统随时杀掉 | 重型播放器**吃不起** |
| 运营商 IPTV 服务器**单连接限速 0.64 MB/s** | 而 1080i 流要 **1.085 MB/s** 才跟得上 |

第三条是真正的死结：**换算一下，单连接永远追不上，不管你用多好的播放器**。

所以这个 App 的架构核心不是"选个好播放器"，而是：

> **自己写一个本地 HTTP 代理，用 6 条连接并行把分片抢下来落到磁盘，
> 播放器只跟 127.0.0.1 要数据，从此带宽不再是瓶颈。**

播放器退化成最原始的 `MediaPlayer` + 原生 HLS（API19 自带），APK 因此只有 33 KB。

```
│  HlsProxy（进程内单例，ServerSocket 18765）                    │
│                                                               │
│  prefetchLoop ── 每 1.5s 回源 m3u8，裁成 3 片窗口              │
│       │                                                       │
│       ├─→ buildPlaylist()  改写 /s/<md5> 并缓存                │
│       └─→ ensureSeg()      为每片建 Seg 对象                   │
│                                                               │
│  dlLoop × 6 ── 从 candidates() 抢 512KB 块，Range 并发下        │
│       │                                                       │
│       └─→ fetchChunk() → markChunk() → prefix 连续推进         │
│                                                               │
│  httpPool × 10 ── serveSegment() 边下边发，喂给 MediaPlayer    │
└───────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
              上游 http://112.123.243.37:50085/tsfile/live/…
```

**三条线程池职责严格分离**，这是 v2 才修对的关键：

| 池 | 数量 | 职责 | 为什么必须独立 |
|---|---|---|---|
| `httpPool` | 10 | 应答 MediaPlayer 的 HTTP 请求 | 播放器一连上就长期占住线程；若与下载共用，下载永远排不上队 |
| `dlLoop` | 6 | 下载分片块 | 需要长期占用，不能被播放器请求打断 |
| `prefetchThread` | 1 | 刷新 playlist、建 Seg、清缓存 | 轻量，绝不能阻塞 |

> **v1 的致命错误就是三件事共用一个 4 线程池**：播放器一连接就把线程占满，下载任务永远排不上，`serveSegment` 干等 40 秒超时——这才是"换台要一分钟"的真因，跟网速半点关系没有。

## 3. 上游流媒体的真实结构（实测，非文档）

抓一次 m3u8 就能看到全部真相：

```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:11
#EXT-X-MEDIA-SEQUENCE:7265808
#EXTINF:10, no desc
live_1_1_7265804.ts?key=txiptv&key2=12138489&cl=11375504&…
#EXTINF:10, no desc
live_1_1_7265805.ts?…&cl=11374188&…
…（共 5 条）
```

| 参数 | 值 | 含义 |
|---|---|---|
| 窗口分片数 | **5** | 滑动窗口，滚过去就没了（不能回看） |
| 每片时长 | **10 秒** | `EXT-X-PROGRAM-DATE-TIME` 每条差 10 秒 |
| 每片大小 | **11.37 MB**（`cl=11375504`） | ≈ 9 Mbps，1080i |
| 播放消耗速率 | **1.085 MB/s** | 11.37MB ÷ 10s |
| 单连接实测 | **0.64 MB/s** | 3MB 用了 4.7 秒 |
| 6 连接并行实测 | **2.0~2.5 MB/s** | 满足 2 倍余量 |

**两个救命细节：**

1. **`cl=` 参数直接带总字节数**。所以 `sizeFromUrl()` 用字符串截取就能拿到分片大小，**不需要发 HEAD 或 Range:0-0 探测**，省掉一次往返延迟。
2. **播放器起播点不是第 1 片**。Android 4.4 的 HLS 实现从窗口末尾往回数（倒数第 2~3 片）。这一条是 v2 那个"换台后卡十几秒"的根因，见第 7 节。

## 4. 启动与切台全流程

```
onCreate()
  ├─ FLAG_KEEP_SCREEN_ON        播放时不熄屏
  ├─ setVolumeControlStream(MUSIC)  音量键直接控媒体音量
  ├─ HlsProxy.get(cacheDir).start()  起本地服务（端口被占则自动退化为直连上游）
  ├─ loadChannels()             两级加载：/sdcard/tv/channels.txt → assets
  ├─ setContentView(buildUi())
  └─ postDelayed(play(0), 600ms)  等 Surface 就绪再开播
```

```
play(idx)
  ├─ currentIdx = idx; retried = 0; urlIdx = 0
  ├─ adapter.notifyDataSetChanged()   高亮当前行
  └─ startPlay(idx, 0)
        ├─ proxy.setChannel(src)        ← 换代次，旧下载任务立即放手
        ├─ playUrl = HlsProxy.localUrl(src)   ← 包成本地地址
        ├─ setStatus("正在缓冲 …")
        ├─ releasePlayer()              ← stop/reset/release 三连，防泄漏
        ├─ new MediaPlayer()
        ├─ setDataSource(ctx, uri, headers)   ← 带 UA 伪装
        └─ prepareAsync()
```

**为什么切台必须先 `releasePlayer()` 再 `new`**：
Android 4.4 的 MediaPlayer 复用（`reset()` 后重新 `setDataSource`）在 HLS 场景下会残留旧 playlist 的 sequence 状态，表现为切台后播的还是上一台的末尾几秒。**每次重建是最稳的**，代价只有几十毫秒。

**为什么 `setDataSource` 要传 headers**：
上游会校验 UA，裸的 `MediaPlayer` 默认 UA 会被 403。虽然请求其实打到本地 127.0.0.1，但保留这个设置可以保证"代理不可用时自动退回直连上游"也能工作。

**降级链条**（`onPlayFail`，三级）：

```
播放失败
  ├─ 1) 该频道还有下一个源？  → 换线路重播（900ms 后）
  ├─ 2) 同源重试次数 < 1？   → 重试一次（1500ms 后）
  ├─ 3) 还有下一个频道？      → 自动跳台（1200ms 后）
  └─ 4) 都不行               → 提示"换一个台试试"，不再死循环
```

每一级都带 `if (idx == currentIdx)` 守卫——防止用户在等待期间已经手动切走，延迟任务又来抢画面。

## 5. 频道表：为什么放文本文件

格式极简，一行一台：

```
分组|名称|地址1;地址2;地址3
中央|CCTV-1 综合|http://112.123.243.37:50085/tsfile/live/0001_1.m3u8?key=txiptv&playlive=0&authid=0
```

- 第三列用 `;` 分隔多个源，**按顺序尝试**（`Channel` 构造时拆数组）。这是"某个节点 403 就换下一个"的物理基础。
- **两级加载**：优先 `/sdcard/tv/channels.txt`，读不到才回落到 `assets/channels.txt`。
  → **换源可以直接 `adb push` 一个 txt 进去重启 App，完全不用重新编译、不用重装**。这是这个 App 能在源频繁失效的环境里活下来的关键设计。
- 42 台，分三组：中央（CCTV-1~15 全高清）、卫视、地方。

## 6. 界面：那些看起来"多余"的 View 为什么必须有

| 组件 | 作用 | 少它会怎样 |
|---|---|---|
| `SurfaceView` | 视频输出，**铺满整屏** | v1 给了 `leftMargin=300dp`，抽屉一收就留一条黑边 |
| `curtain` | 透明 View，接点击 | **SurfaceView 不响应触摸**，没有这层就点不动画面 |
| `panel` | 频道抽屉，`translationX` 滑出 | 用 `Visibility` 会重新布局导致画面闪；位移是纯合成，零重排 |
| `handle` | 左边中间三条横线 | 抽屉收起后没有任何入口能把它叫回来 |
| `info` | 台名，3 秒淡出 | 切台后不知道自己在看哪个台 |

**抽屉显隐的细节**（`setPanel`）：

```java
float target = open ? 0f : -panelW;
panel.animate().translationX(target).setDuration(200).start();
handle.animate().alpha(open ? 0f : 1f).setDuration(200).start();
if (open && currentIdx >= 0) list.setSelection(currentIdx);   // 展开时滚到当前台
```

- 用 `alpha` 而不是 `Visibility` 控制把手：Visibility 切换会触发 `requestLayout`，在 4.4 上能看到一帧闪烁。
- 展开瞬间 `setSelection`，让用户不用自己滚着找"现在看的是哪个"。
- `list.setCacheColorHint(0)` 是 4.4 的坑：不清零的话滚动时出现黑底块。

**信息条避让**（`showInfo`）：

```java
info.setX(panelOpen ? panelW + dp(16) : dp(14));
```

抽屉开着的时候台名往右让 300dp，否则被面板压住看不见。

**遥控器映射**（`onKeyDown`）：

| 键 | 行为 |
|---|---|
| BACK | 抽屉开着 → 先收抽屉（不退出 App）；关着 → 正常退出 |
| ← / → | 直接上一个台 / 下一个台（不用开抽屉） |
| ↑ / ↓ | 抽屉关着 → 打开抽屉并让焦点落进去 |

BACK 优先收抽屉这条很重要：老人用遥控器时按 BACK 是想"关掉那个列表"，不是想退出 App。

## 7. HlsProxy 三代演进（核心中的核心）

### 7.1 v1：能播，但换台要一分钟

| # | 问题 | 后果 |
|---|---|---|
| 1 | HTTP 服务与分片下载**共用 4 线程池** | 播放器一连上占满，下载永远排不上，干等 40 秒超时 |
| 2 | 5 个分片平分带宽 | 首片只分到零头 |
| 3 | 必须整片 11MB 全落盘才返回 | 白等 3~4 秒 |

### 7.2 v2：换台压到 1.5~3 秒

| # | v1 的问题 | v2 的修法 |
|---|---|---|
| 1 | 线程池互锁 | HTTP 独立 10 线程池 |
| 2 | 平分带宽 | 一次只攻首片，其余排队 |
| 3 | 整片落地才发 | `RandomAccessFile` 预分配 + 边下边发 |
| 4 | 播放器早到拿 404 → `-1004` 重试 | 请求时现场建 Seg 开下 |
| 5 | playlist 每次回源 | 内存缓存 3 秒 |
| 6 | 旧任务抢带宽 | `gen` 代次计数，切台即放手 |

实测：CCTV-11/12/13 连切 **2.79s / 2.54s / 1.43s**。

### 7.3 v3：修掉"切完卡十几秒"（本次）

**现象**：换台快了，但切过去那一瞬起，新台卡 10~20 秒才顺。

**根因一 · 预取和播放器完全错位**

```
上游窗口：  [片A] [片B] [片C] [片D] [片E]     ← 5 片
v2 预取：    ▲ 只下这个（最旧的第 1 片）
播放器起播：              ▲ 从这里开始（倒数第 2~3 片）
```

我们辛辛苦苦下的片，播放器压根不看；它要的片我们一片没下 → 只能现场追。

**根因二 · `prefix` 在段边界假死（这才是那十几秒的直接来源）**

v2 把每片切成 2 段并行下载：

```
片 11.4MB ────────────────┬────────────────
        段0（5.7MB）      段1（5.7MB）
        prefix 只由段0推进 ↑
```

段 0 下完，`prefix` 就停在 5.7MB 不动了。播放器按 1.085MB/s 读，**5.3 秒后读到 5.7MB 就必须干等**，一直等到段 1 也下完（约 9 秒）`join()` 回来才把 `prefix = size` 放开。

用户的体感就是：读一段 → 卡住 → 读一段 → 再卡住，反复几轮，等窗口滚过一遍两边对齐了才顺。**跟"前十几秒卡"的时长严丝合缝。**

**根因三 · 吞吐不够**

单连接 0.64MB/s < 消耗 1.085MB/s，buffer 永远填不满，任何抖动都直接变成卡顿。

### 7.4 v3 的七处改动

#### ① 窗口裁剪：让播放器的起播点必然落在我们预取的第一片

```java
static final int WINDOW = 3;      // 只给播放器最后 3 片（30 秒）

int from = Math.max(0, total - WINDOW);
long startSeq = (seq >= 0 ? seq + from : from);   // MEDIA-SEQUENCE 同步偏移
```

上游给 5 片，我们**只把最后 3 片交给播放器**。播放器从窗口末尾往回数起播点，落在窗口内 → **预取顺序 == 播放顺序**，错位问题从根上消失。

> `EXT-X-MEDIA-SEQUENCE` 必须跟着裁剪偏移，否则播放器算出的序列号跟实际分片对不上，会在边界反复重开连接。

#### ② 块流水线：`prefix` 变成连续推进，永不假死

```java
static final int CHUNK = 512 * 1024;      // 512KB 一块
static final int DL_THREADS = 6;          // 6 条常驻下载线程
```

```
11.4MB 分片切成 23 块：
 [0][1][2][3][4][5][6]…[22]
  6 条连接同时抢块 0~5 —— 谁下完谁再来抢下一块

prefix 推进规则（markChunk）：
  块 0 完成 → prefix = 512KB
  块 1 完成 → prefix = 1MB
  块 2 完成 → prefix = 1.5MB   ← 只要前面的块齐了，立刻往前推
  …
  全部完成  → prefix = size, done = true
```

**关键差异**：v2 是"段 0 独占推进"，v3 是"任何块完成都可能推进前缀"。因为块从 0 开始顺序分配（`nextChunk` 单调递增），块 0、1、2… 依次完成，前缀就**一路连续往前跑，永远不会停在中间等**。

`markChunk` 的实现很朴素但正确：

```java
s.chunkDone[idx] = 1;
while (s.prefixChunk < s.chunkCount && s.chunkDone[s.prefixChunk] == 1) {
    s.prefixChunk++;
    s.prefix = Math.min(s.size, (long) s.prefixChunk * CHUNK);
}
if (s.prefixChunk >= s.chunkCount) { s.prefix = s.size; s.done = true; }
```

#### ③ 6 连接并行：2.0~2.5MB/s，是消耗的 2 倍

buffer 只会越攒越多，任何一次网络抖动都被这点余量吃掉。

#### ④ `playing` 插队：谁被播放器读，6 条连接立刻全转过去

```java
// serveSegment 第一行
playing = s;
```

`candidates()` 把它排在队首：

```java
Seg p = playing;
if (p != null && !p.done && !p.failed) out.add(p);    // 第一位
// 然后才是窗口内按顺序
```

就算起播点判断错了（比如某机型从第 1 片起播），最多浪费 0.2 秒就自动纠正。**这是整个设计的保险丝。**

#### ⑤ 头部预铺：任何片被要时都不是 0KB

```java
static final int HEAD_CHUNKS = 3;      // 每片先铺 3 块 = 1.5MB
```

`dlLoop` 分两轮：

```
第一轮：遍历窗口内所有片，谁的头部（前 3 块）没铺完就给谁
第二轮：头部都齐了，再按播放顺序把当前片补满
```

实测效果：连切 5 个台，**4 次切过去时首片已有 1.5MB 就绪**，最差的 0KB 也能在 0.8 秒内补齐。

#### ⑥ 拉模式下载：不在线程池里嵌套阻塞

v2 用 `segPool.execute(() -> download(seg))`，而 `download` 内部又 `join` 两个子线程——池子里嵌套阻塞，线程会被吃干。

v3 改成 6 条常驻线程自己去抢活：

```java
private void dlLoop() {
    while (running) {
        Seg s = null; int idx = -1;
        List<Seg> cands = candidates();
        // 第一轮：铺头部；第二轮：按顺序补满
        if (s == null) { Thread.sleep(60); continue; }
        fetchChunk(s, idx);
    }
}
```

没有嵌套、没有任务队列、没有 join，线程永远在干活。

#### ⑦ 缓存保护：别删正在播的片

窗口在滚动（10 秒滚一次），如果 `trimCache` 只认"当前窗口内的片"，就会把播放器还在读的旧片删掉 → 读到一半文件没了。

```java
if (keep.contains(key)) continue;              // 窗口内的留下
if (s == playing) continue;                    // 正在读的留下
if (now - s.lastServe < 30000) continue;       // 30 秒内读过的留下
```

---

### 7.5 分片失败兜底

`fetchChunk` 每块重试 3 次，仍失败则**跳过该块并标记完成**：

```java
// 3 次都失败：跳过这块（最多花屏一瞬），保证 prefix 不被永久卡死
markChunk(s, idx);
```

宁可花屏 0.3 秒，也不能让 `prefix` 停在那里导致整个播放永久挂死。**这是"可用性优先于完美性"的取舍。**

## 10. 已知限制

1. **不支持回看/时移** —— 系统 MediaPlayer 的 HLS 只有直播能力，且上游只有 5 片窗口
2. **不支持 EPG 节目单** —— 上游 SDT/EIT 是空的（只能靠抽帧看台标认台）
3. **播放延迟 10~20 秒** —— 窗口裁 30 秒 + 播放器起播点靠前所致，直播场景无感
4. **换台 1~3 秒** —— HLS 起播固有开销（拉 playlist + 首个 TS 包到达 + 解码器初始化）
5. **频道源会失效** —— 跨网源编号不可信，必须逐台验证；主服务器 42 台目前稳定

## 11. 这套方法的可复用性（重要）

这套"HLS 本地代理 + 块流水线"**不依赖任何特定频道或服务器**，是通用的。判断一个新源能不能用这套方案，只需要量三个数：

```bash
# 1. 分片大小和时长（看 cl= 和 EXTINF）
# 2. 单连接速度    → 必须 < 码率，否则不需要代理
# 3. 多连接总速度   → 必须 > 码率 × 2，否则 buffer 攒不起来
```

只要满足 2、3，把 `channels.txt` 换掉就能直接用。**这是这个 App 最有价值的资产，不是那 42 个台。**

## 12. v4 · 根治"播一两分钟整屏冻死"（2026-11-06）

### 12.1 现象与取证

用户原话："任何一个频道进去放个一两分钟就彻底卡住不动了。"
实测最短 **30 秒**就冻，且**永不恢复**。

| 取证手段 | 结果 | 说明 |
|---|---|---|
| 隔 4~5 秒截两张图 | md5 完全一致 | 画面确实定住，不是心理作用 |
| `kill -3` + `/data/anr/traces.txt` | 代理 10 个 HTTP 线程**全空闲** | 不是代理卡死 |
| `/proc/net/tcp` | 播放器→18765 那条连接 ESTABLISHED，收发队列全 0 | 播放器那边在空转 |
| `adb forward` 后直接 curl 本地 playlist | 内容一直在刷新、序号一直在涨 | 代理是健康的 |
| 日志 | 冻住后**再没有任何 `REQ`** | 播放器自己不吃了 |

**结论：代理是好的，是播放器自己不吃了。**

### 12.2 四个根因（全部实测确认）

| # | 根因 | 机制 |
|---|---|---|
| 1 | **m3u8 被播放器缓存** | 响应没有 `Cache-Control`、playlist 还写 `ALLOW-CACHE:YES` → Chromium 启发式缓存把 m3u8 钉住 → 每次刷新都是老窗口 → 播放器认为"没有新内容" → 静默停摆 |
| 2 | **失败返回 200 + 文字** | `no file` / `size unknown` 被当 TS 数据吃掉，不报错也不推进 → 卡死而非重连 |
| 3 | **MEDIA-SEQUENCE 算错** | 上游那个数字是"最新一片编号"，v3 又加了裁剪偏移，对不上且可能回退 |
| 4 | **一块 512KB 卡住 → 整片永远凑不齐** | 块号是一次性单调发出的：某条连接读到一半假死（上游"滴流"回字节，read 永不超时），这块就再没人重下；`prefix` 永久停在块边界。实测停在 **1536KB**（第 3 块），播放器读到 1.5MB 就干等，反复重试 2 分钟 |

第 4 条是最阴的，日志铁证：

```
REQ 片 7269458 第1次 prefix=1536KB
REQ 片 7269458 断流于 1536/11108KB
REQ 片 7269458 第2次 prefix=1536KB
REQ 片 7269458 断流于 1536/11108KB
```

### 12.3 v4 的六处改动

1. **禁缓存**：所有响应 `Cache-Control: no-store,no-cache,must-revalidate` + `Pragma` + `Expires:0`；
   playlist 写 `ALLOW-CACHE:NO`；播放地址带递增 `s=<session>`，缓存键每次都不同。
2. **失败即失败**：404/503，播放器立刻报错走重连。
3. **序号取真值**：`seqFromUri()` 从 `live_1_1_<编号>.ts` 抠真实编号，严格单调。
4. **窗口 5 片 + 只前进不后退**：回源失败沿用上一份；离开窗口的片再留 60 秒；`pinned` 钉住最近 12 个 key 不被删。
5. **块调度改成"认领 + 可抢回"**：
   ```java
   claim(): 从 prefixChunk 往后找空闲块 → 没有就抢"认领超 25 秒"的块
   fetchChunk(): 单块 22 秒硬超时，超了就 release，别的线程立刻重下
   releaseChunk(): giveUp(试满 6 次) 才挖洞标记完成，保证 prefix 不被永久卡死
   ```
6. **画面看门狗**（MainActivity）：
   - 判据：播放器 **35 秒**一次数据都不来（正常实测 9~10 秒一次），或 **120 秒**没吃到全新分片；
   - 若判定为**上游断网**（回源 8 秒没成功）→ 只提示"信号中断，正在重连…"，**不重建播放器**；
   - 否则静默重建（重新 prepare），1~2 秒自己回来；
   - **注意**：不能用 `getCurrentPosition()` 当判据 —— 实测画面冻死时位置照样每秒 +1000ms 上涨。

### 12.4 界面改动

左侧那枚"小长方体 + 三条横线"的常驻把手（`HandleView`）**整块删除**。
列表收起后屏幕上不留任何图标；叫回列表只有两个入口：**点画面**、**遥控器 ↑/↓**。
