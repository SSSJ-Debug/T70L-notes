# 「文件夹」一点就黑屏卡死 —— 源码级根因与修复

> 2026-11-04 定案。这一份是**结论**，不是推测。
> 排查手段：现象复现 → `kill -3` 抓主线程栈 → `debuggerd -b` 抓 native 栈 → 解析 `vulture.app.home` 对帧。

---

## 一、现象

点桌面第二屏的「文件夹」图标：

1. 立刻黑屏，什么也不显示
2. 等很久（>10s）弹「X Link Home 无响应，要将其关闭吗？」
3. 只能点「退出」
4. 全程「设置」正常，时钟/天气正常

注意：**开机后第一次点才会这样，而且是随机的** —— 有时能开，有时必死。这就是为什么之前一直没抓准。

---

## 二、根因：WebView 初始化在蓝牙 binder 上死等

抓到的主线程栈（`/data/anr/traces.txt`，pid 14948，2026-11-04 14:57:16）：

```
"main" prio=5 tid=1 NATIVE
  at android.os.BinderProxy.transact(Native Method)
  at android.bluetooth.IBluetooth$Stub$Proxy.getState(IBluetooth.java:591)
  at android.bluetooth.BluetoothAdapter.getState(BluetoothAdapter.java:637)
  at android.bluetooth.BluetoothAdapter.getProfileConnectionState(BluetoothAdapter.java:1094)
  at com.android.org.chromium.media.AudioManagerAndroid.initBluetooth(AudioManagerAndroid.java:524)
  at com.android.org.chromium.media.AudioManagerAndroid.init(AudioManagerAndroid.java:191)
  at com.android.org.chromium.content.app.ContentMain.nativeStart(Native Method)
  at com.android.org.chromium.content.app.ContentMain.start(ContentMain.java:34)
  at com.android.org.chromium.content.browser.BrowserStartupController.contentStart(BrowserStartupController.java:208)
```

对照 native 栈，卡的位置是 `__ioctl → IPCThreadState::waitForResponse → BpBinder::transact`
—— 一个**同步 binder 调用，永远等不到回包**。

### 为什么「设置」不卡

设置页用的是原生 View，不走 WebView，因此不触发 Chromium 初始化，
也就不会碰 `AudioManagerAndroid.initBluetooth()`。**受影响面 = 任何新开 WebView 的界面**，
目前就是「文件夹」（`MyFullScreenWebActivity`，加载 `cloud.xylink.com/vods/sharecenter`）。

### 为什么是"随机"的

Chromium 的 `BrowserStartupController` **在每个进程里只初始化一次**。
所以只要本进程已经建过一次 WebView（蓝牙还没被冻结时），后续再开文件夹就永远不碰蓝牙，一切正常。
反过来，进程一旦重启（ANR 被杀 / OOM / pm install 触发），初始化状态清零 → 再点必死。

**这就解释了反复出问题的节奏**：不是每次都坏，而是"进程换过之后的那一次"坏。

## 三、修复

### 3.1 主方案：错峰预热 WebView

在蓝牙被冻结**之前**，先让 `vulture.app.home` 建一次 WebView，把 Chromium 初始化完。

这就是 `boot_init.sh` 里 `warm_webview()` 干的事（2026-11-04 06:25 就已加入，日志可见）。

### 3.2 补丁：进程重启后自动重新预热

预热状态是进程级的，进程一换就作废 —— 这是原方案的漏洞。
新增 `webview_guard.sh`：盯着 `vulture.app.home` 的 pid，换号就自动跑一遍
`rewarm_webview.sh`（停网关 → 预热 → 恢复网关），带 5 分钟冷却与 pid 稳定性二次确认。

### 3.3 rewarm 内的二次保险

实测：经过一次「CONT → 预热 → kill -9 bluedroid」后，芯片偶发未恢复，
`t70gw2.sh start` 会报 `HCI_BUS_UP adv_off=-1`。此时再跑一遍即好（内部有 rfkill 自检）。
`rewarm_webview.sh` 已自动检测并重试一次。

## 四、附带的第二个发现：指令执行图标为什么会"透明"

`com.xylink.launcher` 每次**进程重启**（含一次 `pm install` 触发的重建）都会把
`data/data/com.xylink.launcher/databases/_setting.db` 的 `item_info` **整表重建**
（`_id` 递增、旧记录物理删除）。


### 已做的两件事


> 注意：`sqlite3` 的 UPDATE 语句带 8380 字符 hex，**不能直接走 `adb shell` 命令行**（会报
> `shell command too long`），必须 push 成 `.sql` 文件再 `sqlite3 db < file`。
