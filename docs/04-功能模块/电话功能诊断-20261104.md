# T70L 电话功能诊断报告

- 日期：2026-11-04 19:35
- 设备：T70L（octopus_f1），Android **4.4.4**（SDK 19），构建 octopus_f1-userdebug 4.4.4 KTU84Q 20190423
- 卡：中国电信 46011（READY，LTE，非漫游）
- 4G 模块：Fibocom Mobile Boardband（广和通）
- 现象：拨 10000 打不出去

---

## 一、结论先说

**这张卡在这台设备上打不了普通电话，不是卡的问题、不是信号问题、也不是没配好——是设备本身不支持语音通话。**

数据业务完全正常（LTE 上网、短信都在），缺的只有"语音"这一条通道。

---

## 二、三层锁（每层都有实证）

### 第 1 层：系统框架直接禁止语音

从设备拉回 `/system/framework/framework-res.apk`，解析后查资源：

```xml
<!-- res/values/bools.xml:57 -->
<bool name="config_voice_capable">false</bool>
```

这个值是编译期烧进系统框架的。Android 4.4 的 `OutgoingCallBroadcaster` 里：

```java
Phone phone = PhoneFactory.getDefaultPhone();
if (!phone.isVoiceCapable()) {   // ← 读的就是上面这个 false
    // 弹窗 "不支持语音呼叫"，然后直接 return，不往下走
}
```

实测证据：

```
am start -a android.intent.action.CALL -d tel:10000
→ 前台变成 com.android.phone/.OutgoingCallBroadcaster
→ 屏幕弹出「⚠ 不支持语音呼叫 / 确定」
→ mCallState 始终 = 0
→ radio 日志里 **没有任何 RIL_REQUEST_DIAL**
```

也就是说：**拨号请求在进到调制解调器之前就被系统扔掉了。**

### 第 2 层：语音域根本没注册上

radio 日志里两条 AT 回执形成了鲜明对比：

```
AT> AT+CEREG?          ← 数据域（PS）
AT< +CEREG: 2,1,"0BAF","00CE3B32",7
         ↑ stat=1 = 已注册（所以能上网）

AT> AT+CREG?           ← 语音域（CS）
AT< +CREG: 2,4
         ↑ stat=4 = unknown（语音域没有任何服务）

RILJ: VOICE_REGISTRATION_STATE {4, ffffffff, ffffffff, ...}
GsmSST: error parsing RegistrationState: Invalid int: "ffffffff"
PHONE:  setVoiceRegState=1        ← 1 = OUT_OF_SERVICE
```

`+COPS: 0,2,"46011",7` → act=7 是 E-UTRAN（LTE）。也就是说设备只挂在 LTE 上，而 LTE 本身**只跑数据，不跑语音**——语音要么回落 2G/3G（CSFB），要么走 VoLTE。

### 第 3 层：两条语音出路都断了

| 出路 | 需要什么 | 这台设备 |
|---|---|---|
| **CSFB 回落** | 2G/3G 电路域信号 | 中国电信 CDMA 1x 已全国退网，没有可回落的目标 |
| **VoLTE** | Android 5.0+ 的 IMS 协议栈 | 系统是 **4.4.4（2014 年）**，压根没有 IMS 框架；radio 日志里搜 `ims / volte / capability` **零命中** |

所以在别的手机上（有 VoLTE）这张卡能打电话，在这台设备上就必然打不通——不是配置问题，是能力缺失。

## 三、桌面那个"电话"是什么

**它不是运营商电话，是随锐（xylink）云会议的拨号盘。**

证据：

1. 拨号盘提示语写的是「请输入云会议号、终端号或手机号」——把"云会议号"放在第一位；
2. 界面在 `vulture.app.home/vulture.home.call.contacts.ContactsActivity`，通话走 `NemoCallActivity` + CallSdk（Nemo 云会议 SDK）；
3. 按拨号键后日志出现：

```
W/NEMO_UI: HttpConnector, uri: https://cloud.xylink.com:443/api/rest/v3/circleofnemo/351376162...
           response error, java.io.IOException: BufferedInputStream is closed
E/NEMO_UI: RestApiAccessor.syncCircle, onException
```

4. 号码只是被记进了左侧呼叫记录（`10000 ↗ 19:31`），`mCallState` 一直是 0，没有产生任何呼叫。

也就是说：那个界面是给**云视频会议**用的，拨 10000 它并不认为这是个电话号码，只是当会议号/终端号记了一笔，然后同步云端失败。

## 四、能不能改成"能打电话"

三条路，都有硬门槛：

| 方案 | 可行性 | 风险 |
|---|---|---|
| 改 `config_voice_capable` 为 true | 要重编译 framework-res.apk 并用**平台密钥**重新签名 | ⚠️ 签名不对 = 系统起不来 = 变砖。而且就算改成功，第 2、3 层（无 CS 域、无 VoLTE）照样挡住，还是打不通 |
| 给 4.4 加 VoLTE | Android 4.4 没有 IMS 框架，不是装个 APK 能补的 | 需要移植整套 IMS 栈，等于重做一个 telephony 框架 |
| 换模块/换固件 | Fibocom 模块本身可能支持 VoLTE，但系统不提供 IMS 通道 | 属于系统级改造 |

**我的建议：不要动。** 改 framework-res 的变砖风险远大于收益，而且改了也打不通（第 2、3 层不解决，第 1 层改开也没用）。

### 8.2 对"能不能打电话"的影响

**模块本身是有语音能力的**（L710 是面向 M2M 的 LTE Cat.4 模块，支持 CSFB 回落语音）。
但语音打不通不在这颗模块上，而是：

1. 系统框架 `config_voice_capable=false` → 拨号请求根本不下发给 rild；
2. 电信 CDMA 1x 退网 → 没有电路域可回落；
3. Android 4.4 无 IMS 栈 → VoLTE 也走不了。

换句话说：**模块这颗"喇叭"是好的，但系统把线剪了，而且外面的电线杆（CDMA）也拆了。**

### 8.3 手动查模块型号的命令（留档）

## 九、避开第一层后发现的真相（2026-11-04 19:55）

按用户要求"一个一个来"，先解决第 1 层（framework 禁止语音），成功了；但避开之后发现真正的墙在第 2 层。

### 9.1 第 1 层：可以避开，而且没动系统一个字节

**没有改 framework-res.apk，没有 remount /system，没有装任何东西。**

直接在空闲串口 `ttyUSB0` 上跟模块说话（`ttyUSB2` 被 rild 占，不碰）：

```
ATD10000;
OK
+CLCC: 1,0,2,0,0,"10000",129     ← stat=2 = DIALING，呼叫真的发起了
```

这一行证明：**framework 的 `config_voice_capable=false` 只是拦在 App 层，
避开它之后 RIL 和模块完全有能力发起呼叫。** 第 1 层不是问题。

> 也就是说：真要解决第 1 层，不需要动 framework-res（那是变砖高风险操作）。
> 用 `service call phone` 直接调 ITelephony.dial，或者走 ATD，都能避开去。

### 9.2 但呼叫立刻失败，原因是网络侧说了实话

完整过程：

```
+CREG: 1,"0BAF","00CE3B32",7      ← 语音域注册(stat=1)，看起来是好的
ATD10000;  → OK
+CLCC: 1,0,2,...                  ← 正在拨号
+CLCC: 1,0,6,...                  ← 挂断
NO CARRIER                        ← 没有可用的语音承载
```

追问失败原因：

```
AT+CEER
+CEER: "EPS Session Management",51,
       "Combined EPS attach or TAU successful for EPS only, CS domain not available"
```

**"CS domain not available"** —— 这是网络（电信）直接告诉模块的话：
联合附着（EPS+CS）只成功了数据那部分，**电路域根本没有**。

### 9.3 第 2 层：L710 不支持 CDMA，所以电信无路可走

查了模块支持的网络制式：

```
AT+GTRAT=?
+GTRAT: (0-7),(0,1,2,3),(0,1,2,3)     ← 8 种模式，没有 CDMA
```

查了官方规格（L710-CN）：

| 项 | 支持 |
|---|---|
| LTE FDD | B1 / B3 / B8 |
| LTE TDD | B38 / B39 / B40 / B41 |
| WCDMA | B1 / B8 |
| TD-SCDMA | B34 / B39 |
| GSM | 900 / 1800 |
| **CDMA** | ❌ **不支持** |
| **VoLTE** | ❌ 规格书未列 |

电信的 2G/3G **就是 CDMA**。模块不支持 CDMA → 没有可回落的电路域。
模块也没有电信的 GSM（电信压根没有 GSM 网）。

**所以电信卡在这颗模块上，只有 LTE 数据这一条路。**

### 9.4 第 2 层后半：VoLTE 也建立不起来

`AT+CIREP?` → `+CIREP: 0,1`（IMS 显示已注册），但实际呼叫时：

- 没有任何 IMS PDN 激活记录（`AT+CGDCONT?` 只有 `CTNET` 一条，无 `ims` 承载）；
- 拨号走的是 CS 路径，然后被网络以 `NO CARRIER` 拒绝；
- 说明模块的 IMS 注册**只有信令，没有语音能力**（典型 M2M 模块的 SMS-over-IMS，不含 VoLTE 语音）。

### 9.5 第 3 层（Android 4.4 没 IMS 栈）：其实完全不相关

这一点我之前的表述需要修正 —— **VoLTE 不需要 Android 提供 IMS 栈**。

对照项目里的实证：`快话SW100-UH4-话务盒/83-2026-10-15-盒内EC20固件分析-VoLTE语音栈与卡点定位.md`

EC20 的 VoLTE 栈**整个在模块固件里**：

```
quectel_voice_rx_svr_thread / quectel_voice_tx_svr_thread    ← CS 语音
quectel_volte_rx_svr_thread / quectel_volte_tx_svr_thread    ← VoLTE 语音
volte call rx/tx open pcm handle                              ← VoLTE 走 PCM
AT+QCFG="ims"   → "ims",1,0                                   ← IMS 使能
AT+QCFG="volte_disable" → 0                                    ← VoLTE 未禁用
```

那份文档的结论写得很清楚：**"VoLTE 在模块侧不需要我们再补什么"**。
Android 只要能把 ATD 发下去、把音频接出来就行，不需要系统有 IMS 框架。

**所以小辣椒 4.4.4 能打 VoLTE，靠的是它芯片平台（MTK）自带的 IMS，不是 Android 系统。
而 T70L 的 IMS 只能指望 L710 自己 —— L710 没有。**

### 9.6 ★ 新发现：换移动/联通卡可能真的能打

L710 支持 **GSM 900/1800** 和 **WCDMA B1/B8**：

- **中国移动**：GSM 900/1800 → 有电路域，能走 CS 语音
- **中国联通**：WCDMA B1/B8 → 有电路域，能走 CS 语音
- **中国电信**：CDMA（不支持）+ LTE（无 VoLTE）→ 死路

也就是说：**这台设备配移动或联通的卡，大概率能直接打电话**（CS 域可用，不需要 VoLTE、不需要 IMS、也不需要改 framework —— 但需要避开第 1 层那个 false）。

> 注意：移动 2G 正在退网、联通 3G 也在收缩，实际能不能注册要看当地覆盖。
> 但这是目前唯一一条"不改硬件、不刷机"的活路。

### 9.7 这一轮做了什么、没做什么（安全交代）

**做了什么（全部只读或可逆）：**

| 操作 | 风险 |
|---|---|
| `AT+CGMM` / `AT+CGMI` / `AT+CSQ` / `AT+CREG?` / `AT+CGDCONT?` / `AT+CFUN?` / `AT+CGATT?` / `AT+CIREP?` / `AT+CEER` / `AT+GTRAT=?` / `AT+CLAC` | 只读查询，零风险 |
| `ATD10000;` 一次（拨电信客服） | 呼叫发起后立刻 NO CARRIER，未计费、未接通 |
| `AT+CLAC` 拿到 409 条命令全表 | 只读 |

**没做什么（这些才是高风险动作，全部没碰）：**

- ❌ 没改 `framework-res.apk`（重编译+平台密钥重签，错了就变砖）
- ❌ 没 remount `/system`（当前还是 `ro`，原样）
- ❌ 没改 APN（`CTNET` 原样，没加 `ims`）
- ❌ 没改 `GTRAT` 网络制式（还是 3 = LTE only）
- ❌ 没执行 `AT+CFUN=1,1`（模块重启）
- ❌ 没刷任何固件

**设备当前状态：数据和之前完全一样，语音呼叫没有残留（`+CLCC` 为空）。**

### 9.8 下一步的三个选项

| 选项 | 内容 | 风险 | 成功率 |
|---|---|---|---|
| **A. 换移动/联通卡试** | 插一张移动或联通卡，用 `ATD` 直接拨，看 CS 域能不能通 | 极低（只是换卡） | **较高**（模块支持 GSM/WCDMA） |
| B. 避开第 1 层让 App 能拨 | 用 `service call` 或改 App，让桌面电话键走 RIL | 低（不碰系统） | 依赖 A 成功 |
| C. 给 L710 换带 VoLTE 的固件 | 需要 Fibocom 原厂固件包 | **高**（刷模块会变砖，且包拿不到） | 低 |

**建议：先做 A。** 这是唯一不需要动系统、且模块硬件上真的支持的路。

## 十、关于"写语音内核把语音引出来"的可行性评估（2026-11-04 19:58）

用户提出：参照 QDC507（大疆 4G 模块）的做法，给 L710 写一个"语音内核"把语音引出来。

### 10.1 先看 QDC507 那个先例到底做了什么

读了 `QDC507-双向语音/01-技术总备份/ai-recovery/01-系统全景.md` 和 `05-模块接口手册.md`。

**关键认知：QDC507 不是"写内核"，而是"接通一条已经存在的硬件通路"。**

那个模块（百旺 QDC507，大疆用）是**智能模块** —— 模块内部跑的是 Linux，有完整的 ALSA 音频栈：

| 层 | 组件 | 作用 |
|---|---|---|
| 模块内系统 | adb 可登录 | 说明模块内有可执行的 Linux |
| ALSA 音频 | `/proc/asound/card0/pcm4` | 已有 PCM 设备 |
| 语音路由激活 | `alsaucm_test`（FIFO `/run/alsaucm_test`） | `set _enadev Auxpcm Rx/Tx` 打开 modem 的 PCM 通路 |
| mixer | `/tmp/alsa_mixer_set` | 按 numid 设 `SEC_AUX_PCM_RX_Voice Mixer` |
| 桥接 | `mavo-pcm-bridge` | 把 pcm4 ↔ **USB UAC（USB 音频类）** 桥到 Mac |

文档原话：

> "我们真正打通的是另一条路 —— **让模块的语音以 USB 音频形式直接出现在 Mac 上**"

也就是说，QDC507 的链路是：

```
modem 语音 DSP → Auxpcm 硬件引脚 → 模块内 ALSA(pcm4) → mavo-pcm-bridge → USB UAC → Mac 当声卡用
```

**三个前提缺一不可：① 模块内能跑代码（Linux/ADB）；② 有 Auxpcm 音频硬件通路；③ 能通过 USB 音频类送到主机。**

### 10.2 L710 三条全缺

| 前提 | QDC507 | **L710（本机）** |
|---|---|---|
| ① 模块内可执行系统 | ✅ 有 ADB，能登录 Linux | ❌ **纯 AT 模块**，8 个 USB 接口里没有 ADB（1.7 是 ff/42/01 = MBIM），模块内部无可执行环境 |
| ② 音频硬件通路 | ✅ Auxpcm 引脚 + ALSA pcm4 | ❌ **规格书 Functional Interface 只有**：SIM / USB2.0 / UART / LPG / EINT / System Indicator / MUX over UART1 —— **没有 PCM、没有 AUDIO** |
| ③ USB 音频类 | ✅ 模块以 UAC 出现在主机 | ❌ **USB 接口类全表**：`02/06`(CDC ACM)、`0a`(CDC Data)、`ff/ff/ff`×5(厂商)、`ff/42/01`(MBIM) —— **没有 class 01（Audio）** |

实测 USB 接口类（`/sys/bus/usb/devices/1-1:1.x/bInterfaceClass`）：

```
1.0: 02/06/00   CDC ACM
1.1: 0a/00/00   CDC Data
1.2: ff/ff/ff   厂商（ttyUSB0，AT 口）
1.3: ff/ff/ff   厂商（ttyUSB1）
1.4: ff/ff/ff   厂商（ttyUSB2，rild 占）
1.5: ff/ff/ff   厂商（ttyUSB3）
1.6: ff/ff/ff   厂商（ttyUSB4，诊断）
1.7: ff/42/01   MBIM
```

**没有一个 01（Audio Class）。**

> 说明：`/dev/snd/` 里确实有 `pcmC0D0 ~ pcmC0D4`，但那是 **T70L 主控（sunxi sun8i）自己的板载声卡**（接本地麦克风/喇叭），
> 跟 4G 模块没有任何电气连接。模块的声音出不到这块声卡上。

### 10.3 所以"写语音内核"这条路在 L710 上不成立

不是因为技术难度，而是**没有可引的东西**：

- **没有地方放代码**：L710 是哑模块，内部没有 Linux/Android 可供我们注入程序。能写"内核"的前提是那块板子上有个 CPU 能跑我们的代码——L710 没有暴露这样的环境。
- **没有物理引脚出声音**：就算固件里藏着语音栈，L710 的硬件接口表里没有 PCM/AUDIO 引脚，声音从芯片里出不来。
- **没有 USB 音频通道**：USB 描述符里没有 Audio Class，主机根本看不到它的"声卡"。

打个比方：QDC507 是"家里已经铺好了水管，只是阀门没开，我们去拧开"；
L710 是"墙里压根没埋水管"，我们画多少图纸都没用。

### 10.4 如果一定要在 L710 上做，需要付出什么

理论上唯一路径是**改模块固件**（不是写内核，是刷固件）：

1. 拿到 L710 的固件包（Fibocom 原厂，不公开）；
2. 过签名校验（展锐/联发科平台有安全启动）；
3. 在固件里塞进 VoLTE 栈 + 音频路由；
4. **还得解决硬件没有音频引脚的问题** —— 这一步无解，除非改板飞线。

第 4 步是死结：**改固件也变不出引脚**。

### 10.5 结论

| 方案 | 结论 |
|---|---|
| 给 L710 写"语音内核"引出 VoLTE | ❌ **不成立**（无模块内系统、无音频引脚、无 USB 音频类） |
| 参照 QDC507 的桥梁方案 | ❌ 前提不满足（那套方案依赖模块内 ALSA + Auxpcm + UAC） |
| 换移动/联通卡走 CS 语音 | ✅ 可行（模块支持 GSM/WCDMA，有电路域） |
| 换一颗支持语音的模块（如 EC20） | ⚠️ 可行但属于**硬件改造**，不符合项目铁律 |
| 用 4G 数据跑 VoIP/SIP | ⚠️ 可行但那是网络电话，不是 VoLTE，且需 SIP 账号 |

**建议仍然走"换移动/联通卡"这条路** —— 零改造、零风险、模块硬件真的支持。

## 十一、★ 重大更正：这台设备本来就"能打电话"，只是不走 SIM 卡（2026-11-04 20:05）

用户质疑："如果真不支持打电话，为什么拨号盘写着『请输入云会议号、终端号或手机号』？通讯录里为什么有那么多手机号？"

**这个质疑是对的。我之前"设备打不了电话"的结论不完整，必须更正。**

用 静态分析 流程深度分析了 `vulture.app.home`（19MB，classes.dex 6.7MB + `libcallmodule_aw.so` 11MB），
结论是：**这台设备有一套完整的云端 PSTN 外呼能力，只是它不经过 SIM 卡、不经过 RIL。**

### 11.1 铁证一：整个 APK 里没有任何运营商拨号 API

```
grep -rn "android.intent.action.CALL|ITelephony|TelephonyManager|ACTION_DIAL|\"tel:" → 0 命中
```

**一次都没有。** 这个 App 从不调用系统电话栈。

### 11.2 铁证二：它有一套完整的 PSTN 呼叫体系

### 11.3 三种输入的真相 = 三种 DeviceType

拨号盘那句"请输入云会议号、终端号或手机号"，对应的正是 `DeviceType` 枚举：

| 用户输入 | 解析成 | DeviceType |
|---|---|---|
| 云会议号 | 会议 | `CONFERENCE(97)` / `CONFNO(96)` |
| 终端号 | 设备 | `HARD(2)` / `SOFT(1)` / `BROWSER(3)` |
| **手机号** | **PSTN 电话** | **`TEL(99)`** |

`cp.java` 里有一段 `switch (deviceType.ordinal())` 分 10 个分支，每种类型走不同的呼叫方式。

### 11.5 所以"打不出去"的真正原因

不是硬件、不是 SIM 卡、不是 VoLTE、不是 CDMA 退网 —— **是云账号侧没有外呼资格**。

最可能的三种情况（按概率）：

1. **企业账号没开 PSTN 外呼权限**（最常见）；
2. **"免费通话余额"为 0** —— 代码里专门有个 `dial_panel_free_call_balance` 字段；
3. **主叫号码 179411 未在运营商侧备案**（PSTN 外呼必须报备主叫号，否则网关直接拒）。

### 11.6 更正总结

| 之前的结论 | 更正后 |
|---|---|
| "这台设备打不了电话" | ❌ 不准确。**它设计上就是能打手机电话的**，走云平台 PSTN 出局 |
| "需要 VoLTE / IMS" | ❌ 不需要。PSTN 出局由云端网关完成，与 SIM 卡语音能力无关 |
| "需要换移动/联通卡" | ❌ 对"打电话"这件事不必要（换卡只影响 CS 回落那条路，而 App 根本不走那条路） |
| "SIM 卡没用" | ⚠️ 部分正确：SIM 卡只提供 4G 数据，让设备能连云平台；通话本身不走它 |

**结论：这是一台"云电话机"。它打的每一通电话，都是云端网关替它拨出去的。**

这也解释了通讯录里为什么有那么多手机号 —— 那些是企业云通讯录同步下来的联系人，
以及这台设备历史上用云账号拨打过的 PSTN 号码。
