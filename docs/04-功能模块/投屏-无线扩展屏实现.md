# 无线投屏 / 扩展屏 —— 实现与结论（2026-11-07）

> 一句话：**「平板 → Mac」在这台硬件上是死路，但「Mac → 平板」已经跑通，15fps、20.9KB、40MB 内存。**
> 平板开 App 就能看到 Mac 桌面，同一 WiFi，不插线。

---

## 一、先把方向定死：哪个方向能做

你提的两个方向，技术上是完全不同的难度，实测结论如下：

| 方向 | 依赖 | 实测结果 | 结论 |
|---|---|---|---|
| T70L → Mac（把平板画面投到电脑） | 设备端必须能**采集自己的屏幕** | 见下方三条实测 | ❌ 系统层面无解 |
| Mac → T70L（把电脑屏幕扩展到平板） | 平板只需**显示一张图** | 15fps 稳定，延迟可接受 | ✅ 已实现 |

### 为什么 T70L → Mac 走不通（不是没试）

| 尝试 | 实测数据 | 为什么不行 |
|---|---|---|
| `screencap` 轮询 | **2.9~3.0 秒/帧**（0.3fps） | 4.4 只能出 PNG，1280×800 一张 596KB，编码+落盘吃掉全部时间 |
| `screenrecord` | 不支持 `--output-format=h264` | 裸 H.264 输出是 Android 5.0 才有的 |
| 直读 `/dev/graphics/fb0` | 0.42 秒/帧 | `dd` 落盘 + FUSE 写 /sdcard 太慢；就算 mmap 直读，还有三缓冲取活跃 buffer 的问题 |
| HDMI 采集卡 | **屏幕是 MIPI 直连 LCD，机器上没有 HDMI 输出口** | 物理上不存在这条路 |
| `adb exec-out` 管道 | 返回 0 字节 | 这台设备的 adb 实现不支持 |
| Miracast / Wi-Fi Display | `getprop | grep wfd` 全空 | 固件没编这功能 |

**根因**：Android 4.4 没有 `MediaProjection`（5.0 才有），屏幕又没有对外输出口。
scrcpy / Vysor 这类工具全部要求 **Android 5.0+**，在 4.4 上根本起不来。

> 唯一理论上还能走的是 `minicap`（OpenSTF，用私有 `createDisplay` + BufferQueue 抓帧，
> 明确支持 4.4）。但它需要 NDK 编译，且要走 adb 的 Unix socket，不能直接用 WiFi 连。
> 见文末「还能做什么」。

## 二、Mac → T70L 是怎么做的

### 架构

```
Mac                                              T70L (192.168.1.151)
┌────────────────────────────┐                  ┌──────────────────────────┐
│ ScreenCaptureKit 采集       │                  │ 扩展屏 App               │
│   1280×720 @15fps          │   TCP 7200       │   读帧 → RGB565 解码      │
│        ↓ CIImage           │ ───────────────► │        ↓                 │
│   JPEG 编码 q=0.45         │  117KB/帧        │   ImageView 全屏显示      │
│        ↓                   │  1.8MB/s         │                          │
│   只保留最新一帧（丢旧帧）  │                  │   只保留最新一帧          │
└────────────────────────────┘                  └──────────────────────────┘
```

**协议只有两行**，平板端十行代码就能解：

```
[4 字节小端长度][N 字节 JPEG]   ← 循环
```

### 为什么用 JPEG 而不是 H.264

| 方案 | Mac 端 | 平板端 | 结论 |
|---|---|---|---|
| H.264 | MediaCodec 硬编，代码量大 | **4.4 的 MediaPlayer 拉不了裸流**，得自己写解码 | ✗ |
| WebRTC | 需要整个库 | Chrome33 内核不支持 | ✗ |
| **MJPEG** | ImageIO 一行 | `BitmapFactory.decodeByteArray` 一行 | ✓ |

MJPEG 的代价是带宽高（1.8MB/s vs H.264 的 0.3MB/s），但**WiFi 完全吃得下**，
换来的是两端各几十行代码、零依赖、零兼容问题。1GB 内存的机器经不起重方案。

### 关键实现细节（这些坑都是实测踩出来的）

**① SCStream 对 output 是弱引用**
```swift
try stream.addStreamOutput(cap, type: .screen, sampleHandlerQueue: queue)
```
`cap` 是局部变量，函数一返回就被释放，**采集回调从此永远不触发**。
现象特别迷惑：能连上、能握手、就是**一帧都没有**。
必须自己用静态数组攥住 `cap` 和 `stream`。

**② 帧长度是「小端」**
Swift 发的是 `UInt32(d.count).littleEndian`，Java 的 `DataInputStream.readInt()`
读的是**大端**。直接用会读出天文数字，表现为「帧长度异常，断开重连」。
平板端改成手工拼字节：
```java
int len = (b0 & 0xFF) | ((b1 & 0xFF) << 8) | ((b2 & 0xFF) << 16) | ((b3 & 0xFF) << 24);
```

**③ 必须丢帧，不能让 TCP 缓冲积压**
解码慢于发送时，如果老老实实读完每一帧，延迟会越积越大（表现为「画面越来越滞后」）。
两端都做了**只保留最新一帧**的槽位：新帧直接覆盖没被取走的旧帧。
效果是「掉帧」而不是「延迟增长」——这才是实时该有的行为。

**④ 旧 Bitmap 要延迟回收**
```java
view.setImageBitmap(newBm);
ui.postDelayed(() -> oldBm.recycle(), 150);   // 不能立刻 recycle
```
立刻回收会踩到还没画完的那一帧，报 `Canvas: trying to use a recycled bitmap`。
150ms 足够让这一帧走完绘制。

**⑤ 全程 RGB_565，不用 ARGB_8888**
单帧 1.8MB → 不是 3.6MB。肉眼在这个尺寸上看不出差别，但内存差一倍。

**⑥ 三缓冲 + inBitmap 复用（这条最要命）**

第一版是「每帧新解一张 Bitmap，150ms 后回收旧的」，实测**内存以 9MB / 30 秒的速度往上涨**
（约 5 张 Bitmap），因为 15fps 下每 66ms 就分配 1.8MB，而回收是异步的，永远追不上。
1GB 的机器跑十几分钟就会 OOM。

改成**固定 3 个 buffer 轮转 + `inBitmap` 复用**：

```java
Bitmap cached = pool[bufIdx];
opt.inBitmap = cached;          // 让解码器直接写进这块已有的像素内存
Bitmap bm = BitmapFactory.decodeByteArray(data, 0, data.length, opt);
pool[bufIdx] = bm;
bufIdx = (bufIdx + 1) % 3;
```

稳态下**再也不产生新的 Bitmap 分配**，内存从 34~45MB 直接压到 **23.8~25.9MB 一条平线**。

为什么是 3 个而不是 2 个：`show()` 是 `post` 到 UI 线程异步执行的，
用 2 个的话，解码端可能已经开始复用「正在被绘制」的那块，导致花屏。
3 个留出 200ms 余量，被复用的那块肯定已经被 ImageView 换下来了。

用这个方案后，`show()` 里**绝对不能再 recycle 旧 bitmap**，
否则会把马上要被复用的 buffer 干掉。所有 Bitmap 的生命周期统一归 decodeLoop 的三缓冲池管。

## 三、实测数据

### Mac 端（ScreenCaptureKit，1920×1080 → 1280×720）

| 指标 | 数值 |
|---|---|
| 采集帧率 | 28.4 fps 上限（配置限到 15fps 发送） |
| 单帧 JPEG | 117 KB（质量 0.45） |
| 单帧编码耗时 | **9.5 ms** |
| 网络占用 | **1.8 MB/s ≈ 14.4 Mbps** |

### 平板端

| 指标 | 数值 |
|---|---|
| 显示帧率 | **14~15 fps**（和 Mac 端完全同步，解码没掉队） |
| 进程 PSS | **23.8~25.9 MB**（三缓冲复用后，稳定不涨） |
| 全机空闲内存 | 358 MB |
| 连续运行 | 2 分钟无掉线、无 OOM、无重启、无花屏 |

### 分辨率与比例

- Mac 屏 1920×1080（16:9），平板 1280×800（16:10），**比例不一样**
- 默认：保持 16:9，上下各留 40px 黑边（不变形）
- 长按屏幕：切换「铺满全屏」，纵向拉伸 11%，肉眼几乎看不出，Dock 贴底更好看

## 四、怎么用

### Mac 端

```bash
cd 核心资产/源码/13-投屏/mac
./start.sh          # 首次会自动编译
```

启动后会打印：
```
源显示器 1920x1080 → 输出 1280x720 @15fps 质量 0.45
采集已启动
已监听 0.0.0.0:7200
平板端填这个地址： 192.168.1.210     ← 记下这个
等待平板连接…
```

### 平板端

打开桌面上的「扩展屏」（包名 `com.lm.screen`），它会自动连上次的地址。

- **默认地址**：`192.168.1.210`
- **改地址**：点一下屏幕（出现状态条）→ 再点一下 → 弹出输入框
- **切换铺满**：长按屏幕
- **退出**：返回键

状态条会显示：`已连接 192.168.1.210 · 15 fps · 1280x720`

### 断线怎么办

平板 3 秒自动重连一次，Mac 端不会退出。Mac 睡眠唤醒后，平板会自动接回来。

## 五、已知限制

1. **只能看，不能操作**。平板上点屏幕不会传到 Mac（传触摸需要额外做一遍 InputEvent 注入，
   而且 Mac 侧要改鼠标坐标系，工程量翻倍，先没做）。
2. **15fps**，看文档、看代码、看监控完全够；看视频会有轻微顿感。
3. **带宽 1.8MB/s**，2.4G WiFi 会比较吃力，建议 5G 频段。
4. Mac 端**必须保持程序运行**，终端窗口不能关（关了就断流）。
5. 首次运行时 macOS 可能弹「屏幕录制」权限，需要允许一次。

## 六、还能做什么（如果以后要继续深挖 T70L → Mac）

调研到的唯一可行路线：**minicap**（OpenSTF）

- 明确支持 Android 4.4（`minicap_19.cpp`，用 `createDisplay` + BufferQueue，不是 fb0）
- 官方说老设备能到 10-20fps
- 预编译的 `minicap.so` 仓库里就有，但**主二进制要 NDK 编译**
- 通信是 Unix domain socket，想走 WiFi 需要再套一层转发

代价：装 NDK（约 1GB）、编译、适配 A83T 的私有 API、写转发层。
收益：把平板画面投到 Mac 上，而且没法反控（minicap 只出画面）。

**另外还有一条更省事的**：`darcyg/android-vnc-server`，明确写了支持 4.4~10.0，
把 minicap + libvncserver 合成一个二进制，直接监听 TCP 5900，Mac 自带的「屏幕共享」就能连。
同样需要 NDK 编译。

结论：**要做就得先装 NDK**，工作量约半天，成功率中等（A83T 的 SurfaceFlinger 私有接口有不确定性）。
等你觉得确实需要「平板投到电脑」再动，现在先用 Mac → 平板的扩展屏。
