# 语音控制：麦克风真相与接管方案


---

## 一、麦克风硬件：确实是两颗独立麦

用「抢占麦克风 → 录 10 秒 → 做声学分析」的方式实测（原始数据 `voice/mic_raw.pcm`，48000Hz/2ch/16bit）：

| 指标 | 数值 | 说明 |
|---|---|---|
| 时长 / 大小 | 9.43 秒 / 1,810,432 字节 | 无丢帧 |
| 左声道 RMS | **-69.0 dBFS** | 真实麦克风底噪水平 |
| 右声道 RMS | **-69.3 dBFS** | 与左声道独立 |
| **左右相关系数** | **0.342** | 若是单麦复制到两声道，应接近 1.0 |
| **完全相同的采样** | **3.37%** | 几乎无重复 |

**结论：左右是两颗独立的物理 MEMS 数字麦克风，不是单麦复制。**

硬件链路：
- Codec：Allwinner **AC100**（I2C `0-001a`）
- 麦克风输入：`ADCL Mux = DMIC`、`ADCR Mux = DMIC`（tinymix 控件 26/27）
- 采集能力：2ch / S16_LE / 48000Hz（`pcm0c`）
- I2S 是 TDM 结构（`AIF1 ADC timeslot 0/1 volume`）
- **I2C 上没有任何外部阵列 ADC 芯片**（无 ES7210/TLV320 之类），USB 上也没有音频设备

所以软件能看到的物理上限就是 **2 路**。物理上是否还有更多麦通过模拟开关合并到这两路，软件无法区分——但**任何软件方案都只能拿到 2 通道**。

补充：`audio_policy.conf` 里有个非标准的输入设备 `AUDIO_DEVICE_IN_AF`（Audio Front-end），说明厂商在 HAL 层做过音频前端扩展，但它没有对应独立的采集通路。

## 二、为什么"自己录音"走不通（Android 4.4 的硬限制）

### 实测现象

任何 App 调用 `AudioRecord.startRecording()` 都失败：

```
AudioRecord: start() status -38        ← ENOSYS
getRecordingState() 停留在 1 (STOPPED)
read() 返回 -3 (ERROR_INVALID_OPERATION)
```

测遍的矩阵（`/tmp/ardiag/` 探针）：4 类 source（MIC / VOICE_RECOGNITION / CAMCORDER / DEFAULT）
× 3 采样率（48000/16000/8000）× 单双声道，
外加 VOICE_UPLINK / VOICE_DOWNLINK / VOICE_CALL / VOICE_COMMUNICATION —— **全部 -3**。

### 真正的根因（logcat 实录）

```
V/audio_hw_primary: adev_open_input_stream ... status 0        ← HAL 层其实允许
V/AudioFlinger:     openInput() created record thread: ID 16   ← 新建了一条流
W/AudioPolicyManagerBase: startInput() input 16 failed: other input already started..
E/AudioRecord:      start() status -38                          ← 被策略层拒绝
```

**HAL 是允许的，卡在 `AudioPolicyManagerBase`。**

- Android 4.4 的 `getInput()` **不做输入流复用**，每次请求都新建 input descriptor；
- `startInput()` 又**全局只允许一路 input 处于活动状态**（AOSP 4.4 的设计，出于隐私/兼容考虑）。

### 试过但无效的路

| 尝试 | 结果 |
|---|---|
| 改 `audio_policy.conf` 移除 `AUDIO_DEVICE_IN_BACK_MIC`（让 device 与桌面一致） | 仍新建、仍被拒 |
| 用 VOICE_COMMUNICATION 强制走 BUILTIN_MIC | 仍被拒 |
| 通过 `pcm1c`（Voice DAI）直接录音 | 只支持 2ch/8000Hz，且**与 pcm0c 并发会导致整机重启** |
| `kill -9 mediaserver` 让配置生效 | **mediaserver 是 init 的 critical 进程，杀它会整机重启**（踩过，uptime 归零） |

**结论：Android 4.4 上"两个应用同时录音"不存在任何软件解法。**

## 三、麦克风被谁占着，为什么抢不得

`pcm0c` 长期被 **`vulture.app.home`（NemoHome 桌面）** 占用：

```
Input dump:
 Sampling rate: 48000
 Format: 1
 Channels: 0000000c        ← 立体声
 Devices  80000004         ← AUDIO_DEVICE_IN_BUILTIN_MIC
 Ref Count 1
挂载的 Effect: Acoustic Echo Canceler（硬件回声消除）
```

它录音是**会议核心功能**，不是可关的开关：
- dex 里有 `AudioCapture.registerNativeAudioDataSource sourceID =`，音频交给小鱼易连会议 SDK 做上行采集；
- `local_config.xml` 里 `enableDigitalMic=true`、`SupportRecordingInCall=true`；
- 它还承担"小连小连"语音唤醒的常驻监听。

**抢占的致命后果（实测）**：桌面只要被拒一次 `AudioRecord`，录音线程就**永久损坏**——
即使把麦克风还回去，它仍以 **187 次/秒** 空转刷：

```
I/NEMO_UI: AudioCapture.startCapture: Recording Thread read data error, ret=-3
```

CPU 只多占 2%（可接受），但日志洪水会淹没 logcat，而且**不自愈，只能 `kill -9` 桌面重启**。

→ **"抢占麦克风"方案被证伪：代价是每次都要重启桌面。**

## 四、意外突破口：原厂预留了「智能家居」插件接口

在被麦克风问题逼到墙角后，翻桌面 APK（NemoHomeApp.apk, 19MB）的 dex，发现了这套东西：

```
Lvulture/module/speech/smartHome/smartHomeController;
Lvulture/module/speech/SmartHomeResult$SmartHomeDetail;
SmartHomeCommand
sendSmartHomeCommand / sendSmartHomeCommandBroadCast
supportSmartHomeApps          ← 插件白名单
mCurrentSmartHomeSeq          ← 命令序号（时序管理）
com.ainemo.intent.smarthome.action.command    ← 命令 Action
com.ainemo.intent.smarthome.action.result     ← 结果 Action
"can not find service for com.ainemo.intent.smarthome.action.command"
```

**也就是说，桌面本来就有这套链路：**

```
桌面录音 → 语音识别 → 判断为家居指令 → 发 command 给插件 → 插件执行 → 回传 result
```

而且日志里那句 "can not find service" 说明：**它一直在找这个插件，但没人实现，所以一直失败。**

### 已经做好的事

写了一个插件 `com.lm.smartlink`（APK 已装在设备上），包含：
- `SmartHomeService` / `SmartHomeReceiver`：监听上面两个 Action；
- `Probe`：把收到的 Intent 连同**所有 extras 的类型和值**完整 dump 到 `/sdcard/smartlink.log`；
- `TtsPlayService`：用原厂 TTS 合成并播放指令（用于自测）。

**验证结果（用 adb 模拟桌面发命令）**：

```
=== SERVICE onStartCommand ===
action=com.ainemo.intent.smarthome.action.command
extras keys=...
  [device]  (java.lang.String)  = light
  [seq]     (java.lang.Integer) = 1
  [command] (java.lang.String)  = on
```

**插件能被正确调起、能完整解析参数。现在就差桌面真正发出那条命令。**

## 五、桌面的语音能力（已摸清）

### 唤醒词是「小连小连」，不是"Hi 小文"

- NemoHome 的 `assets/ivw/speech_engine.jet` + dex 里的 `WAKEUP_ACTION / WAKEUP_THRESHOLD /
  wakeupHighThreshold / wakeupLowThreshold / wakeupListener score` → 桌面自带唤醒引擎；
- 隐藏设置页 `SystemSettingSpeechDebugActivity`（"语音调试"）里写着：
  「点击"开始"，以正常语速重复三次**"小连小连"**」——支持采样本自定义唤醒词。

### 语音机器人界面

- Action：`nemo.itent.action.activity.SPEECH` → `.speech.activity.SpeechActivity`
- 界面标题"语音机器人"，蓝色声波+麦克风圆钮，处于聆听待命状态
- 语音模块每 20ms 向 `ACTIVITY_PROXY_MODULE` / `CALL_MODULE` 发状态消息（6020）

### 原厂四个语音服务（MarlinSpeech.apk）

全部 `exported=true` 且无权限校验，可直接 bind：

| Action | 能力 |
|---|---|
| `...service.wakeup` | 本地唤醒（JNI + LSTM），但**唤醒词写死**（`res/raw/hotword` 内模型名 `hixiaowen_auto`），`setParameter` 是空实现 |
| `...service.asr` | **喂数据模式**：`putData()` 进队列 → `startMixRecognizerWithQueue(dev,null,null,queue)`，自己不录音；支持 `updateCommands(String[])` 自定义命令词并编译进本地语法 |
| `...service.understand` | 语义理解（Mobvoi 云端，实测仍可用，能识别"查天气"等意图） |
| `...service.tts` | 本地合成，`onDataArrival(byte[])` 回调 PCM（实测约 8kHz 单声道），但 **`onCompleted` 从不回调** |

## 六、为什么 TTS 自测唤不醒（重要教训）

想让设备"自己说一句"来验证语音，试了 TTS 合成 → 扬声器播放 → 麦克风拾取。
数据能放出来（33284 字节），但桌面完全没识别。

**原因：桌面那条录音流挂着硬件 `Acoustic Echo Canceler`。**
AEC 的职责就是把"扬声器正在播放的声音"从麦克风信号里减掉——
所以我们放出去的话，在它自己听来是被消掉的。

**结论：任何"自播自听"的语音自测，在这台设备上都不成立，必须真人说话。**

## 九、几个必须记住的坑

1. **`kill -9 mediaserver` = 整机重启**。它是 init 的 critical 进程。
2. **抢占麦克风 = 桌面永久空转**，只能靠重启桌面进程恢复。
3. **`AudioRecord.start()` 返回 -38 / read 返回 -3** 不是权限问题，是 4.4 的单路 capture 限制。
4. **`pcm1c` 只支持 8000Hz**，且与 `pcm0c` 并发会崩系统。
5. **TTS 自测无效**，因为硬件 AEC 会消除自播声音。
6. `/system` 每次重启会变回 ro，改动前要 `mount -o rw,remount /system`。
7. 设备 shell 极简，`head/wc/md5sum/which` 都没有，用 `/sbin/busybox`。
