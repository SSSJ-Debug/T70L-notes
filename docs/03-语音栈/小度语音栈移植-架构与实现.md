## 2. 当前运行架构（已实测跑通的那条）


### 2.1 为什么必须让 `tinycap` 独占采集

用 Java `AudioRecord` 采同一句话，唤醒 **0/3**；换 `tinycap` 直连 ALSA，唤醒 **3/3**。
AC100 这颗 codec 的 HAL 交给 `AudioRecord` 的数据在声道结构、电平、通路上都不对，而 HAL 我们改不了。
**结论：采集只走 tinycap，别再回头试 AudioRecord。**

### 2.2 引擎帧协议（从固件 JS 层 `sdkmessage.js` / `binparser.js` 还原）

```
帧   = [total_len : int32 LE] + token...
token= [len : int32 LE][type : int32 LE][payload]
        type 1 = STRING
        type 2 = INT
        type 3 = BUFFER
```

`duer_wake` 就是按这个格式把 16k PCM 写进 `WAKEUP` 的 stdin；引擎把结果写到一个 FIFO
（`/data/local/tmp/duer/wakeup_output_fifo`），`status == 4` 即唤醒命中。

### 2.3 引擎参数（唤醒，已实测有效）

```
WAK_CMD_CONFIG {
  COMMON_PARAM_KEY_DEBUG_LOG_LEVEL   = 6
  WP_PARAM_KEY_ENABLE_DNN_WAKEUP     = 1
  OFFLINE_PARAM_KEY_LICENSE_FILE_PATH = resources/bds_license.dat
  WP_PARAM_KEY_WAKEUP_WORDS          = {"words":["小度小度"]}
  WP_PARAM_KEY_WAKEUP_DAT_FILE_PATH  = resources/end2end_wakeup_far.dat
}
→ WAK_CMD_LOAD_ENGINE → WAK_CMD_START → WAK_CMD_PUSH_AUDIO{DATA_CHUNK}
```

## 3. 本次升级：能量 VAD 自动收尾（替代固定 3 秒）

### 3.1 旧实现为什么“慢半拍”

```
唤醒 → 播提示音 → 死等 2300ms → 取最近 3000ms → 解码 ≈ 300ms → 下发
```
用户 0.6 秒说完「开灯」，程序却雷打不动睡满 2.3 秒。**从说完到灯亮 > 2.6 秒**。
小度是「你说完就识别」，停口到响应 < 0.8 秒。差距就在这里，不是模型快慢。

### 3.2 新判据（全部在 `SpeakerService.java`，纯时域能量，A83T 跑得动）

| 参数 | 值 | 作用 |
|---|---|---|
| `VAD_BLOCK_MS` | 50 | 能量统计粒度 |
| 阈值 | `max(250, 底噪×3)` | 底噪取唤醒前一瞬 300ms，自动适应环境 |
| `VAD_ONSET_MS` | 150 | 连续有声 150ms 才算开口（滤掉咔哒声） |
| `VAD_PREROLL_MS` | 250 | 开口点回退 250ms，**保住第一个字** |
| `VAD_SIL_END_MS` | 450 | 停口 450ms 判定说完，立刻解码 |
| `VAD_MAX_MS` | 4500 | 单句上限 |
| `VAD_NO_SPEECH_MS` | 2500 | 唤醒后没人说话就放弃 |
| `BEEP_SKIP_MS` | 320 | 跳过自己的提示音（否则被当成开口） |

**降级兜底**：VAD 没抓到开口（说话太轻 / 阈值偏高）时，自动退回「取最近 3 秒」的旧逻辑。
所以最坏情况等于旧版，**不会因为 VAD 判断失误彻底哑火**。

### 3.3 提示音也改了

`400ms / 幅度 12000` → **`260ms / 幅度 9000`**。
原来提示音太长太响，会把自己麦克风收到的第一两个字压掉，这也是“喊了没反应”的一个次要原因。

### 3.4 代码要点（`$HOME/re-tools/t70l/asr/java/com/lm/rec/SpeakerService.java`）

环形缓冲新增三个方法，给 VAD 用绝对游标（不再用“最近 N 个”这种相对取法）：

```java
synchronized long  total();                 // 累计写入样本数，单调递增
synchronized short[] readFrom(long, int);   // 从绝对游标读，没新数据返回 null
synchronized short[] range(long, int);      // 取绝对区间
synchronized int   rmsOfLast(int);          // 估底噪
```

编译：`cd $HOME/re-tools/t70l/asr && ./build_app.sh` → 产出 `vosk.jar`（9.2 KB，含 classes.dex）。

## 4. 小度原厂离线识别（EASR / KWS）—— 协议分析

### 4.1 已确认的 API 面（从 64 MB `libDcsSdk.so` 符号表提取）

命令（`bds::` 命名空间）：

| 命令 | 用途 |
|---|---|
| `ASR_CMD_CONFIG` | 配置识别引擎 |
| `ASR_CMD_START` / `ASR_CMD_STOP` / `ASR_CMD_CANCEL` | 起停 |
| `ASR_CMD_PUSH_AUDIO` | 喂 PCM |
| **`ASR_CMD_KWS_LOAD` / `ASR_CMD_KWS_UNLOAD`** | **加载/卸载关键词语法（离线命令的核心）** |

回调：`CALLBACK_ASR_STATUS`、`CALLBACK_ASR_RESULT`、`CALLBACK_ASR_LEVEL`。

参数键（**离线识别全套**）：

```
ASR_PARAM_KEY_OFFLINE_ENGINE_TYPE              = "KWS" / "EASR"  ← 引擎里存在这两个字面量
ASR_PARAM_KEY_OFFLINE_ENGINE_DAT_FILE_PATH     = bds_easr_basic_model.dat
ASR_PARAM_KEY_OFFLINE_ENGINE_GRAMMER_FILE_PATH = bds_easr_gramm.dat
ASR_PARAM_KEY_OFFLINE_ENGINE_GRAMMER_SLOT      = 语法槽（如 "cmd"）
ASR_PARAM_KEY_OFFLINE_ENGINE_PROTOCOL          = 协议版本
ASR_PARAM_KEY_OFFLINE_ENGINE_WAKEUP_WORDS_FILE_PATH
ASR_PARAM_KEY_OFFLINE_ENGINE_TRIGGERED_WAKEUP_WORD
ASR_PARAM_KEY_MFE_CMVN_DAT_FILE                = bds_easr_mfe_cmvn.dat
ASR_PARAM_KEY_MFE_DNN_DAT_FILE                 = bds_easr_mfe_dnn.dat
ASR_PARAM_KEY_MODEL_VAD_DAT_FILE               = DNN VAD 模型
OFFLINE_PARAM_KEY_LICENSE_FILE_PATH            = bds_license.dat
OFFLINE_PARAM_KEY_APP_CODE                     = 产品码（SDK config 里为 722）
```

引擎内部的错误串（可作为探测依据，只要参数对不上，它会明确说是哪一类）：

```
Embedded engine is not initialized (...)
Offline engine was not properly configured
[KWS] grammer file invalid.
[ASR] resolve_grammar_file: no grammar file.
Offline engine license is expired / resource is faulty
```

### 4.2 语法文件格式（**与我们现有的生成器完全一致**）

官方 `bds_easr_gramm.dat` 是「整个 JSON 做一次 `urllib.parse.quote(s, safe='')`」的 URL 编码文本，解开后：

```json
{
  "version": "0.1",
  "slots": { "name": ["张三","李四","王五"], "appname": ["微信","百度地图"] },
  "rules": {
    "telephone.call": [
      { "origin": "打电话给<name>", "pattern": "^打电话给(张三|李四|王五)$", "groups": ["name"] }
    ]
  },
  "grammar": "<name> = 张三| \n李四;\n<_wakeup> = 唤醒词占位符;\n\n_SCENE_ID_ 0\n\n( <_wakeup>打电话给<name> )\n...",
  "origin_slots": "...",
  "origin_rules": "..."
}
```

要点：
- `<_wakeup>` 是**唤醒词占位符**，引擎运行时替换成实际唤醒词；
- 每条可接受说法写成 `( ... )`，**同时给「带唤醒词」和「不带唤醒词」两个入口**；
- `_SCENE_ID_ 0` 是场景号（KWS 支持多场景）；
- schema 版本串在官方库里是 `easr.kws.v1`、`easr.kws.ime.v1`。

我们的 `gen_grammar.py` 生成的结构与之**逐字段对得上**，所以自造语法文件是可行的。

### 4.3 为什么小度离线快（机制层面）

| 环节 | 云端 ASR | **EASR/KWS（小度离线）** |
|---|---|---|
| 搜索空间 | 几万汉字全量解码 | 只在你给的语法里匹配 |
| 声学模型 | 大模型 | `bds_easr_basic_model.dat` 2.2 MB + MFE-DNN 前端 |
| 结果形态 | 文本 → 还要再解析语义 | **直接返回 rule + slot**，省掉一次语义解析 |
| 网络 | 要联网、RTT 300ms+ | 全本地 |

这就是「不联网也有反应、还特别快」的真正原因：**它不是通用识别，是关键词 + 语法匹配**。

### 4.4 尚未确定的一处（必须设备在线才能定）

`ASR_PARAM_KEY_OFFLINE_ENGINE_TYPE` 的确切取值（`"KWS"` 还是 `"EASR"`，或带版本后缀），
以及 `WAK/ASR` 引擎能否在**同一个进程里先用 WAKEUP 再用 ASR**（`SDK_TYPE_ASR` 是另一个
`get_instance` 实例，理论上可以并存）。

**验证方法（设备回来后 5 分钟可出结论）**：写一个 `probe_easr`，把候选值逐个试，
引擎会明确回 `Offline engine was not properly configured` 或成功 —— 不需要猜。

## 7. 红线（别再踩）

1. **不要再用 `AudioRecord` 采集** —— AC100 HAL 给的数据是坏的，唤醒 0/3。
2. **不要取消 `tinycap` 独占** —— 原厂桌面 `vulture.app.home` 用 `VOICE_COMMUNICATION` 抢麦且永不释放。
3. **不要把提示音调长调响** —— 会压掉用户第一个字。
4. **不要再用固定 2.3 秒等待** —— 这是“慢半拍”的根因。
5. **不要试图用原厂 `MarlinSpeech` 那套** —— 唤醒词是「你好问问」，且体验差。
6. **`WAKEUP` 必须用 `ld-linux-armhf.so.3` 加载**，直接跑会失败。
