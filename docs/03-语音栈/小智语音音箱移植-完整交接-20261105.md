## 五、踩坑全记录（坑9 ~ 坑17，血泪教训）


**坑9**：`vulture.app.home`（小鱼易连会议 App，进程名 NEMO_UI）常驻独占麦克风 `pcmC0D0c`，不 force-stop 就 `AudioRecord` 读不到数据（wake-loop 卡在 poll）。

**坑10**：录音必须用 `AudioSource.VOICE_COMMUNICATION`（带 AGC），`MIC` 源只有底噪。

**坑11**：录完再传比边说边传快 4 倍。

**坑12**：`/data/local/tmp/xiaoai_token.txt` 的 access_token 3 天过期。

**坑13**：`vulture.app.home` 被 `vulture.watchdog` 反复拉回抢麦克风（"杀了又抢"死循环），且它疯狂刷 `read data error ret=-3` 日志，会冲掉我们的 logcat。**当前只能手动 force-stop，还没固化成自动脚本。**

**坑14**（本轮修）：askAudio 发送循环里每帧调 drainIncoming 会阻塞（recvFrame 默认 30s 超时），导致发送卡死。改成"先全部发完 Opus，再统一收"。

**坑15**（本轮修）：收回答阶段空等 15 秒超时，导致总延迟 19 秒。改成"收到 tts state=stop 立即结束"，延迟降到 7.7 秒。

**坑16**：TFLite 各版本对 Android 4.4 的兼容性（详见第六节）。

**坑17**：`sRunning` 是 static 标志，force-stop 后如果进程没死透，重启服务时 `if(!sRunning)` 不进入，导致 worker 不启动、没日志。彻底重启要 force-stop + 等 2 秒 + 再 startservice。

## 六、本地 KWS 唤醒（最后一块拼图）——完整调研结论

### 6.1 为什么还没上本地唤醒

官方原版 ESP32 的唤醒是**本地 KWS**（WakeNet/MultiNet，几十 KB 模型，毫秒级）。我们当前靠 AIVS 云端识别"小智"文字，要网络往返，所以慢。

### 6.2 已排除的路线（别重蹈覆辙）

**❌ sherpa-onnx**：KWS 模型已验证能识别"小智小智"（Mac 本地 100% 命中），但依赖 onnxruntime，而 onnxruntime **要求 minSdk 21+**，T70L 是 Android 4.4（API19）。所有 armv7 预编译 so 都是 `DT_GNU_HASH`（老 linker 不认），加载即崩 `empty/missing DT_HASH`。

**❌ sherpa-onnx onnx→tflite 转换**：sherpa KWS 的 encoder 模型 4423 个节点，含 `MatMulInteger`/`DynamicQuantizeLinear` 等动态量化 op + 40 个 cached 流式状态张量，TFLite 不支持，转换不可行。

**❌ TFLite 2.5+**：用了 C++ locale/宽字符函数（`wcsnrtombs`/`getpagesize`），这些是 Android 5.0+ bionic 才有的符号，T70L bionic 缺失，加载失败。

### 6.3 唯一可行路线：microWakeWord 训练 + TFLite 2.4.0

**TFLite 2.4.0** 是唯一同时满足"兼容 Android 4.4 + 能跑唤醒模型"的版本：
- `DT_HASH=11396`（老 linker 认），`DT_GNU_HASH=None`
- 不引用 getpagesize/wcsnrtombs
- 但 2.4.0 不支持流式模型的 `CALL_ONCE`/`VAR_HANDLE` op（builtin code 129 报错）

**所以必须用 microWakeWord 的 `NON_STREAM_INFERENCE` 模式**（非流式，输入完整频谱，不需要 VAR_HANDLE）。

### 6.4 训练路径（已探明，未执行完）

1. 训练框架：`$HOME/re-tools/microWakeWord`（kahrendt，Google kws_streaming 改）
2. 环境：Python 3.9 虚拟环境 `$HOME/re-tools/kws-train-venv`（TensorFlow 2.18 + numpy + scipy）
3. **关键绕坑**：`generate_features_for_clip(use_c=False)` 用 TensorFlow 自带 `audio_microfrontend_op`，**不需要编译 pymicro-features 的 C++**
4. 数据源：**用 macOS `say` 生成中文样本**（多种音色 Eddy/Flo/Meijia/Reed/Rocko/Sandy/Shelley/Tingting），不需要 piper-sample-generator
5. 训练命令：`python -m microwakeword.train`（config 在 yaml），产出 NON_STREAM 模型 → quantize → TFLite
6. 模型要求：输入 `[1, spectrogram_length, 40]` int8，输出 `[1,1]` uint8 概率

### 6.5 音频前端（microfrontend，需移植成 Java）

Google microfrontend 源码已拉全：`$HOME/re-tools/microfrontend/`

**前端管线**：16k PCM → 30ms Hann窗(480样本) → 512点FFT → mel滤波器组(40通道,125~7500Hz) → sqrt → 噪声抑制 → PCAN增益 → log缩放 → 40维特征 → int8量化

**量化公式**（mww_core.cc）：`input = (feature*256+333)/666 - 128`

**关键参数**（preprocessor_settings.h）：
- 采样率 16000，窗口 30ms，步进 10ms
- 40 通道，125~7500Hz
- 噪声抑制 smoothing_bits=10，PCAN strength=0.95

## 十、响应提速记录（16:25 本轮优化）


**已做的提速优化**：
1. 静音收尾 SIL_END 600→400ms、SIL_END_WAKE 400→300ms
2. AIVS 识别等待 live.await(3500→2000ms)
3. 切唤醒词：respondVoice() 根据 AIVS 文字比例切掉音频前段唤醒词（发 60帧→44帧）

**实测结果**：
- "一加一等于几"：7.6 秒（发送音频 2.5s + 小智云 ASR+LLM + 收回答）
- 对比 Mac 直连（发文字）：2.4 秒

**剩余慢的根源（无法再大幅优化的部分）**：
1. 发音频是小智官方协议要求（要发 Opus 音频给小智云做 ASR，不能像 Mac 直连那样发文字）
2. 天气类问题：小智云要调 get_weather 工具查实时数据，天然慢（Mac 直连也是 12 秒）
3. T70L 走 WiFi，网络延迟比 Mac 有线略高

**结论**：7~8 秒是"发音频 + 小智云一条龙"的正常水平，天气类 10+ 秒是小智云调工具的正常行为。要真正"秒回"，唯一途径是**本地 KWS 唤醒**（省掉唤醒那趟 AIVS 网络往返，唤醒从"秒级"变"毫秒级"），但问答本身（发音频→小智云→回答）的 7 秒是协议下限。

## 十一、唤醒灵敏度优化（16:30，解决"偷懒/远场听不见"）

用户反馈：连续唤醒/2-3米远距离时"偷懒不回答"，开灯关灯"偶尔执行偶尔不执行"。

**根因分析**（同一个病：VAD 灵敏度不稳定）：
1. ABS_FLOOR=120 太高，远场小声 rms 150-250 过不了门
2. SNR_MULT=1.9 阈值偏高
3. 底噪下降慢（0.997 系数），回声后阈值长期偏高
4. 播后静默期 quietUntil=600ms 太长，连续唤醒时错过
5. resetNoise 用当前 rms 起步，可能被残留回声设高

**修复（WakeService.java 参数调整）**：
- ABS_FLOOR 120→80（远场小声能触发）
- SNR_MULT 1.9→1.6（阈值更灵敏）
- NOISE_CAP 1500→800（防底噪顶爆）
- 底噪下降系数 0.997→0.992、安静跟随 0.82/0.18→0.80/0.20（更快恢复）
- quietUntil 600→400ms（连续唤醒更快恢复监听）
- resetNoise 起步值 Math.max(20,rms)→Math.min(Math.max(20,rms),100)（防回声设高）

**实测验证**：
- 底噪 90 时，阈值从 ~170 降到 ~144
- Mac 音量 40%（模拟远场小声）→ 正常触发，正确回答
- 连续唤醒两次 → 都响应

**未解决的深层问题**：handle() 里 askAudio 阻塞 7 秒期间，主循环停着不录音，这期间的喊话会漏。正常场景（等上次回答完再喊）不受影响，但"打断式连续喊话"会漏。彻底解决需把录音和问答拆成两个线程（较大重构）。

## 九、关键教训（总结）

1. **Android 4.4 是硬约束**：所有现代 ML 库（onnxruntime、TFLite 2.5+）都不兼容，只有 TFLite 2.4.0 能用。

4. **日志被刷屏**：NEMO_UI 疯狂刷日志，必须用 `logcat -s 指定tag` 过滤，否则关键日志被冲掉。

## 十二、开机自启加固（16:44，最后一块）


**根因**：
- `flash_recovery` service（→install-recovery→boot_init）只在**完整冷启动**触发
- 设备软重启（zygote/system_server 重启）不重跑 init，boot_init 不执行
- 其他自研模块靠各自守护进程 + 桌面重启连带恢复；小智靠 wake_guard，软重启后没被拉起


**注意**：还尝试过改 /init.rc 加 `service t70boot`（on property:sys.boot_completed=1 触发），但 /init.rc 在 rootfs（ramdisk），改后重启不持久，**已放弃此方案**，改用 BootReceiver（持久，打进 APK）。
