# 语音唤醒：长期唤不醒的根因与修复（2026-11-03）

> 一句话：**不是麦克风坏、不是算法错、不是增益不够 —— 是原厂桌面 `vulture.app.home`
> 常驻独占录音设备，我们的采集进程从头到尾一帧音频都没拿到。**

---

## 1. 现象与误判历史

| 症状 | 曾经的错误归因 | 实际原因 |
|---|---|---|
| 喊「小度小度」毫无反应 | 以为 DMIC 采集弱，加增益 6 倍 | 采到的是 0 字节，增益再大也没用 |
| 引擎无 WAKE | 以为唤醒词模型不对/帧率不对 | 引擎根本没收到音频 |
| 日志有 `armed, feeding...` 像正常 | 以为链路通了 | 后面紧跟 `NO_AUDIO: 10s 无数据` 才是真相 |
| 偶尔能唤醒一次 | 以为"时好时坏" | 那几次正好赶上原厂桌面还没抢到麦 |

**关键教训：`armed, feeding...` 只代表"我准备好喂了"，不代表"我真的喂进去了"。**

---

## 2. 根因证据链（2026-11-03 06:10 实测）

### 2.1 谁在占用录音设备

```
$ adb shell 'ls -l /proc/22655/fd | grep pcm'
lrwx------ media audio 33 -> /dev/snd/pcmC0D0p
lrwx------ media audio 35 -> /dev/snd/pcmC0D0c     ← 麦克风被 mediaserver 持有
```

pid 22655 = `/system/bin/mediaserver`（Android 音频服务，不能杀）。

### 2.2 谁让 mediaserver 打开录音

```
$ adb shell "dumpsys media.audio_flinger"
- Input configuration:
    Buffer     Frames  Smp rate Channels Format
    0x00000000 00960   48000    0000000c 1        ← 48kHz / 1ch / PCM16
  1 Clients:
    Pid   Priority Ctrl Locked client server
    23279 00000    1    0      00000  00000      ← 唯一客户

$ adb shell "cat /proc/23279/cmdline"
vulture.app.home                                ← 原厂桌面/家庭页
```

### 2.3 杀掉它立刻恢复

```
$ adb shell "am force-stop vulture.app.home"
$ adb shell 'ls -l /proc/22655/fd | grep pcm'
（无输出 —— 设备已释放）

$ adb shell "tinycap t2.wav -D 0 -d 0 -c 2 -r 48000 -b 16 -p 1024"
-rw-rw-rw- root root 573484 /data/local/tmp/t2.wav   ← 3 秒采到 573KB，完全正常
```

### 2.4 它会被 watchdog 拉回来，回来就重新抢

```
$ adb shell "ps | grep vulture.app.home"
u0_a33 16058 ... vulture.app.home      ← 被 vulture.watchdog 重启
$ adb shell 'ls -l /proc/22655/fd | grep pcm'
lrwx------ media audio 37 -> /dev/snd/pcmC0D0c     ← 又占上了
```

**所以 `am force-stop` 只是临时手段，用它做方案会陷入"杀了又抢"的死循环。**

---

## 3. 永久修复：改设备节点权限

```
/dev/snd/pcmC0D0c  原来是  crwxrwx---  media media
改后               crw-------  root  root
```

```sh
chown root:root /dev/snd/pcmC0D0c
chmod 600 /dev/snd/pcmC0D0c
```

**原理**：

| 进程 | 运行身份 | 改权限后 |
|---|---|---|
| `mediaserver`（原厂桌面借它录音） | `media` | **打不开**，彻底放弃 |
| 我们的 `tinycap`（duer_wake 子进程） | `root` | 正常打开 |
| 播放节点 `pcmC0D0p` | 不动 | 音乐/提示音不受影响 |

**验证（06:12 实测）**：改权限后 tinycap 采到 573484 字节/3s；等 `vulture.app.home`
被 watchdog 拉回来，它再也抢不到麦，`mediaserver` 的 fd 列表里从此没有 pcm 设备。
桌面（`com.xylink.launcher`）显示正常，未受影响。

**代价**：系统里其他需要录音的 App 从此都录不了音。对"专用智能音箱"来说这正是我们想要的。

**⚠️ 关键：`/dev` 是 tmpfs，重启后权限会重置回 `media:media`。必须每次开机重申。**
见 `speaker_guard.sh` 里的 `lock_mic()`。

## 4. 改完后立刻验证成功

```
$ adb shell "sh /data/local/tmp/duer/start_speaker5.sh"
$ # 播放一段真人「小度小度」录音
$ adb pull /data/local/tmp/duer/wake.log
armed, feeding...
mic mode ready (gain=1.00)
WAKE! status=4            ← ★ 实时通路首次稳定唤醒
ASR_NOTIFY

$ adb pull /data/local/tmp/duer/speaker.log
model ready in 7705ms
BEEP played
audio len=48000 rms=1528 peak=8356    ← 识别窗口拿到 3 秒音频，电平正常
```

**对照实验（同一天，改权限前后）**：

| 条件 | 采集 | 唤醒 |
|---|---|---|
| 改权限前（原厂桌面占麦） | 0 字节，`NO_AUDIO` | 0/N |
| 改权限后 | 573KB/3s，帧率精确 | **1/1** |
| 离线喂同一段录音（不经过麦克风） | — | 1/1（证明引擎本身没问题） |

## 6. 恢复步骤（设备重启后照这个做）

```sh
# 1) 锁麦克风（重启必做，否则原厂桌面会抢）
adb shell "chown root:root /dev/snd/pcmC0D0c; chmod 600 /dev/snd/pcmC0D0c"

# 2) 起完整链路
adb shell "sh /data/local/tmp/duer/start_speaker5.sh"

# 3) 验证（看到 lvl 行且 in 在涨 = 采集正常）
adb shell "cat /data/local/tmp/duer/wake.log"
```

或者一条命令：

```sh
adb shell "sh /data/local/tmp/duer/speaker_guard.sh once"
```

## 7. 已知问题（诚实记录）

| 问题 | 状态 | 备注 |
|---|---|---|
| 提示音「叮咚」会盖住紧跟的命令词 | **待改** | 用户连着说「小度小度开灯」时，400ms 的 beep 正好压在「开灯」上。真人按节奏说是没问题的 |
| `speaker_guard.sh` 会自己退出 | **待改** | 用 `setsid` 起的 shell 脚本存活不稳，杀进程测试时发现它没恢复。下一步改成 Java 守护线程（SpeakerService 一直很稳） |
| 开机自启未做 | **待做** | 需要在 init 层或 App 层挂一个 BOOT_COMPLETED |
| 识别窗口固定 3 秒 | 待优化 | 应该用 VAD 自适应，说来长句不会截断 |
| `wake.log` 无限增长 | 待优化 | `[lvl]` 每 16 帧一行，一天约 300KB |
