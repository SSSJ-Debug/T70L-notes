# 小度音箱（MarlinSpeech）语音栈 静态分析 分析技术档案

> 目标产物：可直接指导「移植到中移 T70L（全志 A83T / Android 4.4.4 / API 19 / armeabi-v7a）」的源码级档案
> 分析方式：**纯静态**（未接触设备、未运行 APK）
> 工具：静态分析 6.8.0（`analyze` / `decompile` / `decode-android-resources`）+ 解包工具 1.5.x + arm-linux-gnueabihf binutils（GCC 15.2 自带 `nm`/`readelf`/`objdump`）
> 日期：2026-11-02

---

## 0. 结论先行（TL;DR）


**一句话给用户**：这套语音栈是「小鱼在家（ainemo）/出门问问（Mobvoi）」的 Kaldi 离线识别 + LSTM 唤醒组合，`lib/*.so` 全部是 ARMv7+NEON、GCC 4.8 编译、无任何授权校验的普通 ELF，**在 T70L（A83T，Cortex-A7 带 NEON，API 19）上可以原样跑**；真正的移植工作量不在二进制，而在①补上"谁给唤醒服务喂 PCM"、②绕开"模型必须解包到外置存储"这两处工程缺口。

### 1.2 地址约定（全文统一）

* `nm -D` 输出的是**文件偏移**；静态分析工具 中看到的是**加载地址**。
* 本档案统一写作 `so@加载地址（文件偏移 xxx）`，换算关系：**加载地址 = 文件偏移 + 0x10000**（8 个库的 `image_base` 均为 `0x10000`，见 `rea analyze` → `normalized_result.image_base`）。
* 例：`libwakeup.so@0x3f3bc（文件偏移 0x2f3bc）= Java_..._Wakeuper_initNative`。

| `lstm/threshold.npy` | (1,) | `<f4` | **4** | **阈值 = 0.40000000596**（`0x3ecccccd`） |
| `mfcc_filter_bank.npy` | (40, 257) | `<f8` | 82,240 | **40 个 mel 三角滤波器 × 257 个频点**（512 点 FFT 的 r2c 半谱） |

**由此可确定的四条硬事实**：

1. **FFT 是 512 点**：mel 滤波器只有 257 个频点 = 512/2+1，与 4.3 里 `fftwf_plan_dft_r2c_1d(0x200, …)` 互证。
2. **特征是 40 维 log-mel，10 帧拼接 = 400 维**：`w1` 的第一维 400 = 10×40，且 `mfcc_filter_bank` 正好 40 个滤波器。
3. **输出是 3 维而不是 1 维**：`w5`/`proj_weight` 都是 3 列，说明这个模型**同时带 3 个关键词/3 个状态位**（典型 Mobvoi 设计：`{静音, 唤醒词, 非唤醒语音}` 或 3 个候选唤醒词）。`checkWakeup` 里的 `score * 0.25` 与"取均值"逻辑对应第 2 类（唤醒）那一路。
4. **`nn/`（MLP）与 `lstm/` 是两套可切换的模型**，由 `IWakeuper.LSTM_TYPE = "lstm"` 选择（`WakeupFactory.java:17`）；`nn/` 目录是 MLP 版本的兜底权重。**本机实际加载的是 `lstm/`**。

> 这两组权重合计 ~0.5 MB，全部 float32 明文存放，**没有加密、没有 license 绑定**。想换唤醒词，理论上可以用自定义数据重训同形状网络后直接替换这 15 个 `.npy`（`libwakeup` 用 cnpy 读，不校验哈希）——这是"换唤醒词"最干净的路径，比 patch `.so` 现实得多。

### 5.4 两者的"配合"（**已验证**）

* **不叠加**：`libwakeup` 在独立进程/Service 常驻；`libhotword` 在识别会话内起停。二者无共享状态。
* **接力关系**：典型产品逻辑是 `libwakeup` 命中 → 打开 ASR 会话 →（可选）`libhotword` 在会话里做"二次唤醒/打断"。
* **在 MarlinSpeech 里这条接力没接上**：`XYWakeupService` 只是把 `onResult` 广播给 Binder 客户端，**客户端负责**去 `bindService(AsrService)`。MarlinSpeech 内部没有 "wakeup→asr" 的自动串联代码。
* **`libhotword` 这条"会话内二次唤醒"也没接上**：它的开关 `SpeechClient.startHotword()`（`SpeechClient.java:223`）全 APK 零调用。也就是说产品上设计了两级唤醒，实际只启用了第一级。

#### 6.3.3 状态机：4 个状态 + 4 个位图窗口（**机制已验证，语义部分为推测**）

`Segmenter` 内部用 **4 个"位图环形窗"** 而不是队列：每个窗口是一个 `vector<uint32_t>`，一位一帧；`SetBitAndUpdatePos` / `ClearBitAndUpdatePos` 写当前位并推进；统计时对整块做 **SWAR popcount**（`- (x>>1 & 0x55555555)` 那一串，被 NEON 向量化成 `VectorSub/VectorAdd`）。

窗口长度在 `Segmenter::UpdateInternalBitmap`（`@0x46b24`）里 4 次调用 `CreateWindowBitmap(len, ratio, &pos)` 生成，`ratio` 恒为 `kEffectiveWindowRatio = 0.9f`（`@0xc0674`，`0x3f666666`）：

| 位图 | 长度参数 | 实际窗口（÷0.9） | 记什么 | 依据 |
|------|----------|------------------|--------|------|
| #1 `this+0x04` | `0x28 + 0x30` = 50+50 = **100** | **111 帧** | **静音**帧 | `UpdateInternalBitmap` 第 1 次调用 |
| #2 `this+0x0c` | `0x2c + 0x30` = 150+50 = **200** | **222 帧** | **静音**帧（长窗） | 第 2 次调用 |
| #3 `this+0x14` | `0x30` = **50** | **55 帧** | **静音**帧（短窗） | 第 3 次调用 |
| #4 `this+0x1c` | 硬编码 **0x32 = 50**（= `kSteadySpeechThreshold`） | **55 帧** | **语音**帧 | 第 4 次调用 + `kSteadySpeechThreshold@0xc0670 = 50` |

**每帧的窗口更新**（`Segmenter::UpdateSmoothingWindow(int is_speech)`，`@0x45e28`，**完整解析**）：

```c
if (is_speech != 1) {                 // 非语音帧
    this->speech_run  = 0;            // +0x4c 连续语音帧计数清零
    this->frame_cnt++;                // +0x50 总帧计数
    SetBit(#1); SetBit(#2); SetBit(#3);   // 静音窗置 1
    ClearBit(#4);                          // 语音窗置 0
    this->prev = is_speech;           // +0x54
} else {                              // 语音帧
    if (this->prev == 1) { this->speech_run++; this->frame_cnt++; }
    else                 { this->speech_run = 0; this->frame_cnt++; }
    ClearBit(#1); ClearBit(#2); ClearBit(#3);
    SetBit(#4);
    this->prev = 1;
}
```

**状态迁移**（`Segmenter::UpdateState`，`@0x4514c`，27 KB 解析；状态存于 `this+0x44`，初值 0）：

| 当前状态 | 判据 | 迁移 | 备注 |
|----------|------|------|------|
| 0 | `speech_threshold(3) <= 静音累计` 且 `frame_cnt - saved < snr_threshold` | → 2 | 见 caseD_0 尾部 |
| 1 | 若 `speech_run < short_speech_threshold(3)`：数 **#2 长窗**静音数，`< short_pause_threshold + speech_threshold = 200` → **保持 1**；否则 → **0** | 1→0 | 短语音不打断 |
| 1 | 若 `speech_run >= short_speech_threshold(3)` | → 2（`LAB_45548`） | 长语音走另一条 |
| 2 | 数 **#3 短窗**静音数，`< speech_threshold(50)` → 保持；`>= 50` → **1** | 2→1 | 短窗"够静"才继续 |
| 3 | 数 **#1 窗**，`>= short_speech_silence_threshold + speech_threshold = 100` → **0** | 3→0 | — |
| 其他 | — | 打日志 `"ERROR: IMPOSSIBLE STATE!"` 并返回 | 字符串实证 |

`Segmenter::ProcessDecision(int frame)`（`@0x45ec8`）= 三步：

```c

```

### 9.4 结论

> **这 8 个 `.so` 可以在 T70L 上原样加载并运行，不需要重新编译，也不需要 key/授权。**
> 真正的移植缺口只有两处，且都在 Java/系统层，不在二进制里：
> ① **唤醒音频源**——`XYWakeupService` 只收 Binder 推送，MarlinSpeech 里没有"谁去开麦克风"的代码，需要移植方自己补一个录音循环（或复用 `speech.ak`）；
> ② **模型落盘位置**——默认硬编码到外置存储根目录，T70L 若 `/mnt/sdcard` 异常会让离线识别直接崩，需要改工作目录（已有现成参数口子）。
>
> 附加建议：**可删** `LingxiRecognizer` + `assets/ivw/speech_engine.jet`（49 KB，讯飞 IVW 唤醒资源，零引用）。**不要动** `libmsc.so` + `assets/tts/*.jet`——它们是 `TtsService` 的离线 TTS 引擎（见 9.6），删掉等于砍掉 TTS。

### 9.5 性能风险（**推测（待验证）**，需实机）

## 12. 移植到 T70L 的分步方案

### 12.0 目标定义（先定边界，避免过度工程）

| 目标 | 需要保留的组件 | 磁盘 | 内存 |
|------|----------------|------|------|
| **A. 只要唤醒** | `libwakeup` + `assets/{nn,lstm,mfcc_filter_bank.npy}` + `XYWakeupService` + `WakeupFactory/Wakeuper` | ~2.1 MB | ~20 MB |
| **B. 唤醒 + 离线命令词** | A + `libmobvoi_recognizer` + `res/raw/model` + `libmobvoi_vad` + `speech/*`（词表/语法） | ~14 MB | ~100 MB |
| **C. 全套（唤醒+识别+语义+TTS）** | B + `libtts` + `config/*` + `UnderstandService/TtsService` | ~42 MB | ~150 MB |

> 建议：**先做 A（1 天可验证），再决定要不要 B/C**。T70L 是 A83T（4 核 A7 @1.0-1.2 GHz / 1 GB RAM 级别），跑 C 有内存压力。

**Phase 1 的关键实现片段**（照抄即可）：

```java
// 1) 绑定
Intent i = new Intent("com.ainemo.speech.intent.action.service.wakeup");
i.setPackage("com.ainemo.speech.app");
bindService(i, conn, BIND_AUTO_CREATE);
// conn.onServiceConnected → ISpeechWakeup.Stub.asInterface(binder)

// 2) 启动
wakeup.startListening(listener);
wakeup.setParameter("key", "val");   // 注意：服务端是空实现，别指望生效

// 3) 喂音频（线程内循环）
AudioRecord ar = new AudioRecord(MediaRecorder.AudioSource.VOICE_RECOGNITION,
                                 16000, AudioFormat.CHANNEL_IN_MONO,
                                 AudioFormat.ENCODING_PCM_16BIT, 256000);
ar.startRecording();
byte[] buf = new byte[320];          // 10 ms，与官方一致
while (running) {
    int n = ar.read(buf, 0, buf.length);
    if (n > 0) wakeup.writeAudio(buf, n);   // 任意长度都行，native 内部攒 800 B
}
```

> 若 Phase 1 失败，按此顺序排查：① `CHECK_MODEL nn/w1.npy fail!` → assets 没打进去；② `AAssetManager is NULL` → 传了错的 AssetManager；③ `fail to find method onWakeup` → 类名被改/被混淆；④ 无任何日志 → `putDataNative` 没被调用（Binder 没通）。

## 14. 给用户的三个关键发现（一句话版）
