## 1. 唤醒链路的完整调用序列（源码级复原）

`wakeup_config()` 解析后等价于下面这段 C（函数名、参数键均来自二进制的真实符号）：

```c
void wakeup_config(BDSpeechSDK *SDK)
{
    BDSSDKMessage msg;
    msg.name = WAK_CMD_CONFIG;                       // "wak.config"

    msg.set_parameter(COMMON_PARAM_KEY_DEBUG_LOG_LEVEL, 0);
    msg.set_parameter(WP_PARAM_KEY_ENABLE_DNN_WAKEUP,   1);   // 关键：DNN 唤醒
    msg.set_parameter(OFFLINE_PARAM_KEY_LICENSE_FILE_PATH,
                     "resources/bds_license.dat");
    msg.set_parameter(WP_PARAM_KEY_WAKEUP_WORDS,
                     "{\"words\":[\"小度小度\"]}");        // 唤醒词是 JSON
    msg.set_parameter(WP_PARAM_KEY_WAKEUP_DAT_FILE_PATH,
                     "resources/end2end_wakeup_far.dat");  // 远场 DNN 模型

    if (SDK->sendMessage(&msg, &errorMsg) == 0)
        fail();                       // 打印 "failed send config message"

    printf("Sending load command...\n");
    BDSSDKMessage loadEngine;
    loadEngine.name = WAK_CMD_LOAD_ENGINE;            // "wak.load"
    if (SDK->sendMessage(&loadEngine, &err) != 0)
        fail();                       // 打印 "failed send load message"
}
```

主程序流程（与 `wakeup.js` 交叉验证）：

```
wakeup_init()      → 建 wakeup_output_fifo，打印 "fifo open ok"
wakeup_config()    → wak.config（license / DNN / 唤醒词 / 模型）+ wak.load
wakeup_start()     → wak.start      （进入待命，可开始收音频）
wakeup_pushaudio() → wak.push_audio  （每次一包 PCM）
回调               → cb.wak.status.int == 4 表示唤醒，cb.wak.result.string 是命中的词
```

`wakeup_pushaudio` 的解析结果是个测试壳：

```c
void wakeup_pushaudio(BDSpeechSDK *SDK) {
    pushAudio("resources/test_audio/xiaoduxiaodu.pcm",
              &WAK_CMD_PUSH_AUDIO, SDK);
}
```

—— 它证明引擎自带离线自测入口，且样本格式就是 **16 kHz / 单声道 / S16_LE**。

```

```

## 4. 为什么小度的唤醒「秒回」——机制层面

**观察**：

1. 唤醒判定由 `bds` 的 WAK 模块 + `end2end_wakeup_far.dat` 完成，`enable_dnn_wakeup=1`。
   这是**端到端 DNN**，不是「先 VAD 再识别关键词」，而是每帧直接输出「是否唤醒 + 哪个词」。
2. 引擎是本地进程，音频从 FIFO 直接进，**全程不联网**（license 也是本地文件校验，
   启动日志 `WAKED_LICENSE: 0` 即通过）。
3. 唤醒词来自配置 JSON，`decode_wakeup_words()` 把它解析成 `vector<string>`。
4. 状态机：加载完成时 `cb.wak.status.int == 2`，唤醒时 `== 4`。

**推断**：所谓「反应超级快」= 本地 DNN 持续推理 + 无网络往返 + 无需先做完整 ASR。
延迟主要是「凑够一帧上下文」的时间（数百毫秒），与云端方案不在一个量级。

**未知**：DNN 内部结构、门限灵敏度参数（本轮未定位到对外暴露的灵敏度键）；
T70L 上实际推理耗时未做基准测试。

## 5. 对移植的意义（结论）

- 唤醒词**不是写死的**，改 `WP_PARAM_KEY_WAKEUP_WORDS` 的 JSON 即可换词、加词（多词表）。
  这意味着「小度小度」可以原样保留，也可以同时挂「小X小X」等多个词。
- 输入格式确定：**16 kHz / mono / S16_LE**，chunk 大小不敏感（JS 侧就是透传）。
- 引擎与上层只靠 FIFO + 上述二进制协议通信，**可以完全脱离原厂 node.js 外壳**独立运行。
- 因此 T70L 的移植路径成立：本地引擎 + 本地麦克风 + 本地动作执行，无需小度账号、无需联网。

## 6. 移植到 T70L 时踩到的真实坑（已解决，务必保留）

| 现象 | 真因 |
|---|---|
| 引擎永远不醒，`-120 dB` 数字静音 | 厂商会议 App 停止后，mixer 把 `ADC Mux` 从 DMIC 切回模拟 ADC；且 codec 增益改了要重开流才生效 |
| 采到的是恒定底噪 | 裸 ALSA `tinycap` 打开的是 `vir-dai` 虚拟设备（`-d 2`），不是麦克风（`-d 0`） |
| 有声音但引擎不认 | HAL 实际输出是 `[L,L,R,R]` 四值一帧（48000 帧/s × 2ch × 2 次重复），当成单声道会把采样率算成 4 倍，语音严重快放 |
| 电平看着够但不醒 | codec 输出带约 1600 LSB 直流偏置，乘增益后顶到天花板被削平 —— 必须先高通去直流 |
| 与厂商 App 抢麦 | `pcm0c` 单 subdevice，独占；必须 `pm disable vulture.app.home` |

**验证方法（可复现）**：把官方样本按 `[L,L,R,R]` 合成为 48k 流，走完全相同的
「高通 → 25 阶 FIR(fc=7k) → 3 倍抽取 → 320 点定长帧」通路，引擎输出 `WAKE! status=4`。
