## 二、麦克风链路（逐级还原）

### 2.1 硬件层：只有 DMIC，模拟麦通路是断开的

完整 mixer 表 115 个控件，麦克风相关的实际状态：

```
26  ENUM  ADCR Mux                       DMIC      ← 右声道选数字麦
27  ENUM  ADCL Mux                       DMIC      ← 左声道选数字麦
 9  INT   ADC volume                     202 202
13  INT   ADC input gain                 4 4
14  INT   MIC1 boost amplifier gain      4         ← 模拟麦增益，但下面全关
15  INT   MIC2 boost amplifier gain      4
33  BOOL  RIGHT ADC input Mixer MIC1 boost Switch   Off
34  BOOL  RIGHT ADC input Mixer MIC2 boost Switch   Off
40  BOOL  LEFT  ADC input Mixer MIC1 boost Switch   Off
41  BOOL  LEFT  ADC input Mixer MIC2 boost Switch   Off
 92 BOOL  AIF1 AD0R Mixer AIF2 DACR Switch          Off
 94 BOOL  AIF1 AD0R Mixer ADCR Switch               On   ← 数字麦进 I2S 右
 98 BOOL  AIF1 AD0L Mixer ADCL Switch               On   ← 数字麦进 I2S 左
```

**结论**：板上有 MIC1/MIC2 的 boost 放大器（模拟麦输入），但**四路 boost 开关全部 Off**，实际只走 DMIC。这是之前"厂商 App 一被 force-stop，采集就变成 rms≈3 的静音"的根本原因——一旦软件把 ADCL/ADCR Mux 掉回默认，采到的就是没有接麦的模拟输入。

### 2.2 配置层：`libcodec_audio.so` 内的 `codec_in_config`

从 `.data` 段（VA 0xa14c → 文件偏移 0x914c）直接读出：

```
codec_in_config  (录音)
  +00 = 1        channels = 1          ← 单声道
  +04 = 44100    rate = 44100
  +08 = 1024     period_size
  +0c = 4        period_count
  +28 = 1        （第二组 stream 配置起始）
  +2c = 44100

codec_out_config (放音)
  +00 = 1 / +04 = 44100 / +08 = 1024 / +0c = 4
  +2c = 8000     ← 第二组为 8kHz（通话/提示音）
```

**关键点**：DMIC 物理上有 L/R 两路，但 HAL **按 channels=1 单声道** 采集。也就是说系统层面没有把双麦数据分别取出来，不存在软件波束成形的前提条件。

### 2.3 HAL 层：`audio.primary.octopus.so` 的路由表

导出数据符号（`.data.rel.ro`，VA 0x116c94）：

```
cap_normal_route_configs            0x116c50
normal_route_configs                0x116c5c
cap_phone_normal_route_configs      0x116c78
dmic_cap_normal_route_configs       0x116c94   ← DMIC 录音路由入口
ringtone_route_configs              0x116ca0
```

这些是**指针数组**，指向路由配置文件名字符串（`.rodata` 0x10ad40 起）：

```
media-digital-mic        ← 媒体数字麦
media-main-mic
media-headset-mic
media-speaker
media-single-speaker
analog-phone-speaker / -headset / -headphone / -bt / -earpiece
digital-phone-speaker / -headset / -headphone / -bt / -earpiece
abb-phone-keytone-speaker / -headphones / -bt / -earpiece
phone-ring-voice
```

HAL 通过 Android 标准 `audio_route_apply_path()` 按名字应用路径，控件名靠 `libcodec_audio.so` 的 `mixer_ctl_set_enum_by_string()` 下发。

**⚠ 发现一个严重缺失**：HAL 引用了两个配置文件，但**系统里都不存在**：

```
/system/etc/ac100_paths.xml     ← 全盘 find 无结果
/system/etc/phone_volume.conf   ← 全盘 find 无结果
```

这意味着 `audio_route_apply_path()` 全部落空，路由实际上没有 XML 定义可用，只能靠默认值 + 上层代码兜底。这解释了为什么 mixer 状态如此脆弱、为什么必须手工 `tinymix` 兜底。

### 2.4 前处理层：`libwebrtc_audio_preprocessing.so`

版本字符串与算法集合（**全部内容，无遗漏**）：

```
AEC  2.5.0     WebRtcAec_*      （48k 重采样版回声消除）
AECM 1.2.0     WebRtcAecm_*     （移动版，16k）
AGC  1.7.0
VAD  1.2.0
```

搜索 `beamform` / `array` / `delay-and-sum` / `mic array` —— **零命中**。

**结论：这套固件里没有麦克风阵列处理，没有波束成形，没有方向估计。** 前处理只有单通道的 AEC / AGC / VAD。

### 2.5 8 米拾音的真相

结合 `WAKEUP` 的资源清单：

```
resources/end2end_wakeup_far.dat        7,014,404   ← "far" = 远场端到端 DNN
resources/end2end_wakeup_far_fast.dat   3,817,252
resources/hmm_wakeup_far.dat            1,463,902
resources/bds_easr_dnn_wakeup_model.dat   884,670
```

官方宣称的 8 米拾音 = **远场 DNN 模型的泛化能力** + DMIC 高灵敏度 + 单通道 AGC，**不是硬件阵列 / 波束成形**。这一点决定了我们的移植上限：只要把同样的远场模型喂上干净的音频，理论上就能复现官方距离；反之，靠加麦克风或改阵列增益都没有意义。

## 三、扬声器链路

```
DAC volume                = 160
digital volume            = 0        （该 codec 中 0 表示 0dB，非静音）
Left  Output Mixer DACL Switch = On
Right Output Mixer DACR Switch = On
SPK_L Mux = MIXEL Switch
SPK_R Mux = MIXER Switch
speaker volume = 26      ← 当前实际值
earpiece volume = 30
headphone volume = 59
line out volume = 3
MIC1/MIC2 boost → L_R outp mixer gain = 3（未启用）
```

链路：`I2S DAC → Output Mixer(DACL/DACR) → SPK_L/SPK_R Mux → 外部功放 → 喇叭`。
`SPK_L/R Mux` 指向 `MIXEL/MIXER`（混音器输出），说明功放输入取自 mixer 而非直连 DAC。

`codec_out_config` 有两组：44.1kHz（媒体）与 8kHz（通话/提示音），所以提示音与媒体播放走的是不同的采样配置。

## 四、发现的两个实际问题

### 4.1 PCM 持续 XRUN（音频丢帧）

`dmesg` 中反复出现，且持续到最近（系统 uptime 3615s，最后一条在 3293s）：

```
xrun: snd_pcm_update_state, l:297
snd_pcm_lib_read1, SNDRV_PCM_STATE_XRUN
```

含义：**读端来不及取数据，环形缓冲溢出，音频帧被丢弃**。分布在高频段（同一秒内多次），说明不是偶发。

影响：任何依赖连续音频的处理（DNN 唤醒、命令词识别）都会被断帧破坏。这是识别不稳定最可能的隐藏原因之一，优先级应高于继续调参。

可能原因：录音线程优先级不足、period 1024×4 的缓冲余量偏小、或两条 AudioRecord 竞争（厂商 App 共存时会抽帧 65%，已实测）。

### 4.2 路由配置缺失

见 2.3，`ac100_paths.xml` 与 `phone_volume.conf` 均不存在于本固件。系统靠默认值运行，属于厂商裁剪产物。

## 五、对当前方案的直接影响

1. **不要指望双麦/阵列**：硬件与固件都没有这条能力，任何"提升远场灵敏度"的方案只能走 DNN 模型与增益链。
2. **必须自建 mixer 兜底**：路由 XML 缺失，`ADCL/ADCR Mux` 会随厂商 App 的启停漂移，这是反复采到静音的直接原因。启动脚本里的四条 `tinymix` 是必需的，不是可选优化。
3. **优先解决 XRUN**：断帧对 DNN 的破坏比增益不当更致命。
4. **电平工作点已标定**：`ADC volume 202 / input gain 4` 对应 rms 500~700，与官方运行态一致；195/4 会低到 60（几乎静音），230/6 会高到 3300（底噪淹没语音）。该 codec 的音量档位是非线性的，不能线性外推。

- 外部功放的 GPIO 使能脚未确认（`SPK_L/R Mux` 之后到喇叭之间）。
- 电源键按用户要求**未做任何改动**。已查明物理源为 `/dev/input/event0`（`axp81x-supplyer`，仅 system_server 持有），改动点在 services.jar，风险高，暂不动。
