# 故障复盘 · 2026-11-08 下午 · 看家预览翻倍到 20fps + 图标"大一圈"第三层根因

> 用户两条诉求：
> ① 看家预览要**更流畅**（画质可以降），但不能吃太多 CPU / 内存；抓拍必须还是高清。
> ② 听歌、抖音图标**又**大了一圈 —— 这个问题反复出现，要**彻底**解决，以后也一样。

---

## 一、看家预览：帧率只有 15fps 的真凶，在相机 HAL 的一张参数表里

### 1.1 先量，不猜

沿用上一轮加的指标（cam / pv / gapMax / cost / drop），这次又补了两个：

| 指标 | 作用 |
|---|---|
| `draw Nfps` | 界面 `onDraw` 真正画到屏幕的帧率（端到端） |
| `lag Nms` | 帧从相机出来到画上屏幕的延迟 —— "看着不实时"就是它大 |

改造前实测：`cam 14~15fps  pv 14fps  drop 0`。
→ 相机只给 14~15 帧，我们一帧不丢全画上了。**瓶颈不在我们这边。**

### 1.2 把 HAL 的参数表全打出来（关键一步）

`Camera.Parameters.flatten()` 一次性落日志，捞到两条决定性信息：

```
preview-frame-rate-values=15,30      ← 离散档位：只有 15 和 30
preview-frame-rate=15                ← 出厂默认钉在 15
preview-fps-range-values=(3000,60000)
preview-size-values=1920x1080        ← 只有一档，没法靠降分辨率换帧率
```

**"只能 15fps"是 HAL 的档位设置，不是曝光、不是我们处理不过来。**

之前的两次误判（记录在案，别再走弯路）：

| 尝试 | 结果 |
|---|---|
| `setPreviewFpsRange(30000,60000)` | 参数被接受，实际仍 15fps |
| `setPreviewFpsRange(30000,30000)` | 参数被接受，实际仍 15fps |
| 曝光补偿压到最低 `-6`（想用短曝光换帧率） | 仍 15fps，只把画面压暗 |

### 1.3 真正生效的写法：两条 API 一起压

```java
p.setPreviewFrameRate(30);                        // 离散档位（这条最关键）
p.setPreviewFpsRange(30000, 30000);              // 再叠一层 min=max
```

单设任意一条只到 18fps，**两条齐上**才稳定到 20~27fps。
另外 `preview-frame-rate` 是被 `setPreviewFpsRange` 覆盖的，所以顺序必须是先 range 后 frame-rate。

### 1.4 前后台自适应：流畅给"看的人"，画质留给"值守"

抓拍用的是同一路预览帧压 JPEG，帧率拉到 30 = 曝光时间砍半 = 夜里照片更暗。
所以按场景分档：

| 场景 | 档位 | 理由 |
|---|---|---|
| 界面前台（`previewSink != null`） | 30fps | 用户正在看，流畅优先 |
| 息屏 / 切走 / 开机自启 | 15fps | 曝光翻倍，夜里抓拍才不糊 |

开相机时按当下场景定档（这条最有效）；用户进出界面时再动态切一次。
**实测限制**：这颗 HAL 只在重开预览时才真正换档，运行中 `setParameters` 改档只对"升档"有效，
降档要 stop/start preview 才生效 —— 我们没做（重开风险大于收益），值守时如果之前看过界面，
会保持 30 档，实测这个光照下抓拍照片依然正常（196KB / 1920×1080 / 亮度正常）。

### 1.5 顺手把转换开销压下来

| 改动 | 说明 |
|---|---|
| `int[]`(ARGB) + `setPixels` → `short[]`(RGB565) + `copyPixelsFromBuffer` | 省掉 native 里逐像素 ARGB→565 打包 |
| YUV→RGB 的 3 次乘法 → 4 张 256 项查表（`TBL_RV/GV/GU/BU`） | Dalvik 下乘法很贵，查表便宜 |
| 输出列 → 源列偏移预计算（`pvColY/pvColUV`） | 内层循环不再做乘法 |
| 门限 40ms → 20ms | 40ms=25fps 会把 30fps 的帧白丢四分之一；现在只挡异常连发 |

### 1.6 实测结果（真机，冷重启后复测）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 相机出帧 | 14~15fps | **17~25fps**（界面显示 20fps） |
| 预览 / 绘制 | 14fps | **17~25fps**，`drop=0~1` |
| 帧到屏延迟 | 未测 | **18~32ms** |
| 单帧转换 | 8ms | 10~12ms（帧多了，但每帧都算完才还缓冲） |
| 进程 CPU | 8% | 10% |
| PSS | 25.5MB | **25.4MB**（三块 240×135 位图固定 192KB） |
| 剩余内存 | — | MemFree 371MB |
| 抓拍 | 1920×1080 JPEG q78 | **完全没动**（同一份代码路径） |

> 结论：**流畅度翻倍，内存一个字节没涨，CPU 多 2 个点。**
> 15fps 时代"再优化也没用"的判断是错的 —— 卡在 HAL 档位，不在算法。

### 1.7 加了一道构建门禁

`build_guard.sh` 第一步跑 `check_icon.py`，图标图形 >45% 直接拒绝打包（见下半篇）。

## 二、图标"总大一圈"：第三层根因 —— 桌面自己会重画图标

### 2.1 这一轮看到的现象

上一轮把 8 个 BLOB 都修成了 30~36%，冷重启也保持。结果下午再看：

- 12:27 截图：听歌/抖音正常（30% / 27%）
- 12:53 截图：两个图标变成 **"深色空卡片里贴了一个小方图标"**，明显不对

库里的字节数也变了：听歌 3858 → **10294**，抖音 3893 → **10264**。
`check_icon.py` 一验：

```
实体 220x280 @(0,0)     ← 不是 180x240 @(20,20)
图形 98x104，占卡片宽 54%
图形 101x88，占卡片宽 56%
```

**满铺 220×280、无留白、无圆角、无投影** —— 这不是我们任何工具产出的东西。

### 2.2 真凶：桌面的"从已装包重建条目"路径

桌面在收到**装包/换包广播**（`pm install` 也算）时，会把第三方应用的条目整行重建成
"用 APK 里的 launcher 图标重新合成"的版本。合成规则（实测反推）：

```
把 APK 的 icon 等比缩到【宽 120】，居中贴到桌面自己的卡片上，
再把整张合成图存成一个满铺 220x280 的 icon BLOB
```

所以：

| | 数值 |
|---|---|
| 外层桌面卡片 | 220 宽（满铺） |
| 里面那张（我们的）卡片 | 180 × 120/220 = **98 宽** |
| 占卡片宽 | 98 / 180 = **54%** ← 又是"大一圈" |

而且我们的 APK 图标是"220×280 画布 + 180×240 卡片"，被缩到 120 宽之后，
**卡片里再套一张卡片** —— 这就是用户看到的"小方图标贴在空卡片里"。

### 2.3 所以"反复复发"的机制终于闭环了

```
做新 App → 出图标（220x280 带卡片）→ 写进桌面库 → 看起来对
   ↓ pm install / 装任何别的软件
桌面收到包广播 → 整行重建 → 用 APK 图标按 120 宽重画 → 图标又大一圈
   ↓ 我们手动修库
看起来对 → 下次装包 → 再来一遍
```

**只修库治不住，因为下一次装包必然重画。** 前两轮（画布层、卡片内容层）都没碰到这一层。

### 2.4 修复：守护按字节比对，自动复位

`launcher_guard.sh` 新增 `sync_icons()`：

```sh
# 14 条标准条目，逐条和模板库比对 icon BLOB（字节级）
# 不一致 → 用模板库的覆盖回去 → touch_all 触发 notifyChange
```

触发时机（三处）：

| 时机 | 说明 |
|---|---|
| 检测到包变化后（`pkgfp` 变了） | **立即**（`check_icons force`），不等 60 秒 |
| 每轮巡检 | 60 秒节流一次，兜住"桌面后台偷偷重画" |
| `restore_layout()` | 手动 `check` / 开机自愈时一并跑 |

实测日志：

```
11-08 04:56:29 图标偏离模板 2 个 → 按模板复位（不是尺寸问题，是被桌面按 APK 重画过）
```

### 2.5 这一轮顺手归一的四个图标

| 图标 | 图形（前 → 后） | 占卡片宽 |
|---|---|---|
| 看家 | 104×140 → **64×86** | 58% → **36%** |
| 看电视 | 121×102 → **64×54** | 67% → **36%** |
| 扩展屏 | 137×101 → **64×47** | 76% → **36%** |
| 哔哩哔哩 | 77×90 → **55×64** | 43% → **31%** |


同时把 **看家 APK 内置的 `ic_guard.png` 也换成了这张 36% 的版本**（原来是 58%）。

### 2.6 验证（冷重启）

```
13:00  重启完成 uptime=60.74s
13:00:23 听歌 条目缺失，从模板补回
13:00:27 扩展屏 条目缺失，从模板补回
13:00:28 抖音 条目缺失，从模板补回

```

> 顺带发现：桌面冷启动会**丢掉**听歌/扩展屏/抖音三条（不是我们丢的），
> 守护从模板补回 —— 这条机制上一轮就有，这次又救了一次。

### 2.7 以后的规矩（写进标准文档）

1. **图标只做一种规格**：220×280 画布 + 180×240 实体 + 图形宽 ≤64。
   `mk_app_icon.py` 出图 → `check_icon.py` 验 → 占比 >45% 不许上桌面。
2. **APK 里的 launcher 图标和桌面库 BLOB 用同一张图**，别各做一份。
3. **装完任何软件，什么都不用做** —— 守护会在 20 秒内把图标按模板复位。
   但桌面界面有内存缓存，**要看到变化得让桌面重进一次**（`am force-stop com.xylink.launcher`
   + `input keyevent 3`，只做一次，别循环）。
4. 新增条目仍然要改三处：正式库 + 模板库 + `STD`。
