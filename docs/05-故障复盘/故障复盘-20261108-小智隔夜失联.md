# 故障复盘 · 小智「隔夜失联」（2026-11-08）

> 一句话：**T70L 全机只有一路录音通道，原厂 `vulture.app.home` 抢走后永不释放；
> 而小智这边把「录音启动失败」当成了「麦克风就绪」，于是"服务活着、日志漂亮、喊它没反应"。**
> 另有第二根病灶：WebSocket 从不发心跳，NAT 把连接静默回收，「早上第一句」必然发进黑洞。

---

## 一、现象（用户主诉）

> 「长时间不用，比如晚上让它关灯，清早起来小智就彻底失联了，怎么喊都不吱声。
> 只要 T70 开机，24 小时里"小智开灯/关灯"无论如何必须可用。」

## 二、证据链（08:57 现场）

### 2.1 麦克风被原厂独占

```
$ dumpsys media.audio_flinger
Input thread 0xb75d1e38 tracks
Client Fmt Chn mask Session S   Server fCount
   804   1 0000000C      11 6 59EB9B40   3840     ← vulture.app.home 正在录（S=6），带 AEC 效果链
                                                standby: 0（从不休眠）
Input thread 0xb7761ca0 internals
No active record client                          ← 小智这条输入线程是空的
  1207   1 0000000C   20960 0 00000000  16384     ← S=0，压根没开起来
```

- `804` = `vulture.app.home`（原厂 Nemo/XYlink 主程序，带 `.speech.activity.SpeechActivity`）
- `1207` = `com.lm.xiaozhi`
- Android 4.4 全局只允许 **一个** 录音客户端，**先到先得**，抢到就独占

### 2.2 小智在"假装成功"

系统日志每 3 秒一组，连续 1737 次：

```
W/Xz: 麦克风 2.5 秒没数据，重开录音
V/AudioFlinger: closeInput() 20902 ...
V/AudioFlinger: openInput() created record thread: ID 20905
W/AudioPolicyManagerBase: startInput() input 20905 failed: other input already started..
E/AudioRecord( 1207): start() status -38        ← -38 = INVALID_OPERATION
I/Xz: 麦克风就绪                                ← ★ 还是打了"就绪"
```

`xz.log` 里 87 分钟内 `麦克风 2.5 秒没数据` 出现 **1737 次**。

根因在代码：

```java
// 旧代码 openRec()
rec.startRecording();          // 返回 void，失败只在系统日志里报
rec.read(junk, 0, CHUNK);      // 返回值 -38 没人看
rec.read(junk, 0, CHUNK);
L.i(TAG, "麦克风就绪");         // 无条件打日志
return true;                   // 无条件报成功
```

→ 主循环以为成功 → `read()` 一直返回负数 → 看门狗 2.5 秒判一次"没数据" → 重开 → 再失败。
无限循环，而且**旧 AudioRecord 对象没 release**，AudioFlinger 里 client 越堆越多（日志里
`Unable to retrieve AudioRecord object, can't record`）。

### 2.3 一踢就好（决定性实验）

```
$ am force-stop vulture.app.home     # 只踢原厂这一个 app
（6 秒后）
Input thread tracks: 15576 ... Session 21030 S 6   ← 小智立刻拿到麦
I/Xz: 开口 rms=1264 底噪=420 ... 声道=R 增益=1.6 连接=ok   ← 真的听见了
I/Xz: 识别: 都搬出来了，做穿业10点就。                    ← 云端 ASR 也通了
```

→ 责任方 100% 锁定：**vulture.app.home 独占录音通道**。

### 2.4 第二根病灶：连接静默死掉

`XzClient.java` 里 2026-11-07 就写了注释，但**只做了诊断没修**：

> 「WiFi 路由器的 NAT 表空闲几分钟就回收，而这条 WebSocket 上我们从不发心跳，
> 只被动等云端 ping。如果云端也不发，连接会静默死掉 —— 本地 `open` 还是 true，
> 音频发出去进了黑洞，这一句就'像没听见'。」

原逻辑只在 `beginTurn()` 里判「闲置超过 180 秒就重连」——
**可不喊话就永远进不了 beginTurn**，死连接一直留着，于是"早上第一句"必然踩空。

---

## 三、为什么"过夜"才坏

麦克风是"先到先得"，小智平时一直握着（长命流，播放时不释放）。
只要出现下面任一情况，vulture 就会拿到麦并**再也不还**：

1. 小智进程被杀（内存压力 / `am force-stop` / 系统回收）→ 重启时 vulture 已占
2. 设备半夜重启 → 开机时序上 vulture（系统级常驻）比小智的 BootReceiver 早
3. 小智异常自愈过程中短暂 `release` 了录音

今早的现场是 ①/②：设备 00:14 左右重启过，`mic_owner.sh` 只在开机跑一次，
跑完就没人管了 —— 之后任何一次失手都是**永久聋**。

## 四、修复（四处，缺一不可）

### 4.1 `XzService.openRec()`：真判定（根因修补）

- `startRecording()` 之后检查 `getRecordingState() != RECORDSTATE_RECORDING` → 判定被占用
- 首读 `read()` 两次都 `<= 0` → 判定 HAL 假活，同样当失败
- 失败时 `release()` 掉对象再置 null（不再泄漏 AudioFlinger client）
- **失败就打「麦克风被别的应用占用」，不再伪装「就绪」**

### 4.2 `XzService.loopImpl()`：别拿电钻怼 HAL

- 失败重试从 `sleep(500)` → `sleep(3000)`（退避，越怼越抢不回来）
- 内层读循环连续 20 次读不到（≈200ms）就拆掉重开，比等看门狗 2.5 秒快一个数量级

### 4.3 `XzService.startLinkKeeper()`：连接保活（病根二）

```
每 40 秒：连接空闲 > 30 秒 → 主动发 WebSocket ping（保 NAT 表项）
          空闲 > 240 秒 且 不在对话中 → 判定假死，close + 重建
```
重建只放在非对话态，不会把正在说的话拦腰砍断。
配套 `XzClient.sendPing()`（0x9 帧，走已有的掩码/长度逻辑）。

### 4.4 `mic_keeper.sh`：常驻麦克风守护（兜底）

- 每 15 秒巡检 `dumpsys media.audio_flinger` 的录音持有者
- 小智没麦 → 分级恢复：
  1. 占麦的是 `vulture.app.home` → `force-stop`，**立刻** `startservice PeripheralService`
     （把电话 widget provider + 电源键呼吸灯状态机拉回来，这是 11-07 踩过的坑）
  2. 小智不在 → 拉起 `XzService`
  3. 等 8 秒看门狗自愈；仍不行 → 重启小智
- 安全边界：不认识占麦者只记日志；每小时动手上限 6 次（防踢成风暴）；
  绝不碰 `com.xylink.launcher` / `mediaserver`
- 已挂进 `boot_svc.sh` 的 `start_daemons()`，开机自启
