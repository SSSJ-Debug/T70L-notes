# 故障复盘：命令行 SIGPIPE 触发原厂看门狗重启（2026-11-07）

> **事故等级：P2（单次重启，未进 bootloop，系统自愈）**
> 时间：2026-11-07 21:59:06 埋雷 → 21:59:08 判定 → 21:59:19 重启 → 21:59:40 恢复
> 设备：中移 T70L（Android 4.4.4，sun8i，1G 内存）
> 一句话教训：**`adb shell "cmd" | head` 会让设备上的程序收到 SIGPIPE，Android 4.4 把它记成崩溃；原厂看门狗「180 秒内崩 5 次」就重启整机。**

---

## 一、现象

- 设备在正常运行中突然重启一次
- 重启后正常进桌面，**没有**进入反复重启 / 安全模式循环（与 11-01、11-05 两次 P0 事故不同）
- 用户当时正在等排查结果，看到设备"关机重启"

---

## 二、根因（一条链，四个环节）

```
① Mac 端执行  adb shell "ls -l /data/system/dropbox/" | head -40
② 设备上 ls 还没写完，Mac 端 head 读够 40 行就退出 → 关闭管道
③ 设备上的 ls/grep 继续 write() → 收到 SIGPIPE → 进程死
④ Android 4.4 的 debuggerd 把 SIGPIPE 也写成 tombstone（signal 13）
⑤ NemoWatchdog 的 AppCrashMonitor 数到「180 秒内同一进程崩 ≥5 次」
⑥ NemoWatchdog 执行 rebootSystem → 整机重启
```

### 2.1 铁证一：6 个 tombstone，进程名就是 grep

`/data/tombstones/tombstone_01` ~ `tombstone_06`，全部 13184 字节，同一时刻 21:59:06：

```
pid: 2041, tid: 2041, name: grep  >>> grep <<<
signal 13 (SIGPIPE), code -6 (SI_TKILL), fault addr --------
backtrace:
    #00  pc 000202f4  /system/lib/libc.so (write+12)
    #01  pc 00025869  /system/lib/libc.so (__sflush+50)
    #02  pc 00014537  /system/lib/libc.so (fclose+54)
    ...
    #07  pc 0001c821  /system/lib/libc.so (exit+8)
    #08  pc 00014e47  /system/bin/toolbox
```

**注意：这不是真的崩溃。** SIGPIPE 是"下游关了，我写不进去"，是 Unix 管道的正常语义。
但 debuggerd 只要看到致命信号就 dump，于是被看门狗当成了崩溃。

### 2.2 铁证二：看门狗自己记了重启原因

`/cache/watchdog/reboot_reason.info` 最后一行：

```
REBOOT_REASON : Sat Nov 07 21:59:08 GMT+08:00 2026 , grep crash more than 5 times in 180s
```

与其对应的是 6 个 grep tombstone，**数量对得上规则（≥5 次）**。

| 时刻 | 记录 |
|---|---|
| 21:58:47 | `system_app_anr`（com.android.bluetooth / HidService） |

## 三、为什么不是"内存爆了"

用户第一反应是内存爆了（1G 内存设备）。**实测排除**：

| 证据 | 数值 | 说明 |
|---|---|---|
| MemTotal | 1026456 kB（1002 MB） | — |
| 重启后 MemFree | 291660 kB → 稳定在 224~227 MB | 剩两成以上，远未到 OOM |
| 重启原因 | `grep crash more than 5 times` | 明确不是 lowmemorykiller |
| OOM 特征 | 无 | 没有 `Killed process`，没有 `am_kill`，没有 LMK 记录 |

**Android 的 OOM 应对是杀单个 App（LMK），不是重启整机。** 若是内存不足，表现是"App 被踢掉重开"，不是"整机重启"。

## 四、历史 67 次重启分类（`/cache/watchdog/reboot_reason.info` 全量统计）

| 原因 | 次数 | 性质 |
|---|---|---|
| `app_process crash more than 5 times in 180s` | 36 | **真·灾难**，11-01 集中爆发，即「反复重启到安全模式」 |
| `ps crash more than 5 times in 180s` | 20 | **命令行 SIGPIPE**（`adb shell ps \| head`），同本次 |
| `mediaserver crashed, reboot system` | 6 | **真·系统级崩溃**，与音频链路相关，未解 |
| `ls crash more than 5 times in 180s` | 2 | 命令行 SIGPIPE |
| `grep crash more than 5 times in 180s` | 2 | 命令行 SIGPIPE（本次） |
| `com.lm.guard crash more than 5 times in 180s` | 1 | **我们自己的守护 App**，已随版本更新消失 |

### 4.1 重要结论

> **67 次里，24 次（36%）是 `ps`/`ls`/`grep` 被管道打断造成的，不是设备故障，是操作方式的问题。**

其中 11-05 18:02~18:22 那 10 分钟里连续 10 次 `ps crash`，全是排查时反复 `adb shell ps | head` 造成的——**当时以为是设备坏了，其实是自己一直按着重启键。**

## 六、新增铁律

| # | 禁止 | 原因 |
|---|---|---|
| 12 | ⛔ **`adb shell "命令" \| head` / `\| grep` 直接接管道** | 设备端进程会收到 SIGPIPE，被 debuggerd 记成崩溃，5 次触发重启 |
| 13 | ⛔ **对设备连发大量会被打断的查询命令** | 180 秒窗口内同一进程崩 5 次就到阈值，很容易凑满 |

### 6.1 正确姿势

```bash
# ❌ 错：管道下游提前退出
adb shell "ls -l /data/system/dropbox/" | head -40

# ✅ 对：先落本地文件，再在 Mac 上过滤
adb shell "ls -l /data/system/dropbox/" > /tmp/dbx.txt 2>&1
head -40 /tmp/dbx.txt

# ✅ 对：只要少量输出，用设备端自带的 head（无 busybox 时才可用 Mac 侧）
#    本机 /system/bin 无 head，因此统一用"落文件"方案
```

**原理：`adb shell "cmd" > file` 时管道消费者是 adb 本身，它会一直读到 EOF，不会提前关闭 → 不产生 SIGPIPE。**

### 6.2 如果已经发现自己在制造崩溃

```bash
# 立刻停手，等 180 秒窗口过去（看门狗按窗口计数，不是累计）
sleep 200
# 确认没有新 tombstone
adb shell "ls -l /data/tombstones/" > /tmp/ts.txt
cat /tmp/ts.txt
```

## 七、本次发现的额外资产

### 7.1 `/cache/watchdog/reboot_reason.info` —— 重启原因的权威账本

这是**厂商看门狗自己写的重启记录**，比 dropbox、比 logcat 都直接。
每次怀疑"是不是又自己重启了"，第一件事读它：

```bash
adb shell "cat /cache/watchdog/reboot_reason.info" > /tmp/rr.txt
tail -5 /tmp/rr.txt
```

### 7.2 `NemoWatchdog` 的结构（解析 `strings` 所得）

- 包名 `vulture.watchdog`，APK 在 `/system/app/NemoWatchdog.apk`，以 **system** 身份运行（PID 666 附近）
- 监控器：`ProcessMonitor`、`AppCrashMonitor`、`RecoveryMonitor`、`SystemStatusMonitor`、`NetworkServiceMonitor`、`DndKeyMonitor`
- 落盘：`/cache/watchdog/reboot_reason.info`、`crash_recovery.txt`、`recovery_reason.info`
- 能力：`rebootSystem`、`request shutdown`、`RebootRequestReceiver`
- **已知后门**（见《故障复盘-开机崩溃.md》附录 A）：
  ```
  action : com.vulture.watchdog.EXECMD
  extra  : frompackage = "vulture.app.home"
  extra  : context     = enablenetadb 5656 / cmd:=ainemo!1234 / <任意命令>
  ```
  设备进 bootloop 且 5555 关闭时，这是唯一救命通道 → **5656**。

## 十、一句话收尾

> 11-01 是「常驻循环里放了个必然崩的程序」，11-05 是「常驻循环里放了个必然杀桌面的动作」，
> 这次是「我自己用手敲了 6 次会让设备崩溃的命令」。
>
> 前两次是**代码的错**，这次是**操作习惯的错**。
> 前两次能把机器搞到不能用，这次只是重启一下。
>
> **但三者共同的机制是同一个：`NemoWatchdog` 只要看到某进程 180 秒内崩 5 次，就重启整机。**
> 所以在这台设备上，「不要制造崩溃」不是优化项，是**安全底线**。
