## 一、看家预览卡顿：真凶有三个，全在"从相机到屏幕"这一段

### 1.1 先量，不猜

给 GuardService 加了三个指标，每 2 秒打一行日志：

| 指标 | 含义 |
|---|---|
| `cam Nfps` | 相机**实际**交给我们多少帧（HAL 出口） |
| `gapMax` | 这 2 秒里最大的一帧间隔（平均 15fps 但偶尔掉 300ms 一样读作"卡"） |
| `pv Nfps / cost / drop` | 我们转出多少帧、单帧转换耗时、被界面丢掉了多少 |

改造前后：

| 项 | 改造前 | 改造后 |
|---|---|---|
| 相机出帧 | 14~15fps | 14~15fps（没变，这就是硬件上限） |
| 预览出帧 | **6~10fps** | **14~15fps** |
| 最大帧间隔 | 未测（肉眼可见顿） | **81~122ms** |
| 单帧转换 | ~3ms（320×180） | **5ms（240×135）** |
| 界面丢帧 | 队列堆积、越画越晚 | **drop=0（每帧都画上了）** |

### 1.2 三个真凶

**① 我们自己把帧率锁死在 10fps（最致命）**

```java
// 旧代码：在支持区间里挑"上限最小的、但≥10fps"那一档
if (best == null || range[1] < best[1]) { best = range; }
p.setPreviewFpsRange(best[0], best[1]);     // 于是锁死在 10fps
```

叠加 `maybePreview()` 里 65ms 的节流门限（≈15fps 上限），相机 14fps 和门限一拍一撞，**每隔一帧就被丢掉一帧** → 实际只剩 6~7fps，这就是"卡格"。

改：不再挑选低档，改为显式请求 `setPreviewFpsRange(30000, 60000)`（本机 HAL 只上报一个 `[3000-60000]` 区间，等于把帧率全交给自动曝光），节流门限降到 40ms（≤25fps，相机给多少就放多少）。

**② 只有两块 Bitmap 轮换 → 界面慢一帧，画面就被覆写**

双缓冲在"生产者比消费者快"时必然撕裂：界面正在画 A，服务已经写了 A 又要写 B，下一帧又回头写 A。肉眼就是"一顿一顿 + 边缘错位"。改成**三块轮换**，界面最多同时只有一块在路上，永远不会画到刚被写的那块。

**③ 每帧 `ImageView.setImageBitmap()` → 每帧 new 一个 BitmapDrawable + 一次 layout**

`setImageBitmap` 内部走 `setImageDrawable(new BitmapDrawable(res, bm))`，15fps 就是每秒 15 次分配 + 15 次 `requestLayout`。1GB 的 A83T 上，光这一步就能把 UI 线程拖到跟不上。

改：新增 `PreviewView extends View`，自己 `onDraw` 里 `drawBitmap(src, null, dst, paint)`，只 `invalidate()`，不 new 对象、不触发 layout、不重新测量。

**④ 附带：UI 队列无上限堆积**

旧代码每来一帧就 `runOnUiThread(post)`，UI 一忙队列就越排越长，画出来的都是**过期帧**，视觉上就是延迟 + 抖动。改成 **latest-wins 合并丢帧**：同一时刻只允许一帧"在路上"，新帧直接覆盖旧帧（`previewDrop` 计数），UI 永远画最新那张。

### 1.3 相机能力：查清了，别再折腾

```
preview sizes 1920x1080        ← 只有一档，没法降分辨率换帧率
picture sizes 2688x1520
fps ranges   [3000-60000]      ← 只报一个区间，帧率由自动曝光决定
```

关键实验：**把看家切到后台（不做任何转换）再测，相机仍然只有 15fps**。
→ 结论：15fps 是这颗前摄在室内光照下的物理上限（曝光时间换帧率），不是我们处理不过来。
所以预览的极限就是"稳定 15fps、每帧都不丢"。现在做到了。

> 内存/CPU 代价：240×135 RGB565 三块 = 每块 64KB，共 192KB（固定不涨）；
> 转换 5ms/帧 × 15fps ≈ 单核 7.5%，8 核口径不到 1%。

## 二、191MB 那个进程：`com.ainemo.speech.app`（原厂讯飞语音助手）

### 2.1 它是什么

| 项 | 值 |
|---|---|
| 包名 | `com.ainemo.speech.app`（包名带 ainemo，实际是**讯飞 SDK**：shared_prefs 里有 `com.iflytek.msc.xml`、`KEY_APPID=54043ca1`） |
| 版本 | 1.0.0-19 / targetSdk 22 / uid 10028 |
| 提供的服务 | `SpeechService`（自绑定）、`.service.wakeup.XYWakeupService`（**被 vulture.app.home 绑定**）、`.service.asr.AsrService`、`.service.tts.TtsService`、`.service.understand.UnderstandService` |
| 干什么 | 原厂语音助手：唤醒词 → 识别 → 语义理解 → 合成播报。跟 `vulture.app.home` 里的那套语音是两个独立方案 |

### 2.2 191MB 是"养出来的"，不是"启动就要"

```
长跑后（uptime 10h+） : PSS 191MB，其中 Native 堆 176MB（几乎用满）
force-stop 后冷启动   : PSS  39MB，然后 5 分钟纹丝不动（39.10 → 39.30MB）
```

172MB 全在 native 堆，是讯飞引擎把唤醒词模型 + 声学模型预热进内存的结果。**不是泄漏**（之前 4 分钟采样零增长），但一旦热起来就赖着不走。

### 2.3 处理方案：只禁"唤醒"服务，不整包禁用

```bash
pm disable com.ainemo.speech.app/.service.wakeup.XYWakeupService
```

为什么不整包禁用：`XYWakeupService` 是被 `vulture.app.home` 绑定的，整包禁用会把 ASR/TTS 也一起废掉，而原厂通话里的语音提示（`UIDisplayCustomization` 里 `voiceReminder:true`）可能要 TTS。只掐唤醒，识别/合成仍然可用。

### 2.4 实测证据（都跑在真机上）

| 检查项 | 结果 |
|---|---|
| 冷启动后进程 | **0 个**（`ps | grep ainemo.speech` 只有 calendar，是另一个包） |
| 直接拉起唤醒服务 | `am startservice -a ...service.wakeup` → `Error: Not found` |
| 重启后是否复活 | **不复活**（组件禁用状态持久化，power 循环后仍 0 进程） |
| 原厂 vulture.app.home | pid 全程不变，`FATAL EXCEPTION = 0` |
| 电话 widget / 呼吸灯 | `PeripheralService` 记录恒为 7 条，桌面「电话」卡片正常 |
| 小智 | 录音者 = 小智自己，`状态: 小智正在录音（健康）` |
| 看家 | 预览 14~15fps、抓拍正常 |
| 唯一副作用 | vulture 日志每 ~5 秒一条 `W: Unable to start service ... wakeup: not found`（正常告警，不影响运行） |

**收益**：常驻内存 191MB → 0，MemFree 从 ~250MB 涨到 **452MB**（重启后实测）。

### 2.5 怎么恢复（万一以后要用原厂语音）

```bash
adb -s 192.168.1.151:5555 shell pm enable com.ainemo.speech.app/.service.wakeup.XYWakeupService
```
