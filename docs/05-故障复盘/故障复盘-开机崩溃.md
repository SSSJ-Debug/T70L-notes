# 🔴 重大事故复盘：开机崩溃 / 安全模式死循环

> **事故等级：P0（设备濒临不可用）**
> 发生时间：2026-11-01 17:43 埋雷 → 19:20 爆发 → **20:03 彻底修复**
> 设备：中移定制 T70L（Ainemo NE60 同源，Android 4.4.4，sun8i，已 root）
> 结果：**已根治**。设备正常开机、正常进原厂桌面、ADB 自动上线。
> 一句话教训：**自启脚本里一个 `while true`，差点把这台机器报废。**

## 一、事故摘要

### 1.1 现象

设备通电开机后，屏幕停在「**系统异常，进入安全模式**」的提示页，
数分钟后自动重启，重启后又进同一个页面，如此往复。

- 屏幕显示：`系统异常，进入安全模式` / `按电源键重启退出安全模式`
- 页面里能看到：网络设置、服务器地址 `192.168.1.210:443`、版本 `2.24.0-573`、SN `7Y1912128BD03B29`
- 网络：`ping` 不通有线口（当时网线没插）、WiFi 口能 ping 通但 **5555 端口关闭**
- **所有人都以为 adbd 已经死了，实际它只是换了端口（见 §7）**

### 1.2 一句话根因

> 有人往 `/system/etc/install-recovery.sh` 末尾追加了一段 **`while true` 死循环**，
> 循环体里用 `app_process` 去加载一个**根本不存在的类** `com.nemo.rootd.Main`，
> 于是每 3 秒原生崩溃一次。崩溃被原厂看门狗捕获后，每次都触发 2.9MB 日志打包上传，
> 崩溃次数累积到阈值，原厂判定「系统异常」→ 进安全模式 / 重启 → 死循环。

### 1.3 现场实测数据（触目惊心）

| 指标 | 实测值 |
|---|---|
| 单次崩溃间隔 | **约 3 秒**（下一次崩溃距上次 3.0–4.0s） |
| 崩溃转储文件数量 | **326 份**（`/data/log/pending`，每份约 2.9MB） |
| 崩溃包总占用（Mac 端留存） | **1.1 GB** |
| 设备 `/data/log` 体积 | **832 MB**（修复前） |
| `app_process` 的 PID | 冲到 **9916**（说明已 fork 数千次） |
| `/data` 可用空间 | 5.5G 总 / 已用 1.2G，**按此速率约 1 小时填满** |
| 单机重启周期 | 约 17 分钟一次（uptime 到 1010 秒左右就重启） |

> 这个速率如果放任不管，`/data` 写满后 system_server 会彻底起不来，
> 那时就不是"安全模式"而是**真砖**——而且 /data 写满导致的坏块是不可逆损伤。

## 三、根因分析（四层递进）

### 3.1 第一层：直接原因 —— 加载了一个不存在的类

被注入的脚本片段（**这就是罪证原文**）：

```sh
# --- NemoRootd (appended) ---
(
  i=0
  while [ "$(getprop sys.boot_completed)" != "1" ]; do
    sleep 1; i=$((i+1)); if [ $i -gt 180 ]; then break; fi
  done
  sleep 8
  while true; do                                    # ← 死亡开关
    CLASSPATH=/data/local/tmp/rootd.jar app_process /system/bin com.nemo.rootd.Main \
        >/data/local/tmp/rootd.log 2>&1
    log -t nemorootd "rootd exited, restarting"     # ← 日志里刷屏的就是这句
    sleep 3
  done
) &
```

`rootd.jar` 里只有 `classes.dex`，**解包后没有任何 `.class`，也不存在 `com.nemo.rootd.Main`**。
所以 `app_process` 一启动就报：

```
E appproc : ERROR: could not find class 'com.nemo.rootd.Main'
E dalvikvm: JNI posting fatal error: Native registration unable to find class
            'android/debug/JNITest'; aborting...
F libc    : Fatal signal 6 (SIGABRT) at 0x00000e9c (code=-6), thread 3740 (app_process)
```

崩溃栈（tombstone 实测）：

```
#04 abort+4
#05 dvmAbort+78
#06 jniRegisterNativeMethods+42
#08 android::AndroidRuntime::startReg(_JNIEnv*)+24
#09 android::AndroidRuntime::start(...)
#10 /system/bin/app_process
```

> 为什么报的是 `android/debug/JNITest` 而不是 rootd？
> 因为 `app_process` 在 `startReg` 阶段就把 `framework.jar` 的 JNI 注册表过一遍，
> 主类找不到时类加载器已处于异常态，紧接着注册 `android.debug.JNITest` 也失败，
> 于是 `dvmAbort` 直接 abort。**这条报错是"主类没找到"的次生症状，不是根因。**

### 3.2 第二层：为什么是"每 3 秒一次"

`while true` + `sleep 3`，循环体里的 `app_process` 立即退出（崩溃），
所以节拍完全由 `sleep 3` 决定 —— 实测崩溃间隔 3.0–4.0 秒，与脚本完全吻合。

### 3.3 第三层：放大器 —— 原厂看门狗把 1 次崩溃变成 2.9MB 磁盘写入

原厂 `vulture.watchdog` 注册了崩溃广播：

```java
filter.addAction("com.vulture.watchdog.CRASH");
context.registerReceiver(new CrashEventReceiver(), filter);
```

`vulture.app.wall`（NemoWall，system 身份）收到后执行：

```
I NemoWall: Tar log files: [/data/log/logcat_full.log, /data/log/logcat_full.log.1,
                           /data/log/kernel/kernel.log, /data/anr/traces.txt, /data/tombstone...]
I NemoWall: Upload log url http://<服务器>/api/rest/v3/logUpload?subject=T70L_crash_native_...
I NemoWall: do upload log, open connection: ...
```

**每崩一次 = 打一个 2.9MB 的 zip + 发一个 HTTP 上传。**
因为服务器（本机 8080）没在跑，上传失败 → 重试 → **积压越来越多**。

### 3.4 第四层：为什么变成"安全模式 + 重启"

崩溃计数达到原厂阈值后，系统判定"异常"，进入安全模式兜底页；
安全模式下第三方组件被禁，但**这段脚本是 init 级别的，安全模式根本关不掉它**。
于是：安全模式 → 仍在崩 → 仍被判异常 → 重启 → 再进安全模式。

> ⚠️ **这一点极其关键，也是这次最恐怖的地方：**
> **Android 的"安全模式"对 `/system/etc/install-recovery.sh` 完全无效。**
> 因为它在 init 阶段由 root 执行，跑在系统框架之外。
> 所以"进安全模式就安全了"是**错觉**，安全模式只是把第三方 App 关了，
> 注入在系统层的死循环照样跑，磁盘照样被吃。
> 这次能救回来，不是因为安全模式，是因为**找到了 adbd 换了端口（5656）**。

## 四、为什么会被写出来（决策链复盘）

这次不是"运气差"，是**四个决策错误叠加**的必然结果：

| # | 错误决策 | 正确的做法 |
|---|---|---|
| 1 | 用 `while true` 做"常驻守卫" | 常驻应该是 **init service**（`oneshot` 之外由 init 管）或带判活的有限重试，**绝不在启动脚本里写无上限循环** |
| 2 | 循环体里的程序（`rootd.jar`）**没在设备上先手动跑通**就写进开机脚本 | **任何要写进 `install-recovery.sh` 的命令，必须在设备上手动执行成功 3 次以上**，确认退出码为 0 |
| 3 | 把「开机自启」和「常驻后台服务」混为一谈，都塞进同一个脚本 | 自启 = 一次性拉起 → 单独一个 `( ... ) &`；常驻 = 独立 service 或 APK 前台服务 |
| 4 | 出事后尝试"从应用层修"（`nemofix.apk`）、"轮询 5555 等它出现" | 出事后**第一件事是全端口扫描定位 adbd**，第二件事是 `ps` 找循环进程。绕远了两小时 |

### 4.1 一句话总结错误心态

> **"反正能 push 回去"不是理由。**
> 能被写坏的东西，就一定会在某个凌晨被写坏一次。
> 判据不是"我能不能恢复"，而是"**这段代码有没有能力把设备拖进不可恢复的状态**"。
> `while true` + 会崩的程序 + 每崩溃 2.9MB 写盘 = **有**。所以它一开始就不该存在。

## 五、排查过程（含走过的弯路，下次别再绕）

### 5.1 弯路一：只看 5555，误判"adbd 死了"

```
adb connect 192.168.1.153:5555   → Operation timed out
adb connect 192.168.1.151:5555   → Connection refused
```

`Connection refused` 是**设备回 RST**，说明主机活着、只是没程序监听这个端口。
于是判断"adbd 没起来"，转去找别的入口 —— **这是本次最大的误导**。

**真相**：adbd 一直活着，监听在 **5656**。

来源在解析的原厂看门狗里：

```java
// com/vulture/watchdog/Watchdog.java  executeCommand()
if (cmd.startsWith("enablenetadb") || cmd.startsWith("enablenetadbs")) {
    String[] subcmd = cmd.split(" ");
    String port = "5656";                       // ← 默认端口是 5656，不是 5555
    if (subcmd != null && subcmd.length == 2) port = subcmd[1];
    SystemProperties.set("service.adb.tcp.port", port);
    CommandExecutor.execute("stop adbd");
    CommandExecutor.execute("start adbd");
    if (cmd.startsWith("enablenetadbs")) SystemProperties.set("persist.sys.adbport", port);
}
```

**教训：连不上 5555 时，第一个要试的是 5656。**

### 5.2 弯路二：以为"网口不通 = 设备死了"

`arp -an` 能查到 `192.168.1.153 → <MAC>`（eth0 的 MAC），
但 `ping` 100% 丢包 —— 因为**网线根本没插**，ARP 表是历史残留。

**正确判断方法**：别只看有线口，**WiFi 口（另一个 MAC，`...8b:d0`）也要 ping**。
本次 WiFi 口 `192.168.1.151` 三包全通，说明设备活得好好的。

### 5.3 正确的定位路径（下次照这个走）

```
① 全端口扫（不是只扫 5555）
    asyncio 并发扫 1–65535，2.5s 超时
    → 发现 5656、9010 开着    ← 5656 就是 adbd

② 连上后先看 uptime
    cat /proc/uptime  →  1010 秒 = 17 分钟，说明刚重启过，符合"反复重启"

③ 抓崩溃日志（设备自己会存）
    /data/log/logcat_full.log + /data/tombstone*
    搜关键字：JNI posting fatal / Fatal signal / could not find class

④ 顺着"崩溃是谁拉起来的"找父进程
    ps  → 找到 app_process 的 PID（9916）
    cat /proc/<pid>/stat → 第 4 个字段是 PPID（467）
    cat /proc/467/cmdline → "/system/bin/sh /system/etc/install-recovery.sh"
    ★ 到这一步，元凶锁死

⑤ 看脚本内容
    cat /system/etc/install-recovery.sh → 看见 while true，收工
```

**最有用的一招：从崩溃进程反查父进程，再反查父进程的 cmdline。**
（这台设备没 `pgrep`/`pstree`，就手写 `cat /proc/*/stat` 找 PPID）

### 5.4 怎么"证明"污染源还在跑

不要靠猜。在 Mac 上开一个 HTTP 监听，看设备是不是还在发崩溃包：

```python
# 监听 8080，只记录不干扰
srv.bind(('0.0.0.0', 8080)); srv.listen(50)
# 实测：每秒 2+ 个 POST /api/rest/v3/logUpload?subject=T70L_crash_native...
```

**看到这个就 100% 确定：循环还在跑，必须立刻掐。**

## 六、修复全过程（完整可复现）

### 6.1 第一步：止血（纯内存态，不动任何存储）

```bash
export PATH=$HOME/re-tools/platform-tools:$PATH
D=192.168.1.151:5656

# 找到循环进程
adb -s $D shell ps | grep install-recovery     # → root 467 1 ... /system/bin/sh
# 干掉它
adb -s $D shell "kill -9 467"
```

> **为什么杀进程能停？** `init.rc` 里：
> ```
> service flash_recovery /system/etc/install-recovery.sh
>     class main
>     oneshot
> ```
> `oneshot` = init 不会重启它。所以杀掉子 shell，只要不重启设备就不会再起。
> **但下次开机会重新执行脚本 → 必须改文件。**

### 6.3 第三步：准备原厂文件（唯一可信的还原源）

> **这个"原厂文件"是哪来的？（常被问，必须写死）**
> 不是从坏掉的设备上取的，也不是网上找的——**是厂商自己放在官方 CDN 上的全量 OTA 包里的原件**。
>

>
> **① 设备自己把下载地址告诉了我们**
> 设备开机后会向 `cloud.xylink.com` 查系统更新。我们把它劫持到本机做了 TLS MITM（`srv443.py` / `https_mitm.py`），
> 在 `https.log` 里抓到了它请求更新接口的**原始响应**：
>
> ```json

>   "platform": "crushos",

>   "versionName": "2.24.0-573",
>   "versionCode": 22400,

>   "packageName": "os"

> ```
>
> **② 按这个官方 URL 下全量 OTA 包**
> `~/re-tools/t70l/firmware/octopus_crush_2.24.0-573.zip`（**134 MB**）
>
> **③ md5 与官方公布值逐字节一致**

具体路径与校验值：

```

> 📌 **这条经验本身很值钱**：全网确实搜不到这台机器的固件。
> 但厂商的 OTA CDN 是公开的，设备自己会去查更新接口 ——
> **劫持它自己的更新请求，就能拿到官方全量包**。
> 以后任何一台这类封闭设备，"找不到固件"都不是终点。

内容就是 7 行，只做一件事——检查并修补 recovery 分区：

if ! applypatch -c EMMC:/dev/block/by-name/recovery:13260800:ee0bbdabca7ef03a2aaaf7fb1190643a01f3e9f6; then
  log -t recovery "Installing new recovery image"
  applypatch -b /system/etc/recovery-resource.dat EMMC:/dev/block/by-name/boot:12300288:... /system/recovery-from-boot.p
else
  log -t recovery "Recovery image already installed"
fi
```

### 6.4 第四步：写回 /system（**先校验 md5 再落地**）

```bash
adb -s $D push install-recovery.ORIG.sh /data/local/tmp/ir_orig.sh
adb -s $D shell "md5 /data/local/tmp/ir_orig.sh"
#   必须输出 24d0c93530dc8b873a9760455aa1c8a1 才能继续

adb -s $D shell "mount -o rw,remount /system"
adb -s $D shell "cp -f /data/local/tmp/ir_orig.sh /system/etc/install-recovery.sh"
adb -s $D shell "chown 0:0 /system/etc/install-recovery.sh"
adb -s $D shell "chmod 544 /system/etc/install-recovery.sh"
adb -s $D shell "chcon u:object_r:system_file:s0 /system/etc/install-recovery.sh"
adb -s $D shell "sync"
adb -s $D shell "mount -o ro,remount /system"
```

> **两个坑：**
> 1. `chcon` 会报 `Permission denied`（shell 域没有 relabel 权限）。
>    **不用管**——`cp -f` 复用了原 inode，标签本来就是 `system_file:s0`。
>    写完后用 `ls -lZ` 确认即可。
> 2. 上面前四步用 `&&` 串联时，`chcon` 失败会让后面的 `sync` 不执行。

## 八、🔴 铁律（从这次开始，永久生效）

### 8.1 绝对禁止

| # | 禁止 | 原因 |
|---|---|---|
| 1 | ⛔ **在任何开机/自启脚本里写 `while true` 或无上限循环** | 循环体一旦会崩，就是确定性灾难。这次差点报废整机 |
| 2 | ⛔ **把没在设备上手动跑通的命令写进 `install-recovery.sh`** | `rootd.jar` 缺类，手动跑一次就能发现，但直接写进了开机脚本 |
| 3 | ⛔ **把"常驻服务"塞进启动脚本**（靠 `&` 挂着） | 启动脚本只管"拉一次"，常驻该交给 init service 或 APK 前台服务 |
| 4 | ⛔ **只改文件不验证 md5** | 写错一个字节，下次开机就不确定是不是原厂脚本 |
| 5 | ⛔ **出事时只盯着 5555 端口** | adbd 可能在 5656，也可能在任意端口 |
| 6 | ⛔ **认为"进安全模式就安全了"** | 安全模式只禁第三方 App，**禁不了 `/system/etc/install-recovery.sh`** |

### 8.2 写自启脚本的唯一正确姿势

```sh
# ✅ 只做"拉一次"，失败就放弃，绝不重试到死
(
  n=0
  while [ "$(getprop sys.boot_completed)" != "1" ] && [ $n -lt 120 ]; do
    sleep 1; n=$((n+1))
  done
  [ "$(getprop sys.boot_completed)" != "1" ] && exit 0     # 没起来就安静退出

  # 前置判活：目标存在才执行
  [ ! -f /data/local/tmp/target.jar ] && exit 0

  am start -n com.xxx/.MainActivity >/dev/null 2>&1
  log -t xxx "autostart rc=$?"
) &
```

**四条硬要求：**
1. **所有循环必须有上限**（`n -lt N`），到点就 `break`/`exit`
2. **执行前先判活**（文件在不在、命令有没有）
3. **失败写日志并放弃**，不要 `while true` 重来
4. **整体 `( ... ) &` 后台化**，绝不阻塞 init

### 8.3 落地前的强制流程（少一步都不行）

```
① 在设备上手动执行一遍完整命令，看退出码        ← 必须
② 连续执行 3 次，都成功                          ← 必须
③ 用 ( ... ) & 包起来，先放在 /data/local/tmp 试跑 ← 必须
④ 观察 5 分钟，确认不会持续崩溃/写盘             ← 必须
⑤ 才 push 进 /system，且先备好原厂文件           ← 必须
⑥ 重启验证，看 uptime 是否稳定递增               ← 必须
```

> **任何一步答"应该没事吧"，立即停手。** 这次就是"应该没事吧"的代价。

## 九、附录 A：原厂看门狗后门（本次救命的通道）

解析 `com.vulture.watchdog.Watchdog` 得到的完整命令表：

```java
public void executeCommand(String cmd) {
    if (cmd.startsWith("enablenetadb") || cmd.startsWith("enablenetadbs")) {
        String port = "5656";                                      // ← 默认 5656
        SystemProperties.set("service.adb.tcp.port", port);
        CommandExecutor.execute("stop adbd"); CommandExecutor.execute("start adbd");
        if (cmd.startsWith("enablenetadbs")) SystemProperties.set("persist.sys.adbport", port);
        return;
    }
    if (cmd.equalsIgnoreCase("disablenetadb")) { ... }
    if (cmd.equalsIgnoreCase("cmd:=ainemo!1234") ||
        cmd.equalsIgnoreCase("hoho::goodnight!1234")) { this.cmdPass = true; return; }   // ← 解锁 root
    if (cmd.equalsIgnoreCase("disableroot")) { this.cmdPass = false; return; }
    if (this.cmdPass) { CommandExecutor.execute(cmd); return; }                          // ← root 执行任意命令
    // 未解锁：execute_shell(cmd)，且拦截含 rm / mv / reboot / kill 的命令
}
```

**触发方式（广播，只校验一个字符串）：**

```

extra   : context     = <命令>
```

|---|---|
| `enablenetadb [port]` | 开 adbd（默认 5656），不持久化 |
| `enablenetadbs [port]` | 开 adbd 并持久化到 `persist.sys.adbport` |
| `disablenetadb` | 关 adbd |

| `disableroot` | 重新上锁 |
| （解锁后）任意命令 | **以 root 执行** |
