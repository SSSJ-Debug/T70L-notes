# 故障复盘 · 2026-11-08 · 看家「正在接管 / 暂无画面」与低清实时预览

> 设备：中移 T70L（全志 A83T / Android 4.4.4 / 1280×800 / 1G RAM），`192.168.1.151:5555`
> 涉及：`guard.apk`（com.lm.guard）、`cam_guard.sh`、`boot_svc.sh`、`mic_keeper.sh`
> 结果：接管从「永远卡住」→ 相机空闲 2 秒 / 原厂占用 2~4 秒；预览 6fps 卡顿 → 11~12fps 流畅；抓拍仍 1080p 高清、邮件照发。

---

## 1. 用户报的三个现象

1. 开启看家后，预览窗长期显示「摄像头 · 正在接管」+「暂无画面」，摄像头一直出不来。
2. 希望实时预览是「非常低清、但流动、不占内存/CPU」的画面；抓拍仍要高清。
3. 从点「开始看家」到看见画面，感觉慢。

---

## 2. 根因（两层，缺一不可）

### 2.1 第一层：唯一能让原厂交出相机的 `cam_guard.sh` 被撤掉了

`/data/local/tmp/cam_guard.sh` 在 **2026-11-07 12:20** 被从 `boot_svc.sh` 的 `start_daemons()` 里整段删除。
当时的理由写在 `boot_svc.sh` 头部：force-stop `vulture.app.home` 会导致电话 widget 消失、电源键呼吸灯常亮。

后果：这台机器上**没有任何进程能把相机从原厂手里抢过来**。
实测（本次取证）：

```
$ dumpsys media.camera
Camera 0 static information:  Facing: FRONT
  Device is open. Client instance dump:
    Client[0] (0xb7dee288) PID: 1845      ← vulture.app.home 抱着前摄
$ ps | grep vulture.app.home
u0_a35  1845 ... S vulture.app.home        ← 开机 9 分钟一直在
```

而 `guard.apk` 拿不到 root（`su -c id` 返回 1），唯一通道就是写 `/sdcard/HomeGuard/.need_cam` 让 root 脚本动手。
脚本没了 → 请求文件没人读 → `Camera.open(0)` 永远失败 → UI 一直「正在接管」。

### 2.2 第二层：`cam_guard.sh` 的存活判定被「pid 复用」骗了

补回脚本后又出现一个更阴的问题：**重启后它自己不启动**。

原因：`is_running()` 只做 `kill -0 $pid`。重启后 `/data/local/tmp/cam_guard.pid` 里还是上一轮的旧 pid，
而系统把这个 pid 分给了别的进程（本次实测 `991 = com.ainemo.speech.app`），`kill -0` 成功 →
脚本认为「我还在跑」→ 直接退出 → 看家永远拿不到相机。

证据（重启后 boot_svc 日志）：

```
02:32:09 相机守护 pid=991          ← 抄的是旧 pid 文件内容，实际没启动
$ cat /proc/991/cmdline
com.ainemo.speech.app              ← 根本不是 cam_guard
```

**修法：心跳文件。** loop 每轮把 `date +%s` 写进 `/data/local/tmp/cam_guard.beat`，
`is_running()` = pid 活着 **且** 心跳 20 秒内更新过。`mic_keeper` 同样加了心跳（120 秒）。

## 3. 低清实时预览怎么做的

原设计里预览窗只显示「最近一张抓拍」（一张静态 JPG），完全没有实时画面。

### 3.1 方案取舍

| 方案 | CPU | 内存 | 风险 |
|---|---|---|---|
| A. 相机直接输出到 SurfaceView（硬件缩放） | 最低 | 最低 | 要停预览/切 Surface，原厂 HAL1 上易黑屏，且会打断人脸检测 |
| B. 离屏纹理 + GL 渲染 | 低 | 中 | 要写 shader / GLSurfaceView，4.4 上坑多 |
| **C. 回调里把 NV21 采样成 320×180，双缓冲 Bitmap 交给 UI** | **约 3% 单核** | **2×115KB 固定** | **不碰相机配置，检测/抓拍零影响** |

选 C。清晰度按用户要求「能看出画面在动就行」，高清全部留给抓拍。

### 3.2 关键实现（`GuardService.java`）

```java
// 每帧：只在界面前台时才转（sink == null 直接 return，一个像素都不算）
if (now - pvAt < 65) return;              // ~15fps 上限
downscaleInto(bArr, w, h, pvPix, 320, 180);   // 复用 int[]，零分配
bm = pvUseB ? pvB : pvA; pvUseB = !pvUseB;    // 双缓冲，防撕裂
bm.setPixels(pvPix, 0, 320, 0, 0, 320, 180);
sink.onPreview(bm, now);                       // MainActivity 里 post 到 UI 线程
```

- `downscaleInto()` 与原来的 `downscale()` 同一套定点 YUV→RGB 常量，只是不再 `new int[]` / `new Bitmap`。
- `MainActivity.onResume()` 注册 sink，`onPause()` 置 null —— **息屏/切走时预览零开销**，检测和抓拍照跑。
- 预览窗下方状态直接显示 `摄像头 1920×1080 · 实时 Nfps`，一眼能看出画面是真在动。

### 3.3 为什么一开始只有 6fps

两个原因叠加：

1. 节流门限定在 90ms，而设备实测出帧间隔约 80ms → 每两帧才放过一帧 → 6fps。
   改成 65ms 后与出帧节奏对齐。
2. 人脸检测原来和相机回调**共用一条线程**：`FaceDetector` 一次约 200ms，这 200ms 里
   回调线程被占住、缓冲不还给相机 → 预览每 1.2 秒卡 200ms，看起来就是"一顿一顿"。

修法：新增 `guard-detect` 线程专门跑检测，相机回调线程只做「缩图给界面 + 还缓冲」；
回调缓冲从 2 块加到 3 块（检测扣住一块时相机仍有缓冲可用，多花 3MB）。

## 4. 接管提速（点「开始看家」→ 有画面）

| 版本 | 相机空闲 | 原厂占着 |
|---|---|---|
| 修复前 | 卡死（无 cam_guard） | 永远「正在接管」 |
| 补回 v1（2s 轮询 + 2.5s 重试） | ~3s | 4~6s，且可能被原厂抢回 |
| **v2（0.4s 轮询 + 400ms 重试 + 预请求）** | **2s** | **2~4s** |

v2 的三处改动：

1. `cam_guard` 轮询 `usleep 400000`（0.4s），原来 2s；
2. 看家失败重试 400ms（原来 2500ms），前 20 次都这么快；
3. **预请求**：`openLoop` 第一次尝试就先把 `.need_cam` 递出去，和 `Camera.open` 并行跑；
   `cam_guard` 收到请求先看相机是不是真空着，空着就跳过 force-stop（不白杀原厂）。

### 4.1 怎么避免 11-07 那两个副作用

force-stop 原厂后**不立刻**拉它的服务，而是等「看家已经拿着相机」再 `am startservice PeripheralService`：

```
need_cam → force-stop vulture → 看家 400ms 内抢到相机（先到先得，占住就抢不走）
         → 确认 cam_pid == guard_pid → 才拉起 PeripheralService（电话 widget + 呼吸灯）
         → 15 秒还没交出去（用户中途退出）→ 兜底也把 PeripheralService 拉回来
```

实测：接管后 `dumpsys activity services` 里 `PeripheralService` 记录数 = 7，桌面截图电话图标正常。

## 5. 我自己搞出来的两次重启（教训，必须记住）

调试过程中设备重启了两次，原因都是**设备侧管道踩 SIGPIPE**，被 NemoWatchdog 记成
"xxx crash more than 5 times in 180s" 直接 `rebootSystem`：

```
Sun Nov 08 10:32:38 , grep crash more than 5 times in 180s
Sun Nov 08 10:34:38 , sh crash more than 5 times in 180s
Sun Nov 08 10:36:35 , sh crash more than 5 times in 180s
```

具体写法：

1. `ps | grep | awk | head -n 1` —— 设备上**没有 awk/head**，管道断裂；
2. `sh cam_guard.sh status | busybox grep -q running` —— `grep -q` 一匹配就退出，
   `sh` 继续写输出吃 SIGPIPE，15 秒一次（mic_keeper 保活），攒 5 次直接重启。

### 铁律（写进脚本注释）

- 设备侧**禁止** `cmd | grep -q` 和 `cmd | head -1` 这种「消费端提前退出」的管道。
- 统一姿势：`ps > /tmp/.ps` / `dumpsys xxx > /tmp/.dump`，再让 `busybox awk` **从文件读**。
- adb 输出先在 Mac 侧落文件再过滤，别在设备里串管道。

`cam_guard.sh` / `mic_keeper.sh` 已全部改成分文件 + 文件版 awk，并新增 `cam_guard.sh check`
（只回退出码，不给调用方任何可提前关闭的管道）。
