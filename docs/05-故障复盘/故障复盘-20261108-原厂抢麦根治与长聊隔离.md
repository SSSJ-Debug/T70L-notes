## 一、原厂 App 到底是什么（结论：不能删）

包名 `vulture.app.home`（v2.24.7-1583，装在 `/data/app/`，不是 system 分区）。
厂商是**小鱼在家 / ainemo（Nemo 系列）**，这套 ROM 一共有 12 个 `vulture.*` 包：

| 进程 | 干什么 |
|---|---|
| `vulture.watchdog` | **整机看门狗**（system 权限，异常会 rebootSystem） |
| `vulture.app.home` | 业务主壳：视频通话、通讯录、留言、消息中心、设置、桌面 widget、呼吸灯 |
| `vulture.app.lanucher` | 桌面 |
| `vulture.app.wall` | 壁纸 |
| `vulture.driver_service` / `proxy_service` / `network_service` / `update_service` / `app.location` / `app.diagnostics` | 驱动/代理/网络/升级/定位/诊断 |

`vulture.app.home` 里跟"用得上"直接相关的组件（解析清单）：

- 通话：`NemoCallActivity`、`NemoIncomingCallActivity`、`IncomingDialogActivity`、`NemoServerTriggerCallActivity`
- 通讯录：`ContactsActivity`、`ContactDetailActivity`、`DepartmentActivity`
- 留言：`NemoRecordActivity`
- 消息：`MessageCenterActivity`、`FloatNotification`
- 桌面 widget：`TelephoneAppwidget`、`MessageCenterAppwidget`、`ScheduleAppwidget`、`LargeScreenAppwidget`
- **外围设备：`vulture.service.PeripheralService`** ← 电源键呼吸灯、电话 widget 依赖它
- 系统设置一整页：`SystemSetting*Activity`（网络/音频/通话/自动接听/语言）
- 语音：`speech.activity.SpeechActivity` + `SystemSettingDoryActivity`

### 所以：不能删

- 删掉 system_server 不会崩，但**视频通话、通讯录、留言、消息中心、设置页、桌面 widget、呼吸灯全废**。
- 更麻烦的是 `vulture.watchdog`（system 进程）会持续检测，包缺失/进程反复起不来 → 可能直接 `rebootSystem`，变成**开机重启循环**。
- `PeripheralService` 一旦没了，呼吸灯和电话 widget 就掉（11-07 已经踩过一次）。

**结论：一个字节都不删。改用厂商自己留的开关。**

## 二、抢麦的真凶与官方开关

### 代码路径（解包工具 解析 `vulture.app.home` 得到）

```java
// vulture/module/speech/SpeechModule.java:63-67
LOGGER.info("getVoiceAssitantSetting " + b.r().getVoiceAssitantSetting());
this.isEnable = VoiceAssitantSettting.parse(b.r().getVoiceAssitantSetting()).enableVoiceAssitant;
this.mVoiceProcessor = new VoiceRecognitionProcessor(context, this);

// 同文件 159 行
this.mVoiceProcessor.init();
if (this.isEnable) {
    this.mVoiceProcessor.startSpeechUtils();   // ← 只有这里才真正开始语音
    i.a().a(i.f10747a, this);                  // ← 注册音频消费者
    this.isRunning = true;
}
```

开关存在 `local_config.xml`（SharedPreferences），键名 `VoiceAssitantSetting`，
JSON 结构由 `VoiceAssitantSettting`（厂商自己拼错了三个 t）定义：

```java
public boolean enableVoiceAssitant = true;   // 默认 true
public boolean collectWakeupData  = true;
public float   wakeupLowThreshold  = 0.4f;
public float   wakeupHighThreshold = 0.7f;
```

**关键事实：这个键在原机配置里根本不存在**，所以 `parse("")` 走异常分支 → `new VoiceAssitantSettting()`
→ `enableVoiceAssitant = true` → **出厂即常开**。这就是"过几个小时它就自己听不见了"的物理原因：
原厂语音助手开机就跑，抢到录音通道就不放。

另外 `setVoiceAssitantSetting()` 在整包代码里**没有任何调用者**，
说明云端下发不会覆盖这个键 —— 写一次就稳定。

### 动手改的（只改这一行）

```
/data/data/vulture.app.home/shared_prefs/local_config.xml
+ <string name="VoiceAssitantSetting">{"enableVoiceAssitant":false,"collectWakeupData":false,
                                        "wakeupLowThreshold":0.4,"wakeupHighThreshold":0.7}</string>
```

原文件已留底：`/data/local/tmp/local_config.xml.orig`、本地 `local_config.xml.bak-before-off`。

## 四、长聊天隔离（用户第二条诉求）

### 病根两个

1. **`continuous = true`**（`Prefs.java:10` 默认值，设备配置里也是 true）
   → 喊一次"小智"答完一句，接下来 `idleTimeoutSec = 25` 秒内**所有话都不用唤醒词就被接走**。
   家人正常聊天全被当成在跟它说话 —— 这就是"长聊天自己就开了"。
2. **`chatIntent` 靠猜**：旧判据是「人称 + 聊音」两个条件同时成立就算进畅聊
   ```java
   boolean who  = 陪我 / 咱俩 / 我们 / 和我 / 跟我;
   boolean talk = 聊 / 疗 / 辽 / 唠;
   if (who && talk) return true;     // ← "小智，我们聊聊今天天气" 直接进畅聊
   ```
   猜错一次，后面 5 分钟（CHAT_IDLE_SEC=300）全是错的。

### 改法

| 文件 | 改动 |
|---|---|
| `Prefs.java` | `continuous` 默认 `true` → **`false`**（每句都要喊「小智」） |
| `XzService.chatIntent()` | 重写：**只认完整词组**，不再"人称+聊"猜意图 |

新暗语表（必须完整出现）：
`聊聊天 / 聊聊吧 / 聊会儿 / 聊一会 / 聊一下 / 聊一聊 / 陪我聊 / 陪你聊 / 和我聊 / 跟我聊 / 咱俩聊 / 说说话 / 唠嗑 / 唠会儿 / 侃大山 / 畅聊 / 长聊 / 聊天模式`

ASR 容错保留：先把「疗/辽/撩/料」归一化成「聊」再匹配，但**仍须凑成完整词组**，单说"治疗""辽宁"不会命中。
