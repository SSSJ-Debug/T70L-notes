# 故障复盘：tinymix 轮询触发整机重启（2026-11-08 17:30）

## 一句话结论

我在给小智加"麦克风增益巡检"时，让守护脚本**每 30 秒执行一次 `tinymix`**。
这台机的 NemoWatchdog 把**任何短命进程都记成 crash**，180 秒内出现 5 次就 `rebootSystem()`。
于是 17:30:39 整机重启，账本原话：

```
REBOOT_REASON : Sun Nov 08 17:30:39 GMT+08:00 2026 , tinymix crash more than 5 times in 180s
```

**这不是偶发，是必然。** 历史上同一台机已经因为同样的原因重启过：

| 时间 | 账本原话 |
|---|---|
| 11-05 18:05 ~ 20:05（10 次） | `ps crash more than 5 times in 180s` |
| 11-07 12:20 | `ls crash more than 5 times in 180s` |
| 11-07 21:59、11-08 10:32 | `grep crash more than 5 times in 180s` |
| 11-08 10:34、10:36 | `sh crash more than 5 times in 180s` |
| **11-08 17:30** | **`tinymix crash more than 5 times in 180s`** ← 本次 |

也就是说：**`ps`、`grep`、`ls`、`sh`、`tinymix` 这五个命令，每一个都单独把整机搞重启过一次。**
它们的共同点只有一个 —— 都是**执行完就退出的短命进程**。

## 二、为什么之前的守护没出事（重要）

同样在跑、同样每 15 秒一轮的 `mic_keeper.sh` 没触发，原因值得记住：

- 它启动时用 `setsid`，**父进程被 init 收养，ps 里显示的进程名是 `/sbin/busybox`**
- 它内部大量用 `$BB awk`、`$BB grep`、`$BB tr` —— 这些是 **busybox 的 applet**，
  在本机 watchdog 眼里被归成 `busybox`，而不是独立命令名
- 而 `tinymix` 是 `/system/bin/tinymix` 独立二进制，名字独一无二，直接进账本

所以"用 busybox 跑命令"在这台机上是**相对安全**的；
**直接调用系统独立二进制（tinymix / ls / ps / grep / sh）并高频执行，才最危险。**

## 三、修复（已上线）

| 项 | 改法 |
|---|---|
| `xz_guard.sh` | **v4：彻底取消常驻 loop**。只在开机跑一次 `once`（设 DMIC 增益 190 + 拉起服务）。文件头写死铁律：**本脚本绝不轮询任何外部命令** |
| `boot_svc.sh` | 开机调用从 `xz_guard.sh start` 改成 `xz_guard.sh once` |
| `XzService.selfRestart()` | 原来用 `Runtime.exec("sh -c ...")` 实现"3 秒后自己回来"，同样会攒 `sh crash`。改成**只 kill 自己，零新进程**，由 `mic_keeper` 15 秒巡检拉起 |
| 小智假死恢复 | 全部收到 App 内部：主循环心跳 6 秒不动 → 拆录音 + 断连接；12 秒仍不动 → 退出进程。外部只做"进程不在就拉起" |

**当前状态**（17:36 实测）：uptime 284s 稳定、无新重启账本记录、小智 pid 6722 在录、MemFree 345MB。

## 四、以后加守护脚本的硬规则（写死，别再犯）

1. **不要在 loop 里调用 `tinymix`、`ps`、`ls`、`grep`、`sh`、`cat` 这类独立二进制。**
   要读硬件状态，只在**开机/手动**时读一次。
2. 必须常驻的巡检，优先用 **busybox applet**（`$BB awk` / `$BB grep`），且间隔 ≥ 30 秒。
3. 任何"被杀/重启/退出"路径**都不许 exec 新进程**，一律 kill 自己 + 交给既有守护。
4. 加完守护脚本，**先看 `/cache/watchdog/reboot_reason.info`** 再观察 10 分钟，
   确认账本没有新增同类记录，才算上线。

## 五、这次顺带查明的另一个真问题（未完成）

排查小智为什么"喊开灯没反应"时，日志给出了铁证：

```
14:45:02  最后一条业务日志（回答：那就先这样，好好休息，拜拜！）
14:45 ~ 17:12  只剩连接层每分钟一条「连接断开」，没有任何「开口 / [空闲]」
```

抓线程栈（`kill -3`）确认：

```
"xz-loop" NATIVE
  #01 android::ClientProxy::obtainBuffer(...)
  #02 android::AudioRecord::obtainBuffer(...)
  #03 android::AudioRecord::read(void*, unsigned int)
```

**主循环卡死在 `AudioRecord.read()`，一个字节都拿不到。**
而当时的看门狗代码是 `if (inTurn) { lastFrameAt = now; continue; }` ——
主循环正卡在 `endTurn()` 里（等待云端回答），`inTurn` 还是 true，
看门狗**每 1.5 秒亲手把"卡死"刷成"刚刚还有数据"**，于是永远判不出来。

已修：改成只看 `loopBeat` 心跳（主循环顶 / 录音内层 / endTurn 两个等待循环都刷），
6 秒不动就拆录音+断连接，12 秒仍不动就退出进程。

另一个隐患也一并修了：`playing` 标志只在 `endTurn()` 末尾和 `playRaw()` 的 finally 复位，
一旦 TTS 收尾信号丢失就永久为 true，主循环每帧 `if (playing) continue`，同样永久失聪。
现在播放队列空 2 秒会自动放下 `playing`。
